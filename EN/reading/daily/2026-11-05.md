# How Agents Handle Long Inputs: Selective Reading, Working Memory, and Correct Replay

The main reading covers the 2026 revision of RLM: keep long materials in an external environment and let the model write programs to select passages, invoke submodels, and combine results. MEM1 explains reinforcement learning for compact working-memory updates; the 2026 MemoryWalker paper examines how edited histories should be replayed for training. The three readings address accessing, retaining, and replaying information. Start with the RLM example and explore the companions as needed. Recursive calls do not establish recursive self-improvement, and short compressed inputs do not guarantee lossless memory.

Each digest recommends 1 main paper and 2–4 optional papers across LLM inference, RL infrastructure, post-training, RSI (recursive self-improvement), reasoning compute, agent learning and memory, data and evaluation, and model architecture. Explore foundations and current research by theme; a direct connection to current work is not required. A recommendation does not mean it has been read, and there is no need to finish everything in one day.

## Main reading · Recursive Language Models

**Year / publication：** 2025 · NeurIPS 2026 (author publication page); arXiv v3, 2026-05-11 · MIT CSAIL · [Original source](<https://arxiv.org/abs/2512.24601v3>)

**Reading guidance：** Worth close reading. Use Figure 2 and Algorithm 1 to locate the information, then examine Table 1, failure trajectories, and the v3 training studies to separate better access from added computation or training.

### Start with a concrete problem: reading many records without missing a count

Imagine a long file of user questions. You need to decide whether questions asking for a quantity outnumber questions asking why something happens. “How many meters long is the bridge?” and “Why does water freeze?” have no category labels attached: someone must interpret each sentence before counting. Retrieving a few relevant passages may omit records, while summarizing first may discard details that change the total. This teaching example illustrates OOLONG’s requirement to classify individual records and then aggregate them. [§3.1](https://arxiv.org/html/2512.24601v3#S3.SS1)

RLM lets the model write a small program that decides where to look, how to divide the material, what to send to another model call, and how to combine the results. It changes how the model accesses information while solving a task. Even when the original file is extremely long, every neural model call still has its existing context-window limit. [§2](https://arxiv.org/html/2512.24601v3#S2)

### Step one: keep the full material in a variable and inspect it on demand

The paper stores the long input in a persistent Python interactive environment: variables created in one turn remain available in the next. This environment is a REPL. The coordinating “root model” initially receives metadata such as the material’s length, a short prefix, and instructions for accessing it, rather than the entire file. It can write code to inspect a few lines, split on newlines, or search for a word, then choose its next step from the execution result. [Figure 2 and Algorithm 1](https://arxiv.org/html/2512.24601v3#S2)

The complete text and intermediate results remain in environment variables; printed output shown to the root model is truncated so that it does not simply fill the window again. Context offloading here means placing text outside the model window, not implementing a new KV-cache migration algorithm. The root model’s own conversation history still grows, and the paper acknowledges the need to limit iterations at each level. Handling a very long input does not give an individual model call infinite memory.

### Step two: let the model interpret sentences and let code do the counting

In our example, the root model could inspect the file format and divide the questions into batches. A code loop asks a submodel to classify the questions in each batch. The returned labels and record IDs are stored in a list, after which Python counts the two categories. The model handles meaning; code handles exact counting. The root decides batch sizes and whether to inspect results again during the task. This illustrates the mechanism, rather than a mandatory workflow for every RLM task. [§2 and Appendix E.3](https://arxiv.org/html/2512.24601v3)

The important feature is not merely calling several agents: model calls can occur inside programmatic loops. A short program can process many batches without making the root spell out every full delegation separately. Retrieval and summarization can still be tools, but when every record affects the answer, code can iterate over all records instead of relying only on a few preselected passages. Submodels can misclassify records, so exact counting does not guarantee that the labels being counted are correct.

### Step three: preserve outputs in the environment and control recursive depth

If a task asks for a long list of qualifying user pairs, code can store that list in a variable and return the variable directly, without having the root model copy out the entire answer token by token. The implementation supports both direct answers and returning an environment variable. This output path matters: after solving the long-input problem, the resulting answer may itself be too long for a single root generation. [§2 and Appendix C.1](https://arxiv.org/html/2512.24601v3#S2)

The paper evaluates maximum recursion depths from 0 to 3. Depth 0 has a root model and a code environment but no model subcalls. Depth 1 allows ordinary model subcalls. At greater depths, a subcall can itself run an RLM process and further divide the problem. “Recursive” describes the call structure, not a model rewriting its own training procedure during execution. The framework can use unchanged model parameters, while a separate training procedure can teach models to use it better. These are distinct claims. [§3.2](https://arxiv.org/html/2512.24601v3#S3.SS2)

### Evidence one: effective on very long documents, without beating every alternative

The main experiments use GPT-5 with medium reasoning and Qwen3-Coder-480B-A35B. The GPT-5 RLM uses GPT-5 at the root and GPT-5-mini for subcalls. BrowseComp+ contains 150 randomly sampled evaluation questions, each supplied with 1,000 documents guaranteed to include the answer evidence, totaling roughly 6–11 million tokens. This is question answering over an offline document corpus, not unrestricted web browsing. [§3.1–3.2 and Table 1](https://arxiv.org/html/2512.24601v3#S3)

In Table 1, the depth-1 GPT-5 RLM scores 91.3%, with mean API cost $0.99 per question and standard deviation $1.22. The compaction system scores 70.5%, with mean cost $0.57 and standard deviation $0.10. That baseline uses GPT-5-nano for compaction and GPT-5 for the answer: this compares complete system configurations, not a strictly matched model-and-budget intervention. OpenCode with the material offloaded to a file scores 94.0% in the same table, above this RLM configuration. The evidence supports RLM as an effective approach, not universal superiority on document retrieval. [Table 1](https://arxiv.org/html/2512.24601v3#S4)

### Evidence two: fitting the material does not ensure reliable processing of every record

The main OOLONG-Pairs setting has only about 32K input tokens and 20 queries, but requires listing qualifying pairs based on the meaning of the records. Its F1 metric penalizes both incorrect pairs and missing pairs. On the reported 0–100 scale, direct GPT-5 scores 0.1, the code-environment version without subcalls scores 43.9, depth 1 scores 58.0, and depth 3 scores 76.0. Benefits therefore extend beyond bypassing input limits: interpretation, intermediate storage, and answer construction can be separated into executable steps. [§3.1 and Table 1](https://arxiv.org/html/2512.24601v3#S4)

This does not mean that deeper recursion always improves performance. In the same table, Qwen3-Coder performs better on repository question answering with subcalls disabled than with the recursive configurations. Both the model and the task affect the best choice. OOLONG-Pairs is also a particular constructed pairing task with a limited number of queries. The results demonstrate substantial gains on some tasks requiring dense processing of information, not equivalent improvements across arbitrary complex agent workflows.

### Training added in v3: learning to use the environment is not autonomous self-improvement

The 8B experiment teaches how to inspect variables, write code, and decide when a submodel is useful. The authors generate 2,250 trajectories with Qwen3-Coder on 750 English LongBenchPro tasks, remove zero-score or single-turn attempts, split the retained trajectories into individual turns, and correct some interface-format errors before training Qwen3-8B. This is supervised fine-tuning, or SFT: learning the demonstrated next output given the preceding history. Appendix A reports batch size 64, 300 training steps, and 48 H100 GPU-hours; Figure 3(a) shows improvements across the four task families in the main table. This is neither prompting alone nor learning without external filtering. [§3.2, Figure 3(a), and Appendix A](https://arxiv.org/html/2512.24601v3)

A separate experiment trains Qwen3-4B-Instruct-0527 with reinforcement learning using verifiable rewards: the model makes attempts, and scores from checkable answers guide parameter updates. MRCRv2 requires finding and reproducing specified content within long material. Training uses 32K–64K tokens with two target snippets for 150 steps, with periodic evaluation on 512K–1M tokens with eight target snippets. Figure 3(b) demonstrates length generalization in this setting, not across all long-horizon tasks. Both training studies use author-designed data, rewards, and training procedures rather than a system autonomously improving its own research capabilities. [Figure 3(b) and Appendix A](https://arxiv.org/html/2512.24601v3)

### The practical cost: repeated checking, incorrect answers, and slow runs

Appendix E.2 gives an instructive failure. A pair list has already been constructed in the environment, but the model repeatedly rebuilds and checks its work. It eventually generates an incorrect answer itself instead of returning the stored variable. Appendix B also identifies insufficient coding ability, exhausted output budgets, and incorrect termination markers as failure modes. Preserving the material makes revisiting it possible; it does not ensure correct inspection, computation, or stopping. [Appendices B and E.2](https://arxiv.org/html/2512.24601v3)

Mean cost is also insufficient. The paper reports long tails in both cost and runtime: some requests keep launching subcalls and accumulate much larger expenses. Its model calls are blocking and sequential, so the results do not establish that these quality gains meet low-latency serving requirements. Dollar values in the tables are API charges calculated with the paper’s provider prices, not GPU throughput or current prices. Asynchrony and timeout controls are improvements discussed by the authors, not serving optimizations validated in this study. [§4, §7, and Appendix F.2](https://arxiv.org/html/2512.24601v3)

### What does this suggest for systems work?

A systems implication is that one user request can become a chain: the root writes code, launches subcalls, combines results, and makes another decision. A serving system must consider more than original input length: the number and size of subcalls, dependencies between calls, and how long the program environment must remain alive also matter. Parallel execution is useful only where dependencies allow it. These are research questions inferred from the mechanism, not throughput findings reported by the paper.

A useful experiment would record answer quality, total tokens and API cost, end-to-end time, and failure rate together, then separately constrain recursive depth, input-slice size, and total calls. This would help distinguish better information access from simply spending more resources. That is an experimental suggestion derived from the paper. RLM itself is not a KV-cache compression algorithm, nor does it establish a complete training loop for persistent memory across tasks or continual self-improvement.

### Reading route, version, and attribution

Start with Figure 2 and the two algorithms in §2, tracking where the long input, intermediate results, and final output reside. Next read §3.2 and Table 1 to distinguish root models, submodels, recursive depths, and baseline configurations. Appendices E.2 and E.3 then show, respectively, repeated checking that still fails and semantic interpretation followed by programmatic counting. Finish with Figure 3, Appendix A, and Appendix F.2 to separate training improvements from cost and runtime tails. Understanding Python lists, loops, and a model API call is enough to begin.

## Optional reading · MEM1: Learning to Synergize Memory and Reasoning for Efficient Long-Horizon Agents

**Year / publication：** 2025 · arXiv 2025 · SMART / MIT / NUS / Yonsei University · first preprint 2025-06-18; v2 2025-07-17 · [Original source](<https://arxiv.org/abs/2506.15841v2>)

**Reading guidance：** Worth an optional deep read. Start with the rollout and training paths in Figure 3, then §3.1–3.2 and Appendix A.7. Read Table 1 together with the definitions of EM and peak token usage.

### What to remember depends on what remains to be done

Consider an illustrative example invented for this note. A user asks two questions: which school did Project A's lead attend, and which protocol does Product B use? The first search only identifies the lead as Lin, alongside a long project history. What the next turn needs is: “The lead is Lin; search for Lin's school next; Product B remains unresolved.” Merely recording “found the lead” loses the next search clue, whereas keeping the entire page makes subsequent inputs grow. MEM1 studies how to generate a compact state before each action, combining established facts, missing information, and the next decision. [§1 and §3.1](https://arxiv.org/html/2506.15841v2)

The paper calls this an internal state and encloses it in `IS` tags. “Internal” can be misleading: this is generated text placed back into the prompt, not an additional neural hidden layer or a different storage format for the KV cache. We include this 2025 work as a training-based foundation for understanding how a model learns to preserve useful information, rather than presenting it as a newly released long-context result. [Figure 1 and §3](https://arxiv.org/html/2506.15841v2)

### Rewrite the state, then discard material already consumed

Follow one cycle through the example. The model reads its previous state and new search results, writes an updated `IS`, and then emits a search request or final answer. If the new material identifies Lin's school as Harbor College, the state can retain that answer and switch the remaining task to Product B. After the turn finishes generating, the program removes the preceding turn's state, action, and tool response, retaining the current turn's output; the next tool result is then appended. The fixed task prompt remains, and old and new states temporarily coexist while the next turn is generated. Thus, the retained context contains the recent interaction needed for the next step, not simply one standalone summary at every instant. [§3.1 and Algorithm 1](https://arxiv.org/html/2506.15841v2)

This separates two kinds of change. During task execution, model weights stay fixed and the text state changes. During training, rewards update the weights so the model becomes better at writing states and choosing actions. Once earlier source material leaves the active context, attention cannot read it directly unless the model retrieves it again. This is a trade-off rather than a lossless compression guarantee: continue with a smaller current input while risking a wrong answer or repeated search if necessary evidence was omitted. [§3.1–3.2](https://arxiv.org/html/2506.15841v2)

### The training reward comes from correct answers, not attractive summaries

The authors combine existing QA examples, for instance requiring two answers in one task, so the model must remember one objective while searching for the other. The QA model starts from Qwen2.5-7B Base and is trained with PPO. PPO is a reinforcement learning method that uses rewards from attempted tasks to adjust generation probabilities while limiting individual policy changes. The important supervision here is not a manually labeled sentence to retain at every turn, but one point for each correctly answered subquestion at the end. If the model drops the lead's name and cannot subsequently find the school, earning that point becomes harder. [§3.3, §4.1, and Appendix A.4.1](https://arxiv.org/html/2506.15841v2)

The program enforces context deletion; the model learns to answer under that constraint. QA training does not add summary-quality rewards, brevity rewards, or intermediate rewards. However, mismatched final-answer tags or an incorrect answer count receive zero, so formatting still affects the return. EM means exact match: an answer is matched against a reference under the specified processing rules. In multi-objective tasks, EM counts correctly answered subquestions. The paper separately trains a WebShop shopping model using the environment's reward; results from the two settings should not be presented as one universally capable checkpoint. [§4.1 and Appendix A.4.1 and A.6](https://arxiv.org/html/2506.15841v2)

### A weight update must respect what the model could not see

Training introduces an easily missed problem. To compute losses, the system stitches records from several turns together. If later tokens can attend to that entire concatenated history, they can reread pages that had already been deleted during rollout. Their recomputed probabilities then correspond to different input conditions and do not faithfully represent the conditions under which the actions were chosen. MEM1 uses a two-dimensional attention mask: for each token, it specifies which earlier positions remain visible and blocks material unavailable in that turn. It also masks tool-returned text out of the loss, so retrieved content is not treated as an action selected by the model. [§3.2 and Figure 3](https://arxiv.org/html/2506.15841v2)

This implementation does not strictly eliminate training–inference differences. Appendix A.7 explains that the same state occupies different positions in the turn that generates it and in the next turn that consumes it. Matching visibility alone is insufficient; position IDs must also match. To reduce training cost, the authors do not duplicate each state with two sets of position IDs and instead retain the preceding turn's IDs. The lesson is that training should reproduce the context actually visible during rollout as closely as possible; this method should not be described as numerically identical probability recomputation. [Appendix A.7](https://arxiv.org/html/2506.15841v2)

### Assess long-task gains through answer counts, context size, and timing conditions

QA training uses two-objective compositions, while evaluation extends to 16 objectives. In Table 1, MEM1 correctly answers an average of 1.97 subquestions on the 16-objective tasks, versus 0.567 for Qwen2.5-14B-Instruct. This supplies the abstract's approximately 3.5× improvement, but 1.97 is neither a 197% success rate nor close to completing all 16 objectives. Applying the truncation workflow directly to a 7B instruction model yields 0.396 correct answers, showing that deleting history alone does not reproduce MEM1's result in this comparison. Training histories also differ, so the entire gap cannot be attributed to one isolated memory operation. [Table 1 and Appendix A.4.1](https://arxiv.org/html/2506.15841v2)

For that same 16-objective comparison, MEM1 uses approximately 1,040 peak tokens versus 3,840 for the 14B model, with complete trajectory times of 8.70 versus 29.7 seconds. Peak token usage is counted with the GPT-4o-mini tokenizer and excludes the system prompt; it is a proxy for inference memory, not measured GPU bytes. Timing uses one H200, 10 concurrent threads, and vLLM with automatic prefix caching; training uses four H100 or H200 GPUs. The method also does not win everywhere: on single-objective Wiki-QA in Table 3, MEM1's EM is 0.405, below Search-R1's 0.445. [Tables 1 and 3 and Appendix A.1 and A.4](https://arxiv.org/html/2506.15841v2)

### Read closely: what does the short state preserve, and what does it lose?

Start by manually tracing two turns through Figure 3 and Algorithm 1, then connect context deletion during rollout to history masking during training in §3.2 and Appendix A.7. Finally, inspect Tables 1 and 3 for the accuracy–cost trade-off. The experiments allow at most six turns for smaller tasks and 20 for larger tasks, explicitly informing the agent of its remaining budget. Online search evaluation returns titles, snippets, and URLs without requiring full-page retrieval. These tests establish interaction and memory behavior under finite budgets, not learning across months or reliability over unlimited lengths. The paper also acknowledges that training depends on verifiable rewards; deciding whether retained information suffices for open-ended research remains unresolved. [§4.1, §5, and Appendix A.2](https://arxiv.org/html/2506.15841v2)

A further systems implication is our inference: when an updated state rewrites an earlier prefix, a serving system should reassess which cached computations remain reusable. Continuing the same semantic task does not mean the token prefix is unchanged. That is a possible experimental question, not a general scheduling conclusion established by this paper. This note draws on Zijian Zhou, Ao Qu, and collaborators' [MEM1 v2, dated July 17, 2025](https://arxiv.org/abs/2506.15841v2), released under [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/). It is an explanatory adaptation and commentary; the project, person, and school example is invented and is not an experiment from the paper.

## Optional reading · MemoryWalker: Stop Training Agents on Contexts They Never Saw

**Year / publication：** 2026 · arXiv 2026 · Token Foundry / Alibaba Group · v1 2026-09-01 · [Original source](<https://arxiv.org/abs/2609.00865v1>)

**Reading guidance：** Select Section 3, Figure 2, and Appendix G for context replay, then Section 5 and Table 1. Leave proofs for a second pass.

### A later summary cannot be treated as if it had always existed

Consider our teaching example. An agent reads a long document D and produces judgment A. It then replaces D with a shorter summary S and generates its next step B using S and A. A was produced while D remained visible; B was produced after the replacement. Training should score A under the first context and B under the second. One final chat transcript may not reconstruct both conditions.

MemoryWalker studies this mismatch. Context compression here means deleting messages or replacing text with a summary, not moving KV cache from GPU to host memory. The latter can preserve the computational content; the former changes the model input. Even synchronized weights and identical precision need not produce matching probabilities for different inputs. The paper calls the desired invariant conditioning consistency: score each target token with the prefix actually visible when it was generated. [Section 3](https://arxiv.org/html/2609.00865v1#S3)

### Neither the final transcript nor the full history is sufficient

The first naive approach trains the final compressed transcript. In our example, this scores A using S even though S did not yet exist when A was generated. A later edit is applied backward in time, which the paper calls time-travel leakage. The term need not imply leaking a ground-truth answer. More generally, the token is scored under the wrong historical context; for pure deletion, information originally visible may simply be removed too early.

The second approach restores deleted text such as D and trains an ordinary causal sequence containing the full history. This may score A appropriately, but lets B see D even though D was unavailable at deployment. Recovering the correct condition requires the edit timing, removed or replaced content, and actual model inputs at that time. A tree represents these different prefixes: they share an origin but continue on different branches before and after edits. [Sections 3.2–3.3 and Figure 1](https://arxiv.org/html/2609.00865v1#S3.SS2)

### Exact replay: evaluate branches separately or pack isolated branches

LogitTree evaluates the K+1 paths from K edits separately. A loss mask counts each target only on its generation-time branch, avoiding duplicate shared-prefix losses. This costs multiple forward and backward passes. The 4D alternative packs isolated branches with branch-local position IDs. Gradient equivalence concerns the same batch under dense softmax attention and Proposition 4’s five conditions, including exact visibility, matching positions, and no cross-boundary normalization. [Section 4 and Appendix C.2](https://arxiv.org/html/2609.00865v1#S4)

Appendix G is essential for implementation. The main text describes a physical union with each token appearing once and changing visibility, but the authors state that the training implementation replicates shared tokens per branch, packs the copies behind a block-diagonal attention mask, and restarts positions for each branch. Each hidden state is consequently computed from its own prefix. Actual packed length is the sum of branch lengths and can exceed the deduplicated history considerably. One forward therefore does not eliminate all repeated-prefix work. This describes the paper’s implementation disclosure, not an audit of current code. [Appendix G](https://arxiv.org/html/2609.00865v1#A7)

### SDCC reduces backward work but still pays for teacher forwards

SDCC keeps the final compressed transcript as student input. At mismatched positions, it evaluates the same model on the generation-time live prefix to obtain a teacher distribution without backpropagating through it. The teacher is not a separately trained larger model; it uses the same weights with another input. Training adds KL(teacher || student) to the task loss, encouraging predictions from compressed input to resemble those from original input. KL measures a discrepancy between probability distributions; the direction here follows Equation 10 in the main text. [Section 5.1](https://arxiv.org/html/2609.00865v1#S5.SS1)

The student needs one backward pass, but teacher evaluation may still require multiple gradient-free forwards at edit junctions and reconstruction of old prefixes. The saving concerns backward work, not elimination of history or teacher computation. A black-box harness in these experiments still exposes model requests from which contexts can be recovered; final answers alone are insufficient. SDCC is approximate: its KL bound controls a distributional difference at a corresponding position, not equality of whole-task answers or preservation of all necessary information by a lossy summary. [Section 5.2 and Appendices E–F](https://arxiv.org/html/2609.00865v1#S5.SS2)

### Separate probability agreement from task correctness

The authors use Slime with Megatron training and SGLang generation on 80 GB A100- or H800-class GPUs; the cited setup does not assign an explicit GPU count to each result. The Qwen3-4B main matrix trains on 81,638 composite-QA examples with 16 GRPO samples per prompt and evaluates seven QA benchmarks. With the AgentFold editor, Table 1 reports average exact-match accuracy of 33.2% for naive compressed replay, 37.5% for LogitTree, 34.2% for the 4D mask, and 42.4% for SDCC. These are author-reported results from different training runs, not guaranteed gains from repacking an identical batch. [Sections 6.1–6.2 and Appendix F.1](https://arxiv.org/html/2609.00865v1#S6)

Corresponding mean recorded-token log-probability discrepancies are 0.366, 0.012, 0.022, and 0.071, with a no-compression control around 0.014. Exact conditioning recovery is therefore not zero numerical error, and lower drift does not automatically mean higher answer accuracy. The drift is measured at each run’s maximum-reward iteration; EM is the best full-suite result among development-shortlisted checkpoints, so the columns need not describe one checkpoint. Live web search can change as well. These comparisons lack multi-seed confidence intervals, making small ranking differences uncertain. We use the main-table aggregation without mixing in the appendix’s differently aggregated drift values. [Section 6.1, Table 1, and Appendices F.4–F.6](https://arxiv.org/html/2609.00865v1#A6)

### Reading value: establish what the model actually saw

Start with Figure 1 and Section 3 and write the visible prefixes for A and B in the example. Then read Figure 2 and Appendix G for replay costs, followed by Equation 10 and Table 1. The practical lesson is to preserve enough rollout information to reconstruct each request’s input alongside weight versions and generated tokens. Recursive subcalls, memory summaries, and tool-history trimming all merit such a check. This note does not establish the performance of combining this issue’s methods or claim that every existing framework has the problem.
