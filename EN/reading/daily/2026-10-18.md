# How agents improve: rewriting code, learning from demonstrations, and checking gains

Three 2026 studies turn self-improvement into operations we can trace. The main reading, AIDE², has one research agent rewrite another agent's control program: which changes survive, and do they help on new tasks? SDFT explains how information in demonstrations can enter model weights. REUSE asks why repeatedly selecting versions on one benchmark can mistake lucky gains for progress. Each note starts with a concrete example, then develops the mechanism, evidence, and limitations. Read the main paper closely; explore the two optional papers as interest dictates.

Each digest recommends 1 main paper and 2–4 optional papers across LLM inference, RL infrastructure, post-training, RSI (recursive self-improvement), reasoning compute, agent learning and memory, data and evaluation, and model architecture. Explore foundations and current research by theme; a direct connection to current work is not required. A recommendation does not mean it has been read, and there is no need to finish everything in one day.

## Main reading · Recursive self-improvement of AI research agents

**Year / publication：** 2026 · arXiv 2026 · v1 2026-09-22 · [Original source](<https://arxiv.org/abs/2609.26457>)

**Reading guidance：** Today's main read; allow 35–50 minutes. First distinguish the inner loop editing task code from the outer loop editing agent code, then study search and memory. Finish with independent evaluations and the ignition test rather than stopping at the rising curve.

### First improve a training script, then improve the way experiments are run

Suppose we give an agent an image-classification training script and ask it to improve accuracy within a limited budget. It can change the learning rate, train, inspect validation results, and decide whether to retain the change or try something else. What changes initially is the code solving a particular task. **This classification task is a teaching example used throughout this note, not a specific experiment disclosed in the paper.**

Now move up a level. Why does the agent keep making small changes to one approach? Why does it put every old log into every prompt? Could editing the program that chooses experiments, stores history, and checks results make it more effective on different future tasks? The paper calls this organizing code around the model the harness; this note also calls it agent control code.

AIDE² comes from Weco AI. The team published its initial blog on July 14, 2026 and paper v1 on September 22. This note follows the paper, a 2026 preprint. It studies persistent changes to the research tool itself, rather than treating a single rewritten answer as evidence of self-improvement. [Paper](https://arxiv.org/abs/2609.26457); [early team account](https://www.weco.ai/blog/first-evidence-of-recursive-self-improvement)

### What the two loops edit, and what stays fixed

The inner loop receives a concrete task and repeatedly edits task code. In the classification example, it produces training scripts, executes them, records scores and errors, and submits one when its budget expires. The outer loop receives the research agent's code and edits how it selects experiments, organizes inputs, and handles feedback. Evaluating one outer-loop change requires the modified agent to carry out a suite of inner-loop tasks.

The main experiment uses the human-engineered AIDE_human as its outer-loop proposer throughout. An accepted rewrite replaces the inner-loop agent that the next round will edit. The foundation model used in each loop also stays fixed: Claude Opus 4.7 outside and Gemini 3 Flash for inner-loop evaluations. Their language-model weights are not trained here. [Paper §2.1–2.2 and Figure 1](https://arxiv.org/html/2609.26457v1)

Continuously improving one research program therefore differs from replacing the proposer with a stronger one in every generation. The main experiment does the former; the latter requires another test. Fixed language-model weights do not prohibit the inner task from training a classifier. The restriction concerns the model driving the agent, not the research work it executes.

### Three levels of feedback guard against different mistakes

Return to classification. The agent repeatedly sees a public validation score and uses it to choose its next experiment. Enough attempts may nevertheless find a script tailored to that validation data. The submitted solution is therefore scored on private data the inner agent cannot see. The outer loop aggregates private scores across tasks to decide whether to retain the agent rewrite. [Paper §2.1](https://arxiv.org/html/2609.26457v1)

Private here means hidden from the inner solver. Because the outer loop repeatedly uses the aggregate to choose versions, that score still participates in development and cannot establish final generalization. A third level is needed: freeze selected agents and evaluate them on new tasks that never affected version selection. This distinguishes doing better on the selection tasks from a transferable research method.

**Our interpretation of the three levels is:** public feedback asks how to change the next task solution; the private grade asks whether to keep this agent version; independent external evaluation asks whether the retained changes help on new tasks. All three may be called evaluation, but their roles differ. Data hidden from one level is not necessarily unused test data for the whole system.

### Search: avoid betting the entire budget on the current leader

The initial agent tends to keep improving its highest-scoring candidate. In the teaching example, if learning-rate tuning narrowly beats a preprocessing change, most subsequent attempts might go to the former. But preprocessing might only need further refinement; always chasing the current leader can abandon another promising direction too early. Starting a wholly new approach every time would instead discard accumulated progress.

The final agent, AIDE85, groups drafting strategies into five categories, selects a strategy, then expands the best candidate carrying that strategy. Strategy selection uses a multi-armed bandit: allocate another attempt using both previous returns and how insufficiently explored an option remains. The paper specifically uses UCB1 mixed with another score-based sampling choice, and periodically continues the best solution under a different strategy. [Paper §3.5 and Figure 5](https://arxiv.org/html/2609.26457v1)

This need not invent an entirely new research direction. It changes how experimental effort is distributed: useful existing code can survive while the angle of the next attempt changes. **Our classification analogy is:** retain the best training script, but let a different optimization approach continue from it.

### Memory: retain records that can change the next decision

After 30 experiments, sending all 30 scripts and every log makes the input progressively longer. A call intended only to fix an import error still processes many irrelevant successful runs. Deleting all history is also inadequate because the agent may repeat failed attempts. The issue is choosing information, not assuming that a longer input necessarily provides better memory.

AIDE85 switches to shorter, role-specific inputs. Drafting and improvement read summaries of the root solution and recent candidates; recurring error records are added when bugs become frequent. Unlike the starting version, it no longer continually concatenates the complete history. This change lives in the control program and persists across subsequent tasks. [Paper §3.5 and Figure 6](https://arxiv.org/html/2609.26457v1)

**A practical implication of this mechanism is:** when calls and execution are cost-constrained, removing irrelevant input can leave budget for more useful attempts. But shorter inputs do not guarantee better results; dropping an important counterexample can worsen decisions. The whole research task must still be evaluated. A compression ratio is not automatically the same multiplier in research speed.

### How many improvements actually lie inside the eight-day curve

The main run lasts eight days and contains 100 nodes: the initial agent plus 99 rewrite proposals. Seven replace the incumbent, taking the aggregate private grade from 0.703 to 0.778. Two further complete runs accept two and four rewrites. This is evidence of repeatedly finding useful changes, not of every attempt succeeding. [Paper §3.2 and Figure 2](https://arxiv.org/html/2609.26457v1)

The values 0.703 and 0.778 are aggregate selection grades, not a statement that general research ability rises from 70.3% to 77.8%. An incumbent curve retains the best version so far and therefore does not fall when worse candidates are rejected. The relevant questions are how many candidates were attempted, whether acceptance was reliable, and how those versions perform independently.

Humans still define the starting system, task collection, per-task budgets, and acceptance rule; the loop automates proposals, execution, and comparison during the run. The team reports no human intervention inside that loop, which is different from no human design. Comparing eight days with the team's preceding two years of development provides context, but does not establish a matched-condition multiplier for replacing researchers. [Team account](https://www.weco.ai/blog/first-evidence-of-recursive-self-improvement)

### Do the improvements survive a different set of research tasks?

The authors compare the initial, intermediate, final, and human-engineered agents on ALE-Bench, MLE-Bench, FML-Bench, and a weather task based on WeatherBench 2, none used for selection. The first three cover algorithm or ML engineering, while weather tests optimization of a physics-based forecasting program absent from the selection families. Within each benchmark, all agents follow the same protocol. [Paper §3.3 and Appendix A](https://arxiv.org/html/2609.26457v1)

For a concrete ML-engineering comparison, MLE-Bench lite contains 22 competitions with three seeds per task. All agents use Gemini 3 Flash with a primary budget of $5 per run; solution scripts execute in CPU containers with 4–24 vCPUs and 16–192 GB RAM. Mean private percentile rises from 0.678±0.006 for AIDE0 to 0.722±0.011 for AIDE85, versus 0.708±0.007 for the human-engineered agent. The ± denotes one standard error. This relative-ranking metric is not classification accuracy. [Appendix A, Tables 1–2](https://arxiv.org/html/2609.26457v1).

The final version matches or exceeds the human-engineered agent in all four aggregate means; this does not establish significant superiority on all four. Improvement is not monotonic: intermediate AIDE47 beats AIDE85 on MLE-Bench and weather. The weather evaluation contains only one optimization task and three seeds. It demonstrates one transfer across task types, not validation across scientific research generally.

Budget definitions also matter. Some external experiments primarily constrain cost and others search steps, so the entire collection cannot be described as using identical GPU time. The weather number measures improvement relative to its starting forecasting program, not an absolute WeatherBench leaderboard score. **These distinctions determine how far the measured benefit can be extrapolated.** [Appendix A and Tables 1–2](https://arxiv.org/html/2609.26457v1)

### Which appealing code mechanisms lack evidence of effectiveness?

The paper also checks whether fast isolated GPU kernels remain effective inside actual training loops. The experiment covers 38 kernel/context pairs with three seeds each, spanning GPT-2, ViT, and CNN training. Agents use Gemini 3 Flash with at most 20 search steps, and kernels run on NVIDIA A100 GPUs. After averaging speedups across seeds for each pair, the authors count reward hacking when isolated speedup exceeds 1.02× but less than half the reported speedup survives in training, or the kernel crashes there. The rate falls from 55% for AIDE0 to 32% for AIDE85, versus 39% for the human-engineered agent. The denominator is 38 pairs, not 114 runs, and equal step budgets do not imply equal cost or runtime. This measures a disconnect between a proxy and actual outcomes, not an intention to cheat. [§3.4, Appendix A](https://arxiv.org/html/2609.26457v1).

The generated code includes a rule penalizing unusually high-scoring candidates, apparently intended to avoid lucky winners. Inspection shows that it preserves the existing ranking and never changes the selected candidate when evaluations are replayed. The overall improvement therefore cannot be credited to that rule. A mechanism appearing in code does not establish that it performs its intended role.

Another change repairs an evaluation-script defect: one failing test previously brought down the entire private evaluation. Repairing scoring code differs from improving search policy. The paper does not independently ablate every change sufficiently to assign its contribution; whole-version comparisons are stronger evidence than individual mechanistic attributions. [Paper §3.5](https://arxiv.org/html/2609.26457v1)

### The next recursive question: does it become a better proposer?

Even if a new agent is better at modifying classification scripts, it need not be better at modifying agents. Both involve writing code, but require different judgments. For improvement to accelerate, a new version taking over the proposer role must produce better successors than the old proposer could under comparable resources.

The paper tests this with an ignition experiment: AIDE47 and AIDE_human separately drive the outer loop, both starting from the same inner AIDE47. Each arm has three seeds and runs for 50 steps. Their average endpoints are similar. The authors explicitly regard the evidence as inconclusive: it does not establish that the evolved version drives further self-improvement better or more efficiently. [Paper §3.6 and Figure 7](https://arxiv.org/html/2609.26457v1)

The strong evidence here is therefore repeated program optimization and external transfer; continuously improving the ability to improve remains unproven. One finite experiment also cannot establish open-ended evolution without additional human design, unlimited capability growth, or an intelligence explosion. Isolating this stronger test is one reason the paper deserves a close read.

### A reading route and questions to bring back to an agent system

**The inspection sequence we infer from these experiments is:** identify where an improvement is stored and whether the next run will reuse it; determine who supplies feedback and which program can see it; then check whether evaluation tasks participated in choosing versions. This distinguishes revision of one answer, reusable program improvement, and improvement of the proposer itself.

Maintenance remains another unresolved issue. Complex generated code may score better while leaving it difficult to tell which branches matter and which are residue. A research aggregate does not perform compatibility, error-recovery, and interpretability checks for deployment. The paper also identifies these as practical obstacles. [Paper §5](https://arxiv.org/html/2609.26457v1)

Read by question: Figure 1 for the two loops; §2 for feedback and budgets; Figures 5–6 for search and memory; Figure 2 for repeated gains; Figure 3 and Appendix A for independent tasks; and finally Figure 7 for the stronger recursive claim. The early blog and paper differ in several numbers and evaluation scope, so use the v1 paper consistently when citing results.

## Optional reading · Self-Distillation Enables Continual Learning

**Year / publication：** 2026 · ICML 2026 · preprint January 2026 / v2 August 2026 · MIT, ETH Zürich · [Original source](<https://proceedings.mlr.press/v306/shenfeld26a.html>)

**Reading guidance：** Optional and worth reading: §3 / Fig. 2, §4.3 / Fig. 3, and Table 5, followed by the teacher-stability study in Appendix A.3. Allow 30–40 minutes. Understand what each role can see before working through the KL equations.

### Can improvement from seeing a demonstration survive after it is removed?

**Explanatory example, not a paper benchmark item:** give a model a weather-tool specification and ask for Shanghai's temperature. It might choose the right tool but supply the wrong arguments. Showing the correct call for this training question can help it understand the required response. Can that improvement survive when the demonstration is removed?

SDFT assigns two roles to the model: the student sees the question, while the teacher additionally sees a demonstration. Training makes the student learn from the teacher by changing the numerical parameters governing generation—its model weights. Future responses can then use the trained model without repeatedly inserting the original demonstration. The self-teacher still receives external information.

The paper is by Idan Shenfeld, Mehul Damani, Jonas Hübotter, and Pulkit Agrawal, from MIT and ETH Zürich, and appeared at ICML 2026. The first preprint was posted in January 2026. The mechanism and experimental details below follow arXiv v2, dated August 7. [Official proceedings](https://proceedings.mlr.press/v306/shenfeld26a.html); [v2 paper](https://arxiv.org/abs/2601.19897v2).

### The student writes first; the teacher guides along that trajectory

Ordinary supervised fine-tuning, or SFT, trains a model to imitate demonstration answers from a dataset. SDFT instead first lets the current student generate one response from the question alone. This follows the student's own habits and may differ from the expert demonstration. Training on behavior generated by the current model is called on-policy learning.

The teacher then reads the question, demonstration, and the prefix already generated by the student, and computes probabilities for the next token. Tokens are the basic units of text processed by the model. The student also predicts probabilities at the same prefix, and training brings the predictions closer. Learning from another model's predictions is called distillation. The signal is richer than one final correctness score, and the student's response is not simply replaced by the demonstration.

In the weather example, the teacher knows what a correct call should look like, while the student practices producing an answer from the question. At test time, the trained student receives the question and ordinary task inputs without the teacher's privileged demonstration. Figure 6 also compares this approach with generating teacher answers in advance and then training the student, testing whether teacher quality alone explains the improvement. [§3, §4.6, Figs. 2 and 6](https://arxiv.org/html/2601.19897v2).

### How does the teacher improve without following every fluctuation?

Teacher and student start from the same model, but they should not be treated as identical throughout training. By default, v2 retains most of the teacher's previous weights and gradually mixes in the student's new weights. This exponential moving average, or EMA, lets the teacher track progress without immediately following every update.

Appendix A.3 compares three teachers. A frozen base model is stable but weaker; using the current student directly can be unstable; EMA provides a better balance in the experiment. This does not introduce a stronger external teacher for free, nor does it guarantee that every teacher judgment is correct.

KL divergence measures differences between probability distributions, and its direction matters. **The theoretical derivation in §3 uses reverse KL, whereas the practical implementation discussion reports the best results with forward KL.** The former's theoretical interpretation cannot simply be treated as a complete guarantee for the latter. On a first reading, retain the execution order: student-generated practice followed by token-level probability guidance. The objective direction and estimator deserve separate attention when reproducing the method. [§3, Appendices A.1 and A.3](https://arxiv.org/html/2601.19897v2).

### Where does the training information come from?

The main experiments use Qwen2.5-7B-Instruct and fine-tune all model parameters; the appendix specifies a single NVIDIA H200 for training. Skills include scientific questions, tool calling, and medical questions. Science demonstrations are produced by asking GPT-4o up to eight times per training question and retaining a response with the correct final answer. Tool demonstrations come from ToolAlpaca. The medical experiment uses approximately 20,000 English training questions and 1,000 separately sampled verifiable evaluation questions.

Data preparation and model selection are externally organized. Researchers define training, validation, and test sets, search settings such as learning rates, and select checkpoints by validation performance. Medical evaluation uses GPT-5-mini. Training does not require a separately engineered reward function, but demonstrations, known answers, and evaluation procedures still provide external assistance. No explicit reward does not mean no supervision.

A separate knowledge experiment assembles approximately 200,000 tokens of articles about 2025 natural disasters after the model's knowledge cutoff. GPT-5 generates question–answer pairs, and humans check for duplicate questions. The teacher sees both the article and a worked answer, while the student lacks those additional materials. The experiment does not involve the model independently discovering news, establishing its truth, and deciding what to learn. [§4.1, Appendices A.2 and B](https://arxiv.org/html/2601.19897v2).

### After learning a new task, does the model retain its old abilities?

Consider the single-task ToolAlpaca comparison in Table 5. Qwen2.5-7B scores 42.9% before adaptation, 63.2% after ordinary SFT, and 70.6% after SDFT. Average scores across six prior-capability benchmarks are 65.5, 56.0, and 65.4, respectively. This supports stronger new-task performance with less average degradation. It does not establish that every prior ability is perfectly preserved.

Figure 3 more directly tests sequential learning: one model learns the three skills in succession, while earlier skills continue to be evaluated. SDFT retains earlier learning better than sequential SFT. This remains a finite three-task sequence, not months of continuous adaptation to real users. Its vertical axis is also normalized separately using each task's base and maximum scores; it is not a percentage-accuracy axis.

Accuracy uses greedy generation, choosing the highest-probability token at each step. The appendix reports three random seeds unless otherwise specified. The authors also measure pass@k—the chance that at least one of k attempts succeeds—up to k = 128, where gains persist. This adds evidence but does not replace evaluation over more tasks, task orders, and time horizons. [§4.2–4.3, Figs. 3 and 5, Appendix B.2, Table 5](https://arxiv.org/html/2601.19897v2).

### What are the gains and costs of storing new facts in weights?

On the disaster-knowledge experiment, strict accuracy requiring all answer details to be correct is 80% for SFT and 89% for SDFT. For indirect questions that require the new knowledge without explicitly naming the original event, the scores are 80% and 98%. These results concern a narrowly constructed knowledge task with automated evaluation, not all possible factual updates. An ideal retrieval baseline that always supplies the correct article still scores 91% and 100%, respectively.

The model must first be capable of using a demonstration. In the science-task scaling study, the 3B model underperforms ordinary SFT when trained with SDFT. The authors also observe that students can inherit phrases such as references to an accompanying text even when no such text was supplied to them. Useful knowledge and inappropriate wording can be learned together. [§4.2, §4.4, §5](https://arxiv.org/html/2601.19897v2).

Compared with ordinary SFT, this training adds student generation and teacher probability computation before updating student weights. One generated response per question does not make it as cheap as one inference call. Costs depend on generated length, training epochs, and implementation, so these stages should be measured separately. The paper does not fully specify the matched conditions behind its overall cost ratios; this note therefore does not use them as a general budgeting rule. [§5, Appendix B.1](https://arxiv.org/html/2601.19897v2).

### What kind of improvement does this establish?

The persistent change is in model weights, while the learning algorithm, tasks, and demonstration sources remain externally specified. The paper does not show a model autonomously rewriting its learning method and repeatedly improving its ability to improve itself. Self-distillation therefore does not by itself establish recursive self-improvement. The authors acknowledge remaining forgetting and leave noisy demonstrations and user conversations as future directions.

**The following systems connection is our analysis:** an implementation should separately measure student generation, teacher scoring, and parameter updates, while ensuring that teacher and student compare probabilities on the same generated prefix. Removing demonstrations from deployment inputs is purchased through earlier training. Whether that trade is worthwhile requires comparison with retrieval or supplying demonstrations in context.

Read Fig. 2 first and identify the information available only to the teacher. Then use Fig. 3 and Table 5 to separate new-task gains from retention. Finish with Appendix A.3 and §5 for stability, cost, and failure cases. Only then return to the KL derivation in §3, keeping improvement from supplied demonstrations distinct from unconditional, ongoing self-evolution.

## Optional reading · Which Self-Improvements Should We Trust? Reliable Self-Improvement When Agents Reuse Their Benchmarks

**Year / publication：** 2026 · arXiv 2026 · v2 2026-09-29 · [Original source](<https://arxiv.org/abs/2609.33180v2>)

**Reading guidance：** Worth an optional close read; allow 20–30 minutes. Start with the exam example, then read the assumptions in Section 2.1, Algorithm 1, and Table 1, followed by Appendix B's screening details and ablations.

### How an unseen exam can still steer search in the wrong direction

**This is a teaching example, not a result from the paper.** An agent revises a classifier, submits eight versions at a time, and receives only accuracy from an evaluation service. A deeper decision tree scores highest on the first round, so the agent explores depth next. The questions remain on the server, but their scores already guide the search. After many rounds, the program may fit these particular questions increasingly well without improving equally on new examples.

No direct access to answers is necessary. Keeping a high-scoring version and choosing the next experiment from its score already uses evaluation information. This gradual fitting to a repeatedly consulted set is adaptive overfitting, the problem REUSE studies. The authors are at Purdue University. The preprint first appeared on September 27, 2026; this note uses v2 dated September 29 and presents it as a preprint. [Version and authors](https://arxiv.org/abs/2609.33180v2)

### Choosing among eight versions differs from adapting over many rounds

Within one round, the best of eight versions might simply be unusually lucky on this sample. Repeated comparisons also increase the chance of making at least one mistake. If candidates were fixed beforehand, one could allocate smaller error allowances to these comparisons. But an agent uses previous feedback to propose later versions, making those candidates dependent on the evaluation set. Tightening a threshold only by the total number of comparisons does not automatically address that dependence.

REUSE lets the proposer freely use separate development data, while the evaluation service returns only that all candidates were rejected or the index of the accepted candidate. It withholds raw scores, per-example outcomes, and its internal improvement certificate. Acceptance decisions still carry information, so the method must also account for the possible decision histories. Hiding the score alone is insufficient. [Sections 1–2](https://arxiv.org/html/2609.33180v2)

### How acceptance works, and what the guarantee actually covers

For pass/fail evaluation, the service compares the old and new systems on the same questions. How many former errors does the new version fix, and how many formerly correct answers does it break? Questions both versions pass or both fail provide no win–loss evidence. A paired test assesses whether sampling variation can explain the apparent advantage. The acceptance threshold also accounts for the number of candidates, earlier promotions, and possible histories.

The theoretical conditions are strict. Evaluation examples must be independent draws from one target distribution: i.i.d. The set must initially be independent of development data, the starting system, and the proposer's randomness. Subsequently it may influence search only through the prescribed decisions. With an error budget α of 0.05 for the entire process, the result is that, under these conditions, with probability at least 95%, every accepted change improves average performance on that distribution. This is a joint guarantee over evaluation-set sampling for the whole process, not a 95% posterior confidence for an already observed update. It is not a separate 95% assurance for each update, and it does not mean regression is impossible.

Prior contamination, additional feedback through logs, or a changed deployment distribution cannot simply inherit this guarantee. Later stages generally require stronger evidence, so genuine small improvements may be rejected. The method controls false acceptance; it does not promise to keep finding progress. [Section 2.1, Theorem 1, Proposition 1](https://arxiv.org/html/2609.33180v2)

### The experiment changes classifier settings, not a complete research agent

The experiment uses Covertype to predict whether an example belongs to forest cover type 2. Qwen2.5-7B-Instruct proposes scikit-learn configurations through vLLM on one A100 40GB, restricted to gradient boosting and logistic regression. Each candidate changes at most two fields, such as learning rate, feature subset, or preprocessing. A search lasts 200 rounds with up to eight valid candidates per round, and each of two evaluation-set sizes is tested over 30 seeds. [Section 3.1, Appendices B.1–B.2](https://arxiv.org/html/2609.33180v2)

The authors separate 50,000 training examples, 20,000 development examples, a 60,000-example evaluation pool, and a 50,000-example final holdout. A run draws 2,000 or 10,000 examples from the pool and reuses them for acceptance decisions. No search method accesses the final holdout H, which separately checks changes. Humans define the task, configuration space, prompts, and validation rules in advance; the paper describes no human selection at each round. This remains constrained automated search, not 200 autonomous leaps in agent capability. The proposing language model is not trained during search; classifier configurations change, and each classifier is fitted on the training split.

### Accepting fewer changes can still reach a similar final score

In Table 1's 2,000-example evaluation condition, REUSE accepts an average of 3.2 changes per search, with no observed false promotions across 30 searches. Its final improvement over the initial classifier on H is 7.02±0.26 percentage points. Selecting the candidate with the largest positive evaluation gain accepts 13.0 changes per search, produces 75 false promotions in total, and finishes at an improvement of 7.04±0.08 points. The ± values are standard errors. A false promotion is a change with non-positive improvement on H. [Table 1](https://arxiv.org/html/2609.33180v2)

Similar final scores therefore need not imply equally reliable intermediate updates. The more conservative Bonferroni-style baseline also records zero false promotions, but its final improvement in this condition is only 2.35±0.37 points. REUSE is not the only method with zero observed errors, and the paper's SICA-style and DGM-style configuration searches are not full reproductions of those original systems. The 50,000-example H is still finite, so experimental 'true improvement' is an estimate. This evidence also does not establish independent replication by an outside team.

### The final statistical test cannot receive all the credit

The appendix also discloses development-draft updates and submission screening specific to REUSE, along with removal of previously evaluated duplicate configurations. Other methods receive different information and do not use exactly the same search process. The main table consequently compares combined pipelines. Development-search rounds should also not be equated directly with formal queries to the evaluation set. [Appendix B, Tables 2–3 and 6](https://arxiv.org/html/2609.33180v2)

A test-removal experiment gives more direct evidence. The authors shrink development data to 500 examples and relax screening over ten fresh seeds, making mistaken selection easier. With the evaluation test retained, nine candidates with non-positive improvement on H are rejected, and none of 47 accepted changes is false. Without the test, six false promotions occur in five of the ten runs. Final performance does not differ significantly. This supports the test's role in update reliability, but does not establish the same effect for open-ended code changes or long-horizon agents. [Appendix B.4.1, Figure 4](https://arxiv.org/html/2609.33180v2)

### Questions to carry into today's main reading

**The following are reading and engineering suggestions.** For a system that revises programs, writes memory, or changes a training pipeline, first trace evaluation feedback: who sees scores, who uses them to propose the next version, and whether final audit data returns to debugging. Development data may guide repeated exploration. But keeping another set's questions out of the agent's visible context does not make repeated queries to that set independent validation. For example, AIDE² exposes selection grades to its outer loop. It does not directly satisfy REUSE's decision-only feedback restriction, so this guarantee cannot be applied retroactively to the main paper.

Read the assumptions in Section 2.1, Algorithm 1, and Table 1 first, then Appendix B's information table and ablation; leave the statistical derivations until implementation requires them. Paired with AIDE², the value is connecting the ability to propose useful changes with a credible process for deciding which changes to retain. REUSE supplies a conditional evaluation framework; it has not empirically established sustained self-improvement in general research agents. [Full v2](https://arxiv.org/html/2609.33180v2)
