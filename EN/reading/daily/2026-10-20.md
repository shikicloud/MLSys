# Making training and rollout agree: from VeXact to gradient correction

Why can generation and training assign different probabilities to the same input under the same weights? Today's main reading is VeXact: a diagnostic reference for RL that aligns model implementations, operators, and reduction order to remove numerical mismatch. The optional readings explain how batch composition changes numerical results and how Score Centering corrects gradients while the distributions still differ. We distinguish numerical agreement at matched weights, off-policy data from stale weights, and zero expected gradient drift. Start with the worked example and implementation path; the algorithmic derivations can wait for a second pass.

## Main reading · Diagnosing Training-Inference Mismatch in LLM Reinforcement Learning via a Zero-Mismatch Reference

**Year / publication：** 2026 · arXiv 2026 · v1 2026-05-14 / v2 2026-09-29 · ByteDance & University of Virginia · [Original source](<https://arxiv.org/abs/2605.14220v2>)

**Reading guidance：** Worth a close read. Start with rescoring an identical prefix, then read §3.1 and the pinned source paths. Follow with Table 2, the training curves, and the probability denominators in §4. This note uses the September 29, 2026 v2 paper and separately identifies the current code commit inspected.

### Fix one problem first: why can two systems assign different probabilities to the same token?

Suppose a model is solving a mathematics problem and has already produced a particular reasoning prefix. The generation system samples token A next and records its probability. During training, we feed that already generated answer into the trainer and ask it to score A again. We are not asking it to sample another answer: we hold every preceding token fixed and compare the probability of A after that prefix. A and all probability values below are teaching examples.

Feeding a known token sequence back into a model to score its positions is called teacher forcing. Training usually processes the sequence together, whereas generation uses a cache step by step, but the causal mask should give A access to the same preceding context. If the weights and inputs are identical yet generation returns 0.400 and training returns 0.404, the difference cannot be explained by the model having learned something new.

Training often stores the natural logarithm of a probability, called its log-probability or log-prob. The underlying comparison is still between the same conditional probabilities. VeXact studies this training–inference mismatch, or TIM. Its objective is agreement between the two floating-point results, not agreement with infinite-precision real arithmetic. [Paper v2](https://arxiv.org/html/2605.14220v2)

### First align the model implementation and its operators

Weights are inputs to a computation. Two programs can read identical weights while using different normalization implementations, different intermediate precision, or a kernel that combines several operations. A kernel is a low-level program executing a piece of computation on the GPU. Changing where intermediate values are rounded can change the final probability; copying a weight file does not automatically align these execution paths.

VeXact's training-side entry point first enables its operator replacements and then registers model patches. Both levels matter: a model layer needs the intended implementation, and operations such as matrix multiplication inside it need the intended implementation too. This is not merely a correction applied to two probability tables after training. [Training entry point](https://github.com/verl-project/vexact/blob/6c170209f334f2cd59147436ef22740878e49437/vexact/integrations/verl/fsdp_enable_invariant.py#L17-L29)

Two versions must remain distinct. The paper describes its FSDP2 experimental system; FSDP is a way to shard model states across GPUs for training. The code was separately checked on October 20, 2026, at commit `6c170209f334f2cd59147436ef22740878e49437`, whose current integration centers on VeOmni FSDP. Its model registration explicitly connects VeOmni's MoE implementation. This code should not simply be described as the paper's complete original experimental environment. [Model registration](https://github.com/verl-project/vexact/blob/6c170209f334f2cd59147436ef22740878e49437/vexact/models/register.py#L29-L72)

### Why must even the order of additions in matrix multiplication be fixed?

Consider a deliberately exaggerated floating-point teaching example. In float32, `(1e20 + (-1e20)) + 3` can produce 3. With `1e20 + ((-1e20) + 3)`, the small value 3 is lost to intermediate rounding and the result becomes 0. This is not the magnitude of the paper's measured errors. It illustrates why finite-precision addition does not allow arbitrary rearrangement of parentheses.

Matrix multiplication adds many products together; combining these terms is a reduction. A GPU can compute different tiles first and then combine partial sums. A library may choose different tiling for one request and for a larger batch. Repeating an identical batch may therefore be deterministic while changing its neighboring requests still changes the result. Repeatability and independence from batch composition are separate requirements.

VeXact fixes computation arrangements for paths such as matrix multiplication and replaces operators including `mm`, `addmm`, `log_softmax`, and dimension-wise means. Its entry point also restricts reduced-precision reductions and enables PyTorch determinism settings. The constraints on the concrete paths work together; a single determinism switch is not the complete solution. Nor do these constraints imply automatic agreement across GPU architectures. [Operator registration and settings](https://github.com/verl-project/vexact/blob/6c170209f334f2cd59147436ef22740878e49437/vexact/batch_invariant_ops/batch_invariant_ops.py#L741-L759)

### Attention: keep the KV cache while fixing how history partitions are combined

Next consider how A reads the preceding reasoning. Attention uses earlier tokens' keys and values. Retaining them to avoid recomputing history for every new token creates the KV cache. For a long history, an implementation can distribute that history over several computation blocks, calculate partial results, and combine them. The number of partitions and their combination can affect floating-point rounding.

Both current VeXact FlashAttention call paths explicitly pass `num_splits=1`, fixing this part of the computation. They still pass a `page_table` for paged caching. The restriction concerns this KV-splitting and merging path; it does not remove the KV cache or prohibit paged storage. [Both attention paths](https://github.com/verl-project/vexact/blob/6c170209f334f2cd59147436ef22740878e49437/vexact/batch_invariant_ops/flash_attention.py#L172-L206)

Returning to the example, generation may process one new token with a populated cache while training processes the answer sequence together. A valid comparison must align the effective prefix, position indices, and masks as well as the weights. Fixing a reduction addresses computation order. It does not repair a comparison in which the programs were given different contexts. This verification requirement is a deduction from the mechanism.

### MoE: choosing the right experts is not enough

MoE means mixture of experts. A layer contains several different subnetworks; a router selects a small number for each token, and their outputs are combined using routing weights. When the serving batch changes, the number of tokens assigned to a particular expert can change too. Its matrix multiplication may consequently use a different computation arrangement.

Checking that training and generation selected the same experts is therefore insufficient. The current Qwen3 MoE path directly calls VeOmni's `fused_moe_forward`. A source comment explains that the purpose is identical expert arithmetic on rollout and training sides. The important detail is sharing the implementation that actually executes expert computation, not merely sharing a model name or routing decisions. [Actual Qwen3 MoE call](https://github.com/verl-project/vexact/blob/6c170209f334f2cd59147436ef22740878e49437/vexact/models/qwen3_moe/modeling_qwen3_moe.py#L69-L100)

This also explains why coverage must be stated per model. The current README excludes MoE support on the legacy FSDP path and does not offer a blanket guarantee for different paths such as linear attention. Aligning one MoE architecture does not establish alignment for every hybrid architecture. A model change requires checking which patches its execution actually reaches. [Pinned README](https://github.com/verl-project/vexact/blob/6c170209f334f2cd59147436ef22740878e49437/README.md)

### The final gate: identical hidden states do not yet establish identical log-probs

At the output, a model first computes a score for every vocabulary token, called a logit. Softmax converts those scores into probabilities summing to one. A's probability therefore depends on the vocabulary-wide normalization, not just on A's own score. If one path promotes intermediate scores to float32 and another retains bfloat16, this final stage can still differ even after earlier layers agree.

The current inferencer handles this choice explicitly. Its source explains that the training-side fused linear and cross-entropy path promotes logits, whereas another path may retain lower precision; a configuration controls the choice. This is a reason to inspect the active branch rather than stop at the model's main layers. [Inferencer precision explanation](https://github.com/verl-project/vexact/blob/6c170209f334f2cd59147436ef22740878e49437/vexact/inferencer/inferencer.py#L78-L85)

"The tests pass" also requires reading the assertion. One repository FA4 batch-invariance test uses `diff < 1e-5`, and the log-prob verification script accepts configurable tolerances. These are useful checks, but agreement within a tolerance is not bitwise identity. Read the paper's strict claim separately from what each particular test establishes. [FA4 test](https://github.com/verl-project/vexact/blob/6c170209f334f2cd59147436ef22740878e49437/tests/batch_invariant_ops/test_flash_attention_4_batch_invariance.py#L120-L135) · [Configurable verification script](https://github.com/verl-project/vexact/blob/6c170209f334f2cd59147436ef22740878e49437/tests/scripts/verify_logits_vs_native_hf.py#L913-L1033)

### Zero mismatch does not mean every rollout comes from the current policy

Now add time to the example. Generation produces the answer using weight version θ₀, after which the trainer updates to θ₁. Rescoring A with θ₁ can legitimately produce a different probability. That difference reflects an actual parameter change. It is distinct from two programs producing different probabilities when both use θ₀.

An asynchronous rollout can return after the learner has advanced, and a training system can reuse the same answers for several updates. Both can leave the data associated with an older policy, commonly called policy staleness. Even if VeXact perfectly aligns the two numerical paths at every fixed weight version, data generated by θ₀ does not become data generated by θ₁.

A system integration should therefore record weight versions and numerical discrepancies separately. One answers whether the policy is the same; the other asks whether two programs evaluate that same policy differently. Compared with this edition's optional Score Centering reading, VeXact changes numerical execution: zero expected drift in an estimator does not establish equality between these probability tables.

### What the experiment does: remove one confounder, then examine training

Reinforcement learning uses answer rewards to raise token probabilities for relatively better answers and lower them for worse ones. REINFORCE is a family of methods that directly builds such updates from rewards. The paper studies numerical mismatch with one update per rollout batch, reducing entanglement with repeated PPO updates. This remains a particular training setup.

In Table 2, dense REINFORCE uses 16 H100s and dense GRPO uses 8; MoE REINFORCE uses 64. The MoE experiment uses Qwen3-30B-A3B, DAPO-Math-17k training data, and AIME2024 evaluation, with a training batch-size parameter of 512 and prompt/response caps of 2,048/20,480 tokens. These are limits, not the realized length of every sample. [Paper §3 and Table 2](https://arxiv.org/html/2605.14220v2)

In that MoE setup, VeXact reportedly reaches an AIME2024 validation reward of 0.534, whereas the vLLM run degrades to 0.067. This supports the authors' concern about TIM under the tested conditions. It is neither a universal improvement factor nor a throughput measurement, and does not establish that TIM causes every other training collapse. [Training curves and experimental description](https://arxiv.org/html/2605.14220v2)

### A denominator example: how rescoring can hide a discrepancy

Continue with the teaching values. Let q_old = 0.400 be A's probability recorded during generation, and p_old = 0.404 be the trainer's probability under the same old weights. Before an update, the current trainer probability p_new also equals 0.404. Consequently, p_new / p_old = 1, whereas p_new / q_old = 1.01.

The first ratio correctly says that the training program has not changed. It does not reveal its discrepancy from the program that actually generated the data. The second ratio exposes that discrepancy. The recompute and bypass variants discussed in §4 involve which old probability enters the denominator. Such ratios can affect reweighting and clipping in an update, so the choice is more than a logging convention. [Paper §4](https://arxiv.org/html/2605.14220v2)

Changing a denominator still does not align the model's internal arithmetic. This does not invalidate the mathematics of importance sampling: practical training algorithms also involve clipping, approximations, and other implementation conditions. The small example explains why the ratios differ. It proves neither that a correction can never work nor that every update improves once numerical alignment is exact.

### Three boundaries to retain when reading the results

First, bitwise agreement is a property of specified execution paths. Different GPUs, operator versions, precision choices, architectures, or inactive patches can change its premises. The two paths can perform the same rounding and therefore return identical results without matching a higher-precision reference. Calling this 'zero numerical error' would be misleading.

Second, consistency and efficiency require separate measurements. Fixing some parallel partitions can affect performance, while serving optimizations such as chunked prefill and CUDA Graphs can save time. Reducing numerical variability does not imply an unmeasured speedup percentage. An engineering evaluation should record probability differences, generation time, and total time to reach a target training quality. That is this note's evaluation recommendation.

Third, repository updates must not silently expand the paper's evidence. Most reported experiments use seed 42; additional multi-seed checks mainly cover some GRPO settings. The current VeOmni integration is also not synonymous with the paper's FSDP2 environment. Treat the original experiments, subsequent code coverage, and a new configuration of your own as three distinct levels of evidence.

### A reading route and a minimal diagnostic experiment

Start with §3.1 and one question: exactly which model layers and operators share an implementation? Follow the pinned links through the training entry point, base operators, attention, and MoE. Then compare Table 2 with the training curves. Read §4 last, writing down which weight version and which program produced every probability. This establishes a basis for judgment before working through all the loss equations.

For a minimal diagnosis in your own system, freeze a checkpoint and save one rollout's tokens, effective lengths, positions, and masks. Have the trainer score exactly that sequence. Then vary only batch composition, lengths, and prefill/decode paths to see whether discrepancies appear. This is a proposed experiment, not a verification that we have already performed on the reader's system.

Retain at least the maximum absolute difference and the positions with nonzero differences, distinguishing strict equality from agreement within a tolerance. Mean differences alone, or agreement on the final answer, can miss problems. After this passes, introduce weight updates and asynchronous execution to examine staleness separately. The result is an evidence trail that can locate a failure, rather than an assumption that identical weights are sufficient.

## Optional reading · Defeating Nondeterminism in LLM Inference

**Year / publication：** 2025 · Thinking Machines Lab · technical article · 2025-09-10 · [Original source](<https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/>)

**Reading guidance：** Read the mechanism sections closely, especially fixed split sizes in attention; inspect the pinned matrix-multiplication implementation before returning to VeXact §3.1.

### 1. The same request, different neighbors in the batch

Start with a teaching example, not an experiment from the article. You submit an identical question twice without updating the weights. The server first processes your request alone, then processes it alongside seven others. This group of work executed together is a batch. Requests need not read each other's contents for the matrix shape to change and trigger a different underlying algorithm. PyTorch's [numerical accuracy documentation](https://docs.pytorch.org/docs/main/notes/numerical_accuracy.html) explicitly warns that computing a whole batch and selecting one element need not be bitwise identical to computing that element separately.

If two possible next tokens have nearly tied scores, a small numerical difference can reverse their ranking. At temperature zero, greedy decoding chooses the current highest-scoring token; it does not make the scores from separate executions equal. Once one token differs, subsequent inputs differ too, and the answers can diverge further. A useful diagnostic keeps the target request fixed, changes the number of neighboring requests, and compares that request's numerical results.

### 2. The dtype does not specify which numbers get added first

Consider a toy decimal calculator that retains three significant digits. To evaluate 1000 + 1 − 1000, adding the first pair rounds 1001 to 1000, leaving zero. Computing 1 − 1000 first gives the representable value −999, and adding 1000 then gives one. This teaching example is not an exact simulation of BF16. Real floating-point formats likewise retain finite precision; [NVIDIA's floating-point guide](https://docs.nvidia.com/cuda/floating-point/index.html) explains why operation order affects results.

A dtype specifies a storage format such as BF16, rather than every intermediate operation's order and precision. Combining many terms into a sum is a reduction. A GPU can assign a complete row to one group of threads or sum several pieces and combine them afterward. These routes agree over real numbers but may round differently. Repeating an unchanged complete batch reliably and preserving a target request's result after changing its batch are therefore different requirements. Fixing a random seed does not specify these addition orders either.

### 3. The first two fixes: row reductions and matrix multiplication

RMSNorm rescales a token's vector using the mean of its squared elements. For the teaching vector [1, 2, 3, 4], the squared elements sum to 30; with real, long vectors, the question is how those terms are accumulated. Fixing the processing of each row allows additional rows to increase the workload without changing this row's addition path. This supports batch invariance: the row's result remains unchanged when the surrounding work changes.

Matrix multiplication also accumulates many products for each output. An implementation can fix its output tile shape and accumulation order along the inner dimension, instead of switching computation strategies merely because the batch becomes smaller. The linked implementation selects fixed configurations by dtype, not by batch size; this does not mean all dtypes share one configuration. The tradeoff is intuitive: using a large computational tile for a small batch may leave some work unused. See the [pinned operator source](https://github.com/thinking-machines-lab/batch_invariant_ops/blob/f22b1fbe534b1fe045080f44a970a441caaf3c4f/batch_invariant_ops/batch_invariant_ops.py).

### 4. The third fix: how attention reads earlier content

Attention uses earlier tokens' K/V vectors; the KV cache stores these to avoid recomputation. Cache boundaries matter too. In a teaching example with blocks of four positions, six cached positions and six new positions require 2 + 2 blocks if handled separately, versus three blocks if combined into twelve positions first. That can change the reduction path. The article updates the cache and page table before attention, allowing it to read a unified sequence of logical positions.

Long contexts are often processed in separate pieces, called split-KV. Why is fixing the number of pieces insufficient? Consider another teaching example: the same causal-attention query is at token eight. Two equal splits put the boundary at four in an eight-token chunk, but at six when that query is included in a twelve-token chunk, although it still sees only the first eight positions. Fixing each split at four positions preserves its groups of 1–4 and 5–8; later positions are masked. Actual implementations must also control arithmetic within and between splits. [FlashInfer's interface documentation](https://docs.flashinfer.ai/api/attention.html) likewise connects fixed split sizes to deterministic merging, without implying that every backend enables this by default.

### 5. What the released code actually contains

The code was checked on 2026-10-20 at commit f22b1fbe534b1fe045080f44a970a441caaf3c4f. The library uses torch.Library to replace matrix multiplication, matrix multiplication with a bias, log-softmax, and certain mean operations. Log-softmax converts candidate scores into log-probabilities and also involves reductions that require control. The [README at that revision](https://github.com/thinking-machines-lab/batch_invariant_ops/blob/f22b1fbe534b1fe045080f44a970a441caaf3c4f/README.md) describes the vLLM example as a proof of concept.

The operator package should not be equated with a complete serving system. At publication, the article said that the internal FlexAttention modifications needed for fixed split sizes were absent from its code release; that is a statement about its historical release. Integration still requires checking the operators and attention backend actually used by the model. Importing the package does not demonstrate that every execution path has been replaced, and this historical example does not establish the defaults of your current installation.

### 6. Measured cost and missing experimental conditions

The performance experiment served Qwen3-8B on one GPU: 1,000 requests, each producing 90–110 tokens. Total time was 26 seconds for default vLLM, 55 for the unoptimized deterministic variant, and 42 with improved attention. The GPU model and complete input-length and arrival-load protocol were unspecified, so this demonstrates a cost for that setup rather than a universal overhead percentage. See the article's [Performance section](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/).

The mechanism suggests asking which optimization choices the consistency requirement restricts and how often your workload needs them. Another boundary is tensor parallelism, or TP: splitting an operator across GPUs introduces cross-device result reductions, which the article excludes from its discussion. Fixing single-device operators therefore does not automatically preserve bitwise results after changing the TP degree, hardware, or software version.

### 7. Back to VeXact: compare probabilities, not just text

This reading motivates two checks. First, does changing a batch alter the same generator's result? Second, for identical weights and token sequences, do the generator and trainer compute identical log-probabilities? VeXact builds a reference for the second question by unifying model and operator implementations and using batch-invariant operators. Its attention implementation disables KV splitting; fixed split sizes, explained above, are a different approach. Matching greedy text alone is insufficient: two distributions can share the same top token while assigning different probabilities elsewhere. See [VeXact v2 §3.1](https://arxiv.org/html/2605.14220v2#S3.SS1).

Having no stale weights excludes differences caused by parameter versions; it does not exclude differences between training and inference computations. Read the matrix-multiplication and attention mechanisms first, inspect the pinned code, and then return to VeXact's alignment checks. A useful question to take back to a systems code review is whether a cache, scheduling, or parallelism optimization also changes the computation path of the same token. That is a diagnostic question, not a claim that an existing system is already faulty.

## Optional reading · Score Centering Stabilizes Off-policy Reinforcement Learning

**Year / publication：** 2026 · arXiv 2026 · v1 2026-09-17 · Together AI · [Original source](<https://arxiv.org/abs/2609.20807v1>)

**Reading guidance：** Worth an optional close read; allow 25–35 minutes. Start with the recorded-data and tail examples below, then the pinned README, losses.py, and tests/test_loss.py, followed by the experimental limits in Section 5 and Appendix B.

### Why training can stabilize while the probabilities still differ

The generator writes an answer; the trainer later recomputes its token probabilities and updates weights. Quantization, different operation orders, or older weights can make the two probabilities disagree. VeXact tries to align computation paths. Score Centering permits disagreement and modifies the training update instead. Its zero concerns an average push, not identical output probabilities.

A score is not the reward. It is the gradient direction for increasing a token's log-probability. Constant rewards provide no reason to prefer one outcome, yet these directions can have a nonzero average when tokens come from another distribution. Centering subtracts that average before weighting by reward or advantage; advantage expresses reward relative to a comparison baseline. The preprint by Together AI's Martin Marek and Max Ryabinin first appeared on September 17, 2026. [Paper record](https://arxiv.org/abs/2609.20807v1)

### Top-k determines what is recorded, not what may be generated

Source was checked on October 20, 2026, at official repository commit `64842967077ea105470ca73fc5d714366d3f7bdb`. Logits are raw scores for candidate tokens before conversion to probabilities. Generation still samples from the distribution defined by the full logits. Separately, it retains the identifiers and log-probabilities of the k most likely tokens at each position. The sampled token's log-probability is retained even when that token is outside the head. It records the probability of the actual choice for importance weighting. [Sampling code](https://github.com/martin-marek/score-centering/blob/64842967077ea105470ca73fc5d714366d3f7bdb/models/sampling.py)

Collection buffers 32 steps, selects a local top-k on each vocabulary shard, then selects the global top-k from those candidates. The retained head is selected exactly; approximation concerns the unrecorded tail. The trainer must look up the same token identifiers, rather than choose its own head. Renormalizing recorded entries to sum to one would erase the remaining tail mass. [Collection implementation](https://github.com/martin-marek/score-centering/blob/64842967077ea105470ca73fc5d714366d3f7bdb/models/topk.py); [interface requirements](https://github.com/martin-marek/score-centering/blob/64842967077ea105470ca73fc5d714366d3f7bdb/README.md)

Recording has a real storage cost: head identifiers use int32 and log-probabilities use float32. At k=128, these two arrays alone require approximately 1 KiB per position, alongside a 32-step full-vocabulary ring buffer. This is a calculation from code shapes, not a measured throughput result. Integrating separately deployed trainers and generators also requires measuring transfer costs. [Buffer layout](https://github.com/martin-marek/score-centering/blob/64842967077ea105470ca73fc5d714366d3f7bdb/models/topk.py)

### How the unrecorded tail enters the correction

**Teaching example, not an experimental result:** suppose recorded entries cover 80% of sampler probability but 90% of trainer probability. The tails contain 20% and 10%, so `rho = 0.20 / 0.10 = 2`. For unrecorded tokens, provisionally double the trainer probabilities to model the sampler tail. This matches its total mass, not necessarily each tail token.

Let p denote training probabilities and q sampling probabilities. For every recorded entry, the implementation computes `q − rho × p`, multiplies it by the corresponding training log-probability, and sums the terms into a correction subtracted from the ordinary training term. It avoids recording individual tail entries because the expected score under the full training distribution is zero, allowing the tail contribution to be replaced by the negative head contribution. [Loss implementation](https://github.com/martin-marek/score-centering/blob/64842967077ea105470ca73fc5d714366d3f7bdb/losses.py)

The coefficients must use stop-gradient: treat them as constants during this backward pass and differentiate only the log-probabilities they multiply. Otherwise, differentiating the coefficients adds a different update. The implementation also protects near-zero tail masses and computes full-vocabulary training log-softmax in chunks. Keeping k entries reduces stored sampling history; it does not reduce all training computation to k vocabulary entries. [MIT-licensed implementation](https://github.com/martin-marek/score-centering/blob/64842967077ea105470ca73fc5d714366d3f7bdb/losses.py)

### Why the zero-drift test does not prove exactness for every tail

The official test enumerates three tokens, weights their gradients by the actual sampling probabilities, and checks that the average is near zero. Its top-k case uses k=2, leaving a single tail token. Knowing the tail mass then determines that token's probability, making the approximation exact. This is a useful implementation test, but it does not cover a complex tail. [Test conditions](https://github.com/martin-marek/score-centering/blob/64842967077ea105470ca73fc5d714366d3f7bdb/tests/test_loss.py) The test evaluates an enumerated expectation; a finite batch still has sampling noise, so its actual gradient need not vanish on every step.

**Independent derivation example:** in a four-token vocabulary, suppose two tail tokens each have true probability 0.10 but are modeled as 0.15 and 0.05. Their total mass remains correct. In a teaching model parameterized directly by logits, the centered mean update with reward fixed at +1 equals actual probability minus modeled probability, leaving −0.05 and +0.05 at those positions. Matching tail mass therefore does not ensure exact zero drift. A real model additionally maps parameter changes into logits, so the resulting impact requires measurement.

### Why combine it with importance sampling?

Importance sampling weights observations by p/q to convert statistics from q into statistics under p. A full, untruncated correction has a different objective from merely removing the average direction: the latter still learns from outcomes as they occur under q. Practical methods often cap large weights or discard weights outside a band to limit extreme samples.

The combined implementation first chooses a weighting function f, then centers the weighted score rather than the original score. Every modeled tail probability is rho×p, making its p/q ratio 1/rho; the correction therefore uses `alpha = rho × f(1/rho)`. Composition recomputes the appropriate mean instead of arbitrarily adding two independent losses. The pinned README supplies truncated importance sampling (TIS, capping large weights) and masked importance sampling (MIS, zeroing weights outside a specified band) entry points. Applying corrections per token should also not be described as recovering the complete trajectory distribution. [Composition implementation](https://github.com/martin-marek/score-centering/blob/64842967077ea105470ca73fc5d714366d3f7bdb/README.md)

### Amplified mismatch, and why the configuration matters

Public configurations train Qwen3-0.6B on Countdown and Qwen3-30B-A3B-Base on INTELLECT-2 mathematics. Total sequence buffers hold 512 and 1,024 tokens respectively; each prompt has eight completions, with 64 and 16 prompts per batch. Each batch receives one stochastic gradient descent (SGD) step at learning rate 0.01. Training computation uses BF16, while the sampler deliberately receives strong quantization or stale weights. This is controlled training, not a complete long-horizon tool-using serving system. [Small-model configuration](https://github.com/martin-marek/score-centering/blob/64842967077ea105470ca73fc5d714366d3f7bdb/sweeps/06b_quant_stale.yaml); [30B configuration](https://github.com/martin-marek/score-centering/blob/64842967077ea105470ca73fc5d714366d3f7bdb/sweeps/30b_math.yaml)

The paper describes refreshing the sampler every 64 training steps; composition with importance sampling outperforms centering alone in that setting. The pinned code instead sets `staleness=64` and refreshes when `step % (staleness + 1) == 0`, giving a 65-step interval. These specifications are not identical, and neither should be presented as an asynchronous system's maximum sample delay. [Section 5.3](https://arxiv.org/html/2609.20807v1); [refresh logic](https://github.com/martin-marek/score-centering/blob/64842967077ea105470ca73fc5d714366d3f7bdb/train_rl.py)

The paper deliberately combines short sequences with severe mismatch to separate methods sooner. Quantization and staleness plots primarily report training accuracy. Small-model experiments use multiple seeds, while some 30B methods have only one. This supports further testing, not a direct extrapolation to long sequences, mild numerical error, or production asynchronous queues. [Section 5, Appendix B](https://arxiv.org/html/2609.20807v1)

### Three checks to bring back to a training system

**Engineering deductions:** first check recorded probabilities on identical prefixes against the weights and sampling rules actually used during generation. Next measure head coverage, tail approximation, and the remaining mean gradient under constant rewards. Finally compare reward, variance, and throughput at real sequence lengths and refresh schedules. The first two checks diagnose whether the correction is computed as intended; the last determines whether it helps.

Begin with the README's input tensors, follow sampling.py and topk.py into losses.py, then inspect tests and experiment configurations. Alongside VeXact, keep two questions distinct: can the computations produce matching probabilities, and how can harmful updates be reduced when they do not? Improved stability is outcome evidence, not a substitute for checking numerical agreement.
