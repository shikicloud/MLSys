# When does memory help an agent improve with experience?

Remembering an experience, extracting a useful method, and applying that method to a new task are different problems. The main reading, LifeMem, groups trajectories across environments by workflow and extracts reusable skills. AdaMEM asks how strategies should change midway through a task; MemoryArena tests whether memory supports later actions that depend on earlier results. Together they distinguish external-memory accumulation, adaptation through the current context, and offline weight training. Start with the main reading’s example and mechanism, then compare the optional papers as interest permits.

Each digest recommends 1 main paper and 2–4 optional papers across LLM inference, RL infrastructure, post-training, RSI (recursive self-improvement), reasoning compute, agent learning and memory, data and evaluation, and model architecture. Explore foundations and current research by theme; a direct connection to current work is not required. A recommendation does not mean it has been read, and there is no need to finish everything in one day.

## Main reading · LifeMem: Enabling Lifelong Experience Reuse for LLM Agents

**Year / publication：** 2026 · arXiv 2026 · BIT / Beihang / HIT / Baidu · v1 2026-09-11 · [Original source](<https://arxiv.org/abs/2609.12655v1>)

**Reading guidance：** Read the mechanism and ablations closely. Start with Figure 2 and §4, use Tables 3/9 to separate the contributions of trajectories and skills, then inspect task order, FEVER transfer, and per-dataset results. The average improvements are meaningful, but they do not establish improvement in every environment or indefinite self-improvement.

### Why can an agent use the wrong tool even after collecting useful experience?

Suppose an agent previously used Wikipedia search to find a museum's opening year and also used a database tool to look up prices. It now needs to verify the claim that the museum opened in a particular year. This is a teaching example: retrieving old records by textual similarity alone might return a topically related trajectory from a different tool interface. The model copies that example's calling convention, but the current tool does not accept it.

A trajectory records the observations and actions within a task: what the agent saw, what it called, and what the tool returned. Keeping the complete record preserves concrete experience, but also ties that experience to its original environment. Conversely, retaining only a vague instruction such as “analyze, then act” gives little help with the next action. LifeMem tries to keep both usable operational detail and procedural guidance that remains useful across tasks.

The appendix shows a related failure: during fact verification, a baseline retrieves a record from another tool environment and produces a search action with invalid outer brackets. In that example, LifeMem retrieves records from the same Wikipedia-search environment and avoids the misleading syntax. The case explains how interference can arise; the experiments are still needed to assess the average effect. [Paper v1 and Appendix N](https://arxiv.org/html/2609.12655v1#A14)

### What learns here is the memory store, not the model weights

LifeMem has a language model execute tasks while storing accumulated experience outside the model. Before the next execution, relevant memories are added to the input as text and influence the model's actions. The method does not use these experiences for gradient updates; it changes trajectories, cluster descriptions, and skill text. This is nonparametric memory learning: experience resides outside the model parameters.

This distinction also changes what forgetting means. Performance on an old task can decline even without new training overwriting the model's weights. Retrieval can return unsuitable records, later experience can make a summary too generic, or several pieces of advice can interfere with one another. Results showing less forgetting in this setting therefore do not directly establish a solution to catastrophic forgetting in neural-network parameters.

This note is based on the September 11, 2026 v1 by Yuli Qiu and colleagues at Beijing Institute of Technology, Beihang University, Harbin Institute of Technology, and Baidu. The paper is licensed CC BY 4.0; this note is an explanatory adaptation and review. The authors report EMNLP 2026 main-conference acceptance, which this review has not independently confirmed through the conference; the discussion below concerns the methods and results verifiable in the paper. [Paper and license](https://arxiv.org/abs/2609.12655v1)

### Writing memory starts by identifying the workflow

LifeMem initializes memory with five trajectories. A language model groups them by the steps needed to complete their tasks and writes a short description of each workflow cluster. A workflow describes the subproblems that must be solved to obtain a result, rather than merely the nouns shared by the tasks. In the teaching example, “locate the entity, resolve ambiguity, retrieve the attribute, and check the evidence” is a more reusable workflow than “about museums.”

For each incoming trajectory, vector retrieval first finds four relevant old trajectories and obtains their cluster descriptions. A language model then decides whether the new experience fits one of those clusters. If it does, the trajectory is added and the description is updated; otherwise, a new cluster is created. Vector retrieval converts text into numerical representations that can be compared efficiently. It narrows the candidates, while a language model makes the grouping decision.

The reported configuration uses all-MiniLM-L6-v2 for embeddings, FAISS for retrieval, and SQLite for cluster storage. GPT-5-mini assigns incoming trajectories, while GPT-4.1 handles later splitting and skill distillation. These are the paper's settings, not current product recommendations. They also show that organizing experience requires additional model calls; learning does not happen merely by putting text into a database. [§4.1–4.2 and §5.4](https://arxiv.org/html/2609.12655v1#S4)

### When a cluster becomes too mixed, how is it split and summarized?

As a cluster grows, its original description may stop representing its contents. However, a large cluster of repeated similar tasks is different from a heterogeneous cluster containing incompatible workflows. The paper normalizes each trajectory embedding to unit length, averages those vectors, and measures the length R of that average. R approaches one when the vectors point in similar directions and becomes smaller when their directions spread out.

This quantity is called mean resultant length, or MRL. The settings in §5.4 trigger splitting only when both conditions hold: the cluster contains more than 50 trajectories and R is below 0.95. It is a signal for asking the language model to regroup the cluster. Similar embedding directions do not guarantee identical workflows: MRL is a proxy under the selected embedding representation, not a mathematical guarantee of correct grouping.

After grouping, the system distills three to five general rules from successful trajectories in each cluster. For the teaching example, these could be: “Identify the target entity first; resolve ambiguity when names overlap; query and cross-check separate attributes when the answer depends on several facts.” These are the paper's skills: readable textual guidance, not executable functions or newly trained neural modules. Producing them within relatively coherent clusters is intended to keep unrelated experience out of each summary. [§4.2 and Appendix L](https://arxiv.org/html/2609.12655v1#S4.SS2)

### At retrieval time, two kinds of memory answer different questions

The first layer supplies historical trajectories from the same environment, answering “How are tools actually called here?” For example, when the agent still uses Wikipedia search, it can refer to the examples' Search, Lookup, and Finish formats. It should not copy a database interface's syntax into that environment. The paper calls these environment-aligned trajectories.

The second layer supplies skills from the clusters associated with those trajectories, answering “What steps usually help with this kind of task?” A cluster can contain experiences with similar workflows from different environments. Its textual skills can therefore bring in other environments' experience without also inserting their low-level calling conventions. The resulting input contains the task, current observation, concrete examples, and abstract guidance. [§4.3](https://arxiv.org/html/2609.12655v1#S4.SS3)

Returning to the museum example, the old question-answering task and the new fact-verification task require different final outputs, but both involve identifying an entity and checking evidence. Existing Wikipedia trajectories help the model call the tools correctly; the skills help it plan the verification. This explains why the two layers might complement each other. It does not imply that every workflow transfers automatically across environments, or that abstract guidance can replace the current environment's rules.

### How long is the learning process, and who supplies the experience?

Table 1 lists 12,489 training instances and 1,230 test instances across ten environments covering embodied action, tool use, search, data analysis, and browser interaction. The main experiment adds experience in environment-specific stages and then reevaluates earlier tasks. LifelongAgentBench supplies training data only, so the final overall score averages nine test datasets. The headline of more than thirteen thousand tasks includes training and testing; it should not be described as the agent independently completing that many tasks online.

The authors construct four of the data sources: GPT-4.1 generates 2,310 trajectories in the environments, of which environment feedback marks 1,541 as successful. Five human reviewers assess the reasonableness of intermediate steps and report that more than 90% are reasonable. That figure is not the end-to-end task success rate, and it does not mean humans manually wrote more than two thousand solutions. Teacher generation, environmental feedback, human checks, and memory organization all contribute to the experience pipeline. [§5.1 and Appendix B](https://arxiv.org/html/2609.12655v1#S5.SS1)

The executing models are GPT-4o-mini, Deepseek-v3.2-exp, and Qwen3-32b. Sampling temperature is 0.3, and reasoning mode is disabled for the latter two. The experience-extraction baselines also use GPT-4.1 to reduce differences caused by the extraction model. The experiment supports accumulation and reuse within this finite, prepared stream. It is not yet a loop that explores autonomously, modifies its own learning algorithm, and improves indefinitely.

### Separate final performance from changes on earlier tasks

Overall Performance, or OP, averages the test-dataset scores after all experience has been added. With GPT-4o-mini, LifeMem scores 44.13, compared with 28.84 for memory-free ReAct and 41.85 for ExpeL, the strongest memory baseline in that setting. The improvement over ExpeL is 2.28 score points, or approximately 5.45% relative improvement. The reported 5.45% must not be read as an increase of 5.45 percentage points.

Backward Transfer, or BwT, asks a different question: after later experience is added, how much does an earlier task improve or decline relative to its score immediately after its own stage? In a teaching example, a task that rises from 50 to 55 gains five points, but its relative change is `(55−50)/50 = 10%`. The paper computes these relative changes for the earlier tasks and averages them. The final task is excluded because no later stage follows it.

LifeMem's average BwT is positive for all three executing models; it is +5.66% for GPT-4o-mini. This does not mean every earlier task improves. For that model, τ-bench and ToolQA still show negative transfer, and ToolQA's final 68.75 is below memory-free ReAct's 73.53. The evidence supports better overall averages and less average interference, rather than the best result on every task or complete elimination of forgetting. [Table 2, Table 13, and metric definitions](https://arxiv.org/html/2609.12655v1#S5.SS3)

### Where do the gains come from, and what does the cost estimate include?

The ablations use the two memory layers separately. With GPT-4o-mini, environment-aligned trajectories alone score 42.84, GPT-4.1-distilled skills alone score 37.61, and the combination scores 44.13. Concrete examples therefore already provide a large share of the gain; adding skills contributes another 1.29 points in this comparison. The full improvement over the memory-free baseline cannot all be attributed to abstract skills. [Tables 3 and 9](https://arxiv.org/html/2609.12655v1#S6.SS1)

When GPT-4o-mini distills its own skills, the complete system scores 43.18, slightly below 44.13 with GPT-4.1 skill extraction. This weakens the explanation that a stronger teacher writing skills accounts for everything. It does not remove teacher contributions, because some original trajectories still come from GPT-4.1. Nor does it establish that the independent causal effects of environment filtering, clustering, and skill distillation have all been fully isolated.

The cost table measures average input size for the first model call of each task: approximately 2.18k tokens for LifeMem versus 1.88k for Synapse, a difference of about 300 tokens. It includes the system prompt, examples, skills, and task description—not all tokens or latency across the full interaction. The paper separately estimates memory construction at approximately one dollar per thousand trajectories under its reported configuration and pricing. This is not a guarantee of real-time cost at a million-experience scale. [Appendix G](https://arxiv.org/html/2609.12655v1#A7)

### Old experience can help a new task, but task order still matters

A relatively clear transfer test moves from HotpotQA question answering to FEVER fact verification. The task format changes, while Wikipedia search still supplies the evidence. The authors evaluate 100 FEVER test instances with at most four steps per task. For GPT-4o-mini, performance rises from 0.40 with ReAct to 0.49 with LifeMem; skills alone reach 0.47. AutoSkill also reaches 0.49 here, so LifeMem is not the sole best method in this setting.

This result shows that old experience can help with a new task format; it does not establish adaptation to arbitrary unfamiliar tools. The appendix explicitly restricts FEVER trajectory retrieval to the HotpotQA memory repository, using a known correspondence between the environments. When no examples from the same environment exist, the exact skill-retrieval path and how valid actions are ensured still need clearer implementation documentation. [§6.2 and Appendix A.6/N](https://arxiv.org/html/2609.12655v1#S6.SS2)

The main experiment presents similar environments consecutively. Fully randomizing the trajectory order reduces GPT-4o-mini's OP from 44.13 to 39.63. Accumulating five trajectories in small task-specific buffers before adding them in batches recovers the score to 41.64. Memory organization is therefore sensitive to input order, and buffering partially mitigates rather than removes the difference. This tests how a finite task stream is processed, not the rate of long-term autonomous improvement. [§6.3](https://arxiv.org/html/2609.12655v1#S6.SS3)

### How to read the paper, and what still needs clarification before reproduction

Start with Figure 2 and §4 and trace the flow: trajectories enter clusters, clusters produce skills, and execution retrieves both memory layers. Then read the ablations in Tables 3/9, followed by the per-task results in Table 13 and the task-order experiment. The central useful idea is this organization of experience. The paper does not establish that model weights acquire new capabilities, that every environment benefits, or that the system recursively improves its own learning mechanism.

Several reproduction questions should be recorded explicitly. Table 1 labels τ-bench as airline, while the appendix describes retail as the training domain and airline as unseen; readers should not silently resolve that conflict for the authors. The paper describes training/test splits but does not explicitly establish whether memory is frozen during testing or whether test trajectories are written back. Skill retrieval without any same-environment trajectory is also insufficiently specified. Fixing memory snapshots for each stage and checking these paths is a reproduction recommendation, not a claim that the paper has already demonstrated those safeguards.

The main results do not provide variance sufficient to assess stability across random seeds, so small differences deserve caution. The authors also leave deployment with millions of experiences as future engineering work. For a real agent, useful additional measurements would include memory-write cost, retrieval errors, how summaries change over time, and full-task latency alongside correctness. These are evaluation directions inferred from the mechanism; no model experiments were rerun for this note. [Paper v1](https://arxiv.org/html/2609.12655v1) · [Authors' code and data](https://github.com/BITHLP/LifeMem)

## Optional reading · AdaMEM: Test-Time Adaptive Memory for Language Agents

**Year / publication：** 2026 · ICML 2026 · PMLR 306 · [Original source](<https://proceedings.mlr.press/v306/zhang26cn.html>)

**Reading guidance：** Read §3.1, Algorithm 1, and §3.2 closely: first follow runtime strategy updates, then inspect which strategies become training targets. Use Table 1 and Appendix D to check effectiveness and cost.

### 1. When the cabinets are empty, should the agent keep following old advice?

The paper gives a concrete task: put two soapbars in a garbagecan. Following its initial advice, the agent checks cabinets and repeatedly finds nothing. It retrieves experience again, switches to a countertop, and finds the soapbars. After it picks up the first, the environment does not permit immediately taking the second. The agent revises its strategy again: deposit the first, then return. This illustrates changing the procedure mid-task, beyond finding a similar record at the start. [Appendix C.2 and Figure 7](https://arxiv.org/html/2606.05684v1)

AdaMEM comes from the University of Michigan and Cisco Research, appeared in June 2026, and is officially included in ICML 2026. It complements today's memory theme by asking how past experience should guide the present action, and whether a model can be trained to turn that experience into more useful advice. [Original paper](https://arxiv.org/abs/2606.05684), [official proceedings](https://proceedings.mlr.press/v306/zhang26cn.html).

### 2. Store successful procedures, then search using the current situation

The authors first collect complete interaction sequences on training tasks and retain only those ending in success. Each step stores the situation, the next action, and the remaining successful sequence. Situations are converted into numerical vectors for similarity search. At test time, the current situation retrieves a similar record, with one retrieved record by default. The experience bank stays fixed throughout testing. [§3.1 and §4.1](https://arxiv.org/html/2606.05684v1)

The model combines that record with the present environment to write short advice, such as depositing the item already held before taking another. The paper calls this short-term strategy memory, which then guides action selection. The full interaction history still appears in the prompt: the retrieved experience is condensed, rather than the entire task history being replaced by a summary. [§3.1](https://arxiv.org/html/2606.05684v1)

### 3. Discard the advice after one action, or keep using it?

In high mode, each step first proposes an action and decides whether to retrieve memory. A no decision executes that proposed action. A yes decision triggers retrieval, strategy generation, and a newly generated action. The strategy serves only that step and is then discarded. High does not mean unconditional retrieval at every step. [§3.1 and Algorithm 1](https://arxiv.org/html/2606.05684v1)

Low mode retains the current strategy across steps and decides each time whether to refresh it. It retrieves again and replaces the strategy only when a refresh is chosen. This saves advice generation, but the model may mistakenly judge an outdated plan to remain useful. Neither mode changes model parameters—the numerical values saved by training—during execution. [§3.1](https://arxiv.org/html/2606.05684v1)

### 4. Training the model to write useful advice

Step-MFT first runs high mode on training tasks. It records both the action proposed without the strategy and the action actually executed with it. A strategy is retained only if the task ultimately succeeds and those action strings are not exactly identical. For example, a proposed cabinet search that becomes a countertop visit after reading the advice could qualify. [§3.2.1–3.2.2](https://arxiv.org/html/2606.05684v1)

The retained strategy becomes a training answer: given the current situation and retrieved records, the model practices generating that advice. This is supervised fine-tuning, or SFT. The implementation uses LoRA, training a small set of added parameters, with rank 32, batch size 64, and one pass through the data. ALFWorld uses 13,067 filtered strategies. After training, the same model generates both strategies and actions. This is not continued reinforcement learning while executing test tasks. [§3.2.3, §4.1, and Appendix A](https://arxiv.org/html/2606.05684v1)

### 5. How much improvement, at what additional compute cost?

Table 1 evaluates Qwen3-4B-Instruct-2507 on ALFWorld's 134 tasks with unseen room layouts. Success rates, reported as mean ± standard deviation across three independent runs, are 46.8 ± 2.5% without memory, 52.2 ± 0.7% for Synapse, which provides past interaction sequences, and 58.2 ± 3.9% for AdaMEM-low. Memory methods share the same pool of 1,596 successful training trajectories, and retrieve one record by default. Appendix A reports 48GB A40/L40S GPUs, sampling temperature 0.7, and a 2,048-token cap per generation. [§4.1 and Table 1](https://arxiv.org/html/2606.05684v1)

Separately, in Table 5's ALFWorld cost configuration with the same Qwen3 model, low consumes an average of 90K total tokens per task with 54.0% success; Synapse uses 117K with 52.1%; no memory uses 77K with 45.2%. The table does not restate the split, so its costs should not be paired directly with the unseen results above. Low saves tokens relative to inserting historical interaction sequences, but still costs more than using no memory. Total-token consumption cannot be directly translated into dollar costs or serving throughput. [Appendix D, Table 5](https://arxiv.org/html/2606.05684v1)

Sharing the experience pool makes the comparison easier to interpret: AdaMEM was not simply given an extra collection of successful demonstrations. However, retrieval timing, strategy generation, and the number of calls all change, so Table 1 alone does not identify which change contributes most. The authors separately remove components to examine the mechanism; distinguish those diagnostic experiments from comparisons of complete systems. [§4.1 and §4.3](https://arxiv.org/html/2606.05684v1)

### 6. A changed action does not prove that the advice caused success

The action proposed without the strategy is hypothetical: it is not executed through to the end of the task. We therefore do not know whether it would also have succeeded. Under assumptions including deterministic action selection, the authors argue that a changed action is necessary for positive strategy advantage. The implemented filter only compares strings, however, and does not establish causation. A successful training trajectory does not make every piece of advice correct. [§3.2](https://arxiv.org/html/2606.05684v1)

All experiments use text environments. Scarce successful experience limits the memory bank, and the model can refuse to refresh a strategy that has stopped working. Offline bank construction and offline fine-tuning do not demonstrate autonomous, continuing improvement after deployment. A useful serving implication is to track the extra retrieval, strategy-generation, and action-generation calls, then assess whether reusing advice pays off. That is a system-design implication; the paper does not measure production serving tail latency. [§4.1 and Appendices C.3 and E](https://arxiv.org/html/2606.05684v1)

### 7. Reading route and attribution

Start with Figure 7's soapbar example, then trace both low and high through Algorithm 1. Next read Figure 3 and follow why one strategy is retained for training. Finally compare Tables 1 and 5, keeping task splits, success rates, and compute consumption separate. The equations can wait for a second pass: first distinguish changing advice at runtime from changing the model during training. [Full text and appendices](https://arxiv.org/html/2606.05684v1)

## Optional reading · Benchmarking Agent Memory in Interdependent Multi-Session Agentic Tasks

**Year / publication：** 2026 · ICML 2026 · PMLR 306 · July 2026 · [Original source](<https://proceedings.mlr.press/v306/he26am.html>)

**Reading guidance：** Study task construction, scoring definitions, and failure cases: start with §3 and §4.2, then Appendices C.1 and C.3–C.4. Treat rankings as results under particular configurations.

### 1. Recalling a purchase does not ensure choosing the next one correctly

Consider a teaching example: an agent first selects a camera body, then a lens, and finally compatible accessories. Correctly answering which camera it bought is only the first step. Useful memory must also shape search conditions, rule out lenses with incompatible mounts, and track the budget already spent. One poor choice can affect subsequent purchases.

MemoryArena builds evaluations around such dependencies. Each subtask runs its own conversation and tool interactions, called a session. Later sessions need earlier choices and environmental feedback. The paper asks whether storing, retrieving, and using information jointly support task completion, complementing the mechanisms in today’s other memory readings.

### 2. How the tasks make previous experience necessary

The proceedings version contains 701 task groups covering bundled shopping, group travel planning, progressively narrowed search, and mathematical and physical derivations. Shopping requires compatible products; a new traveler may request dinner with an earlier participant; search adds conditions over time; derivations reuse earlier definitions and results. The authors manually verify tasks and answers so later steps depend only on information already introduced. See [§3 and Table 2](https://proceedings.mlr.press/v306/he26am.html).

Memory is reinitialized for each task group and then persists across sessions within that group; travel also supplies the first traveler’s confirmed itinerary. Backends may retain complete history, make it retrievable, or distill it before storage. Retrieval-augmented generation, or RAG, retrieves relevant records before passing them to the model. Completing a subtask updates memory before the next begins. This scope differs from continuously accumulating experience across many independent tasks.

### 3. Establish what success actually means

The paper reports success rate, SR, and progress score, PS. PS first calculates the fraction of correctly completed subtasks within each group and then averages across tasks; travel also uses sPS to measure the fraction of constraints satisfied. In a teaching example, an itinerary satisfying nine requirements but missing one may have high partial progress while remaining invalid overall. Reporting only partial progress can hide this practical failure.

The SR definition varies by environment. Shopping and travel check whether the final bundle or plan meets the overall requirements. Search, mathematics, and physics check whether the final subproblem is answered correctly. In the latter domains, SR therefore does not mean that every preceding step was correct. Establish the scoring target before interpreting a memory system as more reliable. See [§4.2](https://proceedings.mlr.press/v306/he26am.html).

### 4. The same memory approach can help one task and hurt another

To avoid the main table’s inconsistent GPT-5-mini and GPT-5.1-mini naming, consider Appendix C.1, which explicitly uses Claude Sonnet 4.6. Across the paper’s 221 progressive-search task groups, final-question success is 6% with complete history and 27% with vector memory retrieval using text-embedding-3-small. However, overall success across 150 bundled-shopping groups falls from 13% to 4%. Both comparisons hold the task model fixed, showing that retrieval benefits depend on the task rather than establishing a universally superior backend. See [Table 5](https://proceedings.mlr.press/v306/he26am.html).

This workload is more than answering one isolated question: the agent can repeatedly call search tools and continue searching with prior subproblem results. Search obtains external materials, whereas memory retrieval recalls earlier sessions; these are distinct operations. Appendix B specifies sampling and search settings for the main experiments, but Appendix C.1 does not separately enumerate a complete configuration for the added Claude 4.6 comparison. Reproduction therefore still requires checking exact model versions and run settings. These numbers are not a ranking of products’ current default behavior.

### 5. Failure can occur at three stages, and the final score cannot locate it

Revisit the camera example. Writing memory might omit the mount type; retrieval might return only the budget even though the mount was stored; or the model might buy an incompatible lens despite receiving the correct mount. These failures concern storage, retrieval, and use respectively. The paper’s cases include missing purchase attributes during retrieval and failures to enforce constraints even with complete history in the input. A wrong final answer alone cannot identify the failed stage.

Appendix C.3 also supplies correct outcomes from previous subtasks and concise workflows distilled by a model. Performance improves but remains low. This is an approximation to ideal memory assistance, not proof that every necessary piece of information has been supplied. A defensible interpretation is that improving memory inputs helps while subsequent reasoning and actions can remain bottlenecks; remaining errors cannot all be assigned to a single component.

### 6. Include memory operations in the cost of completing the task

Storage, summarization, and retrieval can add calls and waiting time. Although the framework supports retrieval before each action, Appendix B.1 says the actual experiments retrieve once at the beginning of each session to reduce frequency and cost. Complete history has a cost too: inputs grow longer. The paper therefore reports subtask and whole-task completion times rather than only the latency of the retriever itself.

The experiments use commercial model APIs, with H100 GPUs for some local computation. End-to-end time also depends on generation length, tool-call counts, and service responses, so reported seconds should not be interpreted as a fixed overhead intrinsic to a memory algorithm. For systems work, measure success, input and output tokens, memory-operation counts, and total completion time together. This is a measurement recommendation prompted by the reading.

### 7. Reading route and scope

Begin with task examples in §3 to understand dependencies, read the scoring definitions in §4.2, and then inspect comparisons and failures in Appendix C. The benchmark can expose information that was remembered but used poorly, although its constraints are deliberately constructed. It also does not fully separate memory quality from planning, reasoning, and tool-use capabilities. When applying it to a system, inspect actual failure trajectories rather than treating one aggregate score as evidence that long-term memory has been solved.
