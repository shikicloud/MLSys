# MoE inference: why does less computation not always mean more speed?

MoE activates only some experts for each token, yet can still spend considerable time waiting for data. The main reading, RapidMoE, keeps low-precision weights on GPUs and adds CPU computation for a small critical set, reducing large weight transfers. Stepped MoE asks whether training can make a generation segment reuse its experts. Sem-MoE shows how jointly placing experts and scheduling requests can reduce activation transfers between devices. Their hardware settings, permitted design changes, and accuracy tradeoffs differ, so their speeds should not be compared directly. Start with the main mechanism; read the others as interest permits.

## Main reading · RapidMoE: Exploiting Cross-Asymmetry via Adaptive Residual Offloading for Large-Scale MoE Inference

**Year / publication：** 2026 · arXiv 2026 · Tsinghua University · v1 2026-10-01 · [Original source](<https://arxiv.org/abs/2610.01265v1>)

**Reading guidance：** Study Figure 7/9 and §4.4–4.5 first to understand how an expert computation is divided, then read §4.3 on precision selection and Tables 8–10 on throughput, serving latency, and memory. Single-request speed, aggregate batch throughput, and SLO attainment answer different questions; the abstract's speedup alone is not enough.

### Why can a model still fail to fit when it computes only eight experts?

A mixture-of-experts, or MoE, layer contains many feed-forward networks called experts. For each token, a router selects a few of them and combines their outputs with weights. For example, DeepSeek-R1 selects eight routed experts from 256, alongside a shared expert. This reduces the parameters used in one computation, but the next step may select another eight. All experts' weights still need somewhere to reside.

Consider a workstation with limited GPU memory and more plentiful CPU memory. The teaching example used throughout this note considers the eight experts selected in one layer: after a token arrives, the system must compute all eight. Moving a missing expert's full weights to the GPU incurs PCIe transfer waits; computing it directly on the CPU can instead leave the GPU waiting for slower computation. RapidMoE changes this division of work. [§1–2 and Table 2](https://arxiv.org/html/2610.01265v1)

### Keep all eight experts, but do not necessarily give them equal precision

The eight routing weights are generally unequal. The paper observes that preserving precision matters more for some expert contributions, while others tolerate stronger compression. Quantization represents weights with fewer bits, reducing storage and data reads at the cost of approximation error. RapidMoE retains the low-precision computation of the less important experts rather than simply removing them.

In the teaching example, suppose two experts need higher precision and the other six use only low-precision weights. The GPU handles the compressed base that fits in its memory, while the CPU supplies additional work for important experts. This two-versus-six split illustrates execution; it is not a fixed setting throughout the model. The important set changes with input, layer, and inference phase. Routing weights guide selection but are not strict guarantees about an individual expert's error. [§3–4.2](https://arxiv.org/html/2610.01265v1)

In notation, k is the number selected by the router and r is the number receiving extra precision. Here k=8 and r=2; the remaining k−r=6 experts still contribute to the weighted output. Unlike pruning that skips those six, this execution avoids their extra precision-correction computation and weight reads while accepting low-precision approximation; their residuals can remain in CPU memory for later use.

### How a residual restores some precision: a small worked example

For an original weight W, the system first produces a low-precision base Q, then quantizes the difference W−Q into a residual R. The higher-precision version uses Q+R; the lower-precision version uses Q alone. In a teaching example, 1.03 is coarsely represented as 1.00, and the remaining 0.03 is approximated as 0.02. Their sum, 1.02, is closer to the original than 1.00, but still has error.

If the input is x=2, the GPU's base multiplication gives 2.00 and the CPU's residual multiplication gives 0.04. Their sum is 2.04, whereas the original multiplication gives 2.06. Matrix multiplication follows the same linear identity, x(Q+R)=xQ+xR, allowing the two pieces to be computed separately and added. This explains why the full higher-precision matrix need not move to the GPU, and why residual correction does not restore the original floating-point result exactly.

The actual formats are not the decimal numbers in this example. The base averages 1.75 bits and the residual averages 2.5 bits, totaling 4.25 bits. Higher precision is relative to the base; it is still quantized. These average bit counts describe compressed representations, not an ordinary integer type with 1.75 bits per value. [Algorithm 3 and §5](https://arxiv.org/html/2610.01265v1)

### An expert is more than one multiplication: nonlinear operations determine where paths meet

A typical expert first applies gate and up projections to produce intermediate representations, then uses a nonlinear function and elementwise multiplication, and finally maps the result back through a down projection. Here gate names a projection inside an expert, not the router that selects experts. The gate/up matrix multiplications can be split into base and residual pieces. The complete expert cannot generally be replaced by two independent networks whose final outputs are added, because the intervening nonlinear operations do not distribute that way.

RapidMoE first computes the gate/up bases of the two important experts on the GPU and transfers those intermediate results to the CPU. The CPU computes their residual contributions, combines the results, and performs the nonlinear operations and higher-precision down projection. Meanwhile, the GPU fully executes the other six low-precision experts. The two sides then combine their outputs. Thus, saying that the CPU only computes residuals omits its work on the important experts' later operations.

To avoid repeated transfers between devices, the paper applies residual splitting only to gate/up; down retains both high- and low-precision versions. It therefore reduces redundant storage without removing every duplicate weight representation or eliminating synchronization. Savings come from transferring intermediate results, reducing CPU work, and overlapping CPU and GPU execution. [Figure 9 and §4.4–4.5](https://arxiv.org/html/2610.01265v1)

### Why not always correct exactly two experts per layer?

A fixed number misses three differences: inputs depend on different experts, layers have different sensitivity to quantization error, and processing the prompt differs from generating subsequent tokens. The paper calls prompt processing prefill and token-by-token generation decode. The attention cache produced during prefill will be reused during later generation.

The system measures layer sensitivity offline, then calculates a threshold for each layer and phase: a global base multiplied by a layer coefficient and a phase coefficient. A selected expert receives extra precision when its routing score meets that threshold. The authors call this UMIA, a selection mechanism using several levels of information. More sensitive layers receive lower thresholds, making higher-precision execution easier to retain. The decode phase coefficient exceeds one, raising the threshold and typically retaining fewer experts than prefill.

This does not require an expensive search for every request. At deployment, previously calibrated parameters and current scores determine the selection. For prefill and batched decoding, the paper averages routing scores across tokens before selecting the important set. Batch composition can therefore change which experts receive additional precision. It should not be understood as an independent, exactly optimal precision budget for every token. [§4.3 and §5](https://arxiv.org/html/2610.01265v1)

### Does correcting one fewer expert necessarily make execution faster?

Not necessarily. If the CPU remains the slower side, reducing its work can reduce the wait. If the GPU is already slower, further reductions in CPU work may barely change total time. The approximation “total time ≈ synchronization time + max(CPU time, GPU time)” helps explain this. It is a useful bottleneck model, not an upper bound on every request's latency.

The paper first profiles the hardware, then searches for precision configurations meeting estimated latency targets while measuring changes in the output distribution. It uses KL divergence, which measures how two probability distributions differ and is not itself task accuracy. The default calibration uses 16 WikiText-2 prompts. For a 671B model, the authors report approximately 30 minutes for layer-sensitivity profiling and five hours for configuration search. Training-free does not mean deployment requires no preparation. [§4.2–4.3](https://arxiv.org/html/2610.01265v1)

Calibration also defines the scope of the result. The latency model comes from particular hardware measurements and the quantization assessment from a small text sample. Both may change with the CPU, GPU, or workload. A deployment therefore needs to recheck quality and timing rather than treat one calibrated configuration as an optimal solution for every request.

### What memory is saved, and how much CPU memory is still needed?

The strongest operating regime keeps the entire low-precision base on GPUs. Important experts' gate/up residuals and higher-precision down weights remain in CPU memory for selective execution. For DeepSeek-V3, Table 10 reports 149 GB peak GPU memory and 240 GB peak CPU memory for RapidMoE, versus 150 GB and 385 GB for KTransformers in the same configuration. The main saving is redundant CPU-side weights; the entire machine's requirement has not fallen to 149 GB.

If the GPU cannot hold every base weight, the system caches a subset. Cache hits use the division of work described above; misses fall back to CPU execution of the corresponding expert. The paper tests this fallback by limiting coverage to 25%–100% of the base and explicitly identifies full residency as its best regime. It does not establish the same speedup on arbitrarily small GPUs. [§5, Table 10, and §6.4.3](https://arxiv.org/html/2610.01265v1)

The residual has not disappeared: the CPU must read it from memory and compute with it. Low-concurrency generation processes only a few tokens at a time, making weight reads important. Moving part of the reads and computation to the GPU can shorten the CPU's critical path. Once the CPU cannot keep up with more simultaneous requests, further GPU throughput alone does not automatically remove the wait.

### Read throughput with the model, hardware, and batch size attached

The main configuration runs DeepSeek-R1/V3 on two A800 80GB GPUs and Qwen3-235B on one A800 80GB, with the paper-listed Xeon Gold 6326 CPU configuration (64 cores), 512 GB of DDR4 memory, and PCIe 4.0. A separate R1 configuration uses seven RTX 4090 GPUs, not a single consumer card. Multiple GPUs receive different model layers; this is not a cross-node experiment distributing one layer's experts and exchanging tokens through all-to-all communication.

Table 8 reports R1 results under its 1K sequence-length setting. Single-request decode throughput is 21.8 tokens/s for RapidMoE versus 8.0 for KTransformers. At batch size four, the values are 43.6 versus 10.5 tokens/s. The latter is aggregate batch throughput, not 43.6 tokens/s for each user. Prefill in the same table is 150.2 versus 62.8 tokens/s. The abstract's speedup does not replace these workload conditions.

Baselines include KTransformers, HybriMoE, MoE-APEX, and llama.cpp. The authors align comparable memory budgets and use the same matrix-operation kernels for matching quantization formats, although the full-model precision policies still differ. The demonstrated gain is for these hybrid deployment configurations; it does not establish superiority to a fully GPU-resident serving system with sufficient memory. [Tables 3–4/8 and §6.1](https://arxiv.org/html/2610.01265v1)

### Beyond speed: similar accuracy does not mean identical results

Table 5 compares accuracy with a Q4_K_M quantized model, not the original BF16 model. MMLU-Pro is evaluated on a random sample of 1,000 questions. At batch size one, R1 scores 83.8 versus 83.9 on MMLU-Pro, 96.2 versus 95.6 on MATH-500, and 73.3 for both on AIME-24. This supports similar quality on the tested tasks. The small changes lack cross-seed evidence sufficient to establish an advantage, and do not imply identical token outputs.

The serving experiment also measures user waiting time. Time to first token is TTFT; average time per output token is TPOT. For R1, the workload contains 1,000 ShareGPT requests, averaging 715 input tokens with output capped at 512, a concurrency limit of four, and an arrival rate of 0.2 requests/s. The fraction meeting both TTFT ≤ 5 seconds and TPOT ≤ 100 milliseconds is 87.4%.

In that configuration, the 99th-percentile TTFT is 6.21 seconds and TPOT is 101 milliseconds, both above the targets. The system improves low-concurrency serving without making every request meet its SLO. Increasing the batch can improve aggregate throughput while increasing individual waits; throughput alone cannot establish better tail latency. [Tables 5/9 and §7](https://arxiv.org/html/2610.01265v1)

### The useful lesson is how to divide the work, not a fixed precision recipe

Start a close reading by tracing an important expert through Figure 9: which matrices reside on each side, when intermediate results move, and what the CPU still computes afterward. Then read Figure 8 and §4.3 to understand why precision selection must account for the slower side. Finally, evaluate deployment value using Table 8's throughput, Table 9's request latency, and Table 10's machine-wide memory together.

A useful systems question is whether a large representation can be divided into a frequently used base and selective additions, followed by checking whether its computation can also be split and where nonlinear operations force the paths to meet. This is an inference from the mechanism, not a claim that every model layer supports it. Faster GPUs, slower CPUs, or different bandwidth can move the bottleneck, requiring the precision configuration and achievable gains to be revalidated.

## Optional reading · Stepped MoE: Segment-Level Routing with Configurable Inference Complexity

**Year / publication：** 2026 · arXiv 2026 · Apple · v1 2026-10-05 · [Original source](<https://arxiv.org/abs/2610.07348v1>)

**Reading guidance：** Worth selective close reading: Figure 2 and Sections 2.3–2.5, followed by Table 1 and Appendices A.6/A.7. Section 3.4 uses an NPU simulator, not an end-to-end phone measurement.

### What if the experts stay fixed while a sentence is being written?

Suppose a device can hold only some experts in memory. Token-level routing may select different experts after a single generated token, requiring another read from storage. Stepped MoE takes an intermediate approach: reuse one expert selection over a segment, then refresh it. Some token-level flexibility is traded for longer weight reuse. When the whole model already fits in memory, this transfer benefit need not apply.

This technical paper was released by Arnav Kundu and colleagues at Apple on October 5, 2026. This explanatory adaptation and review uses the CC BY 4.0 v1. It proposes an architecture that must be trained; enabling a switch on an arbitrary existing MoE does not establish the same behavior. [Paper and license](https://arxiv.org/abs/2610.07348v1)

### Read the context, then select experts for all later layers

The reported model has 56 layers: 12 dense layers that always execute, followed by 44 expert layers. The early layers process the input, and a selector produces masks for all subsequent expert layers. A mask is a list of experts to enable at a layer. Once those lists are available, later weights can be loaded early rather than waiting for each layer's routing decision.

For response generation, the first selection uses the representation of the last prompt token, remains valid for S generation steps, and then refreshes by segment. Within a segment, expert outputs are not combined with ordinary per-token routing weights. S specifies how long to reuse experts, not how many to select; these control different costs. During pretraining, the first position of each segment supplies the selection representation, without looking ahead at later content. [Sections 2.3–2.5](https://arxiv.org/html/2610.07348v1#S2.SS3)

### How can one checkpoint support active sizes from 1B to 4B?

Total parameters count the weights stored in the model; active parameters count those used in a computation. The main experiments store a model with approximately 12B total parameters and support approximately 1B, 2B, 3B, and 4B active settings. Larger budgets allow more experts to be selected. A learned vector representing the requested budget is added to the input, telling the model which capacity setting it should use.

For example, an application could choose a smaller setting when memory is tight and a larger one when resources permit. This is a deployment use of the architecture, not a measured phone experience in the paper. The full 12B storage requirement remains, and runtime memory also needs context caches and intermediate values. A 1B active setting therefore does not mean the entire device needs to store only 1B parameters.

### The ability to change budgets is learned during training

Training replicates each batch across four budgets so that shared weights adapt to each capacity. The main pretraining experiments use 1T text tokens, an 8192-token context, and fourfold batch replication. This is not the compute cost of training a single ordinary small model. Parameters used mainly by larger settings receive fewer updates; the authors compensate through budget-dependent loss weighting and the capacity embedding.

Loss weighting is a practical approximation, not claimed to be equivalent to separate expert learning rates. Appendix A.6 provides another experiment with two budgets: the shared model's estimated training FLOPs match the combined budget of two independent baselines, not each individual baseline. In that setting, independently trained Static S-MoE models outperform the flexible model on all four reported metrics. Convenient multi-budget deployment does not guarantee cheaper training or better accuracy at every setting. [Section 2.4 and Appendix A.6](https://arxiv.org/html/2610.07348v1#A1.SS6)

### Quality falls between dense models and token-level routing

In Table 1's pretraining evaluation, Flexible S-MoE trained and evaluated at S=32 with 3B active parameters scores 62.27% on five-shot MMLU, versus 57.8% for Dense 3B and 66.2% for token-routed Vanilla MoE. The latter also has 3B active and 12B total parameters. Eight-shot GSM8K accuracy is 48.0%, 34.5%, and 52.8%, respectively. These results illustrate the tradeoff: access to many candidate experts helps, while restricting how often they change gives up some flexibility.

This is not a win on every task. At the 1B setting, the zero-shot Core-En composite is 64.0%, below Dense 1B's 66.2%; it combines language understanding, commonsense, and science tasks. These comparisons also do not eliminate differences in multi-budget training investment and should be read alongside the budget comparison above. [Table 1 and Section 3.1](https://arxiv.org/html/2610.07348v1#S3.SS1)

### Less swapping can help, but the latency evidence is simulated

Section 3.4 uses an NPU simulator with matrix-multiplication latencies and NAND-to-DRAM transfer times, and considers different expert cache hit rates. The reported segment-routing latency approaches dense baselines. This supports the motivation for reducing swaps, but is not an end-to-end measurement on an identified iPhone and does not establish comparable gains for high-concurrency datacenter GPU serving.

Appendix A.7 instead uses a different checkpoint with 12B total and 3B active parameters, trained with S=16, and changes inference S to 16, 32, and 64. MMLU scores are 65.3%, 65.4%, and 65.0%; GSM8K scores are 51.3%, 50.8%, and 48.9%. Longer reuse therefore does not immediately hurt every task, but does carry quality risk. This table reports quality only; it should not be paired with invented matching latency measurements. [Section 3.4 and Table 9](https://arxiv.org/html/2610.07348v1#A1.SS7)

### Compared with RapidMoE, what part of the design may change?

RapidMoE targets existing models and primarily changes the representation precision and CPU/GPU execution of selected experts. Stepped MoE puts expert refresh frequency and active capacity into the architecture and training process. The former requires checking approximate-computation quality; the latter requires evaluating new training costs and routing restrictions. This is an analytical comparison between the papers, not a speed contest conducted by their authors.

Start by drawing two generation segments: select experts at a boundary, reuse them within the segment, then refresh. Read Figure 2 and Sections 2.3–2.5 before Table 1 and Appendices A.6/A.7. The useful distinction is among four quantities: total storage, currently active capacity, expert refresh frequency, and actual data-transfer cost. Any one of these alone is insufficient to judge a deployment.

## Optional reading · Semantic Parallelism: Redefining Efficient MoE Inference via Model-Data Co-Scheduling

**Year / publication：** 2026 · ICLR 2026 · arXiv v5, February 2026; first posted March 2025 · [Original source](<https://proceedings.iclr.cc/paper_files/paper/2026/hash/f0552f14388d95b19740dee809f5cad1-Abstract-Conference.html>)

**Reading guidance：** Read Figures 2–3 and §3.3 closely, then use Table 2 to distinguish first-token latency from complete-response latency. Appendix C.1 checks whether scheduling patterns learned from old data transfer to new requests.

### 1. The right experts were selected—why is a remote trip still necessary?

Consider a teaching example: one device holds experts A and C, while another holds B and D. A token needing A and B requires intermediate data to cross devices. Placing frequently co-used experts A and B together, and preferentially sending requests likely to need them to that device, can reduce transfers. Experts here are computational subnetworks inside the model; the router selects which ones a token uses. [§2 and Figure 3](https://arxiv.org/html/2503.04398v5)

Sem-MoE optimizes expert placement together with input scheduling. The Huawei and Sun Yat-Sen University work first appeared in 2025, reached version 5 in February 2026, and is officially published at ICLR 2026. Its value today is explaining how to reduce MoE communication, rather than being a newly released proposal. [Publication history](https://arxiv.org/abs/2503.04398), [official proceedings](https://proceedings.iclr.cc/paper_files/paper/2026/hash/f0552f14388d95b19740dee809f5cad1-Abstract-Conference.html).

### 2. Use historical inputs to find experts that often work together

The authors first run a collection of inputs and record which experts each token commonly activates at each layer, producing lookup tables. Actual routing still depends on context, but some tokens have stable tendencies that help predict the best device on which to start their computation. This provides statistical scheduling hints; token identity does not precisely replace the router. [§3.2](https://arxiv.org/html/2503.04398v5)

An offline algorithm alternates between adjusting input groups and expert groups. It seeks to place related inputs and experts together, avoid concentrating work on a few devices, and keep the expert count equal across groups. The alternating optimization is approximate, without a guarantee of a globally optimal solution. Deployment reorders experts and their corresponding router indices according to the result; it does not retrain the language model. [§3.3 and Appendix B](https://arxiv.org/html/2503.04398v5)

### 3. Attention-DP: send an entire request to a better device

When each device holds a complete attention module and handles different requests independently, attention uses data parallelism, or DP. The subsequent experts remain distributed across devices: expert parallelism, or EP. Sem-MoE aggregates the statistical tendencies of a request's tokens and favors the device more likely to host the required experts, instead of simply assigning requests in rotation. [§3.1 and §3.3](https://arxiv.org/html/2503.04398v5)

Sending every similar request to one device would create another problem. After assigning a device, the algorithm temporarily masks it; the mask resets only after every device has received a request in that round. This balances request counts while considering affinity. Equal request counts do not guarantee equal computation time for requests of different lengths, an important condition when applying the scheme to a real service. [Appendix B, Algorithm 2](https://arxiv.org/html/2503.04398v5)

### 4. Attention-TP: rearrange tokens during communication already required

When attention computation itself is split across several devices, it uses tensor parallelism, or TP. Selecting one device to receive an entire request cannot solve the problem. The partial results produced by different devices already need to be combined. Sem-MoE combines that reduction with distribution, aiming to leave a token's completed result on a device holding relevant experts. [§3.1 and §3.4](https://arxiv.org/html/2503.04398v5)

Its shuffled reduce-scatter combines partial results and distributes them across devices. After MoE computation, allgather collects the results and the original token order is restored. Prediction uses both historical token statistics and expert-device choices at preceding layers. The actual router still determines which experts execute. A wrong prediction mainly loses an opportunity to avoid transfers; it does not force the token through a different expert. [§3.3–3.4 and Appendix B.2, Algorithm 3](https://arxiv.org/html/2503.04398v5)

### 5. A faster first token need not mean an equally faster complete answer

Experiments use one server with eight accelerators, 96GB HBM per device, and interconnect bandwidth exceeding 400GB/s. The specific device model is not named. The main models are DeepSeek-V2-Lite and Qwen3-30B-A3B, compared against SGLang and MoETuner integrated into the same framework. Inputs come from MMLU, LMSYS, and ShareGPT; 20% of each dataset builds the prediction and placement tables, while the remaining 80% supplies sampled evaluation requests. [§4.1–4.3](https://arxiv.org/html/2503.04398v5)

One concrete Table 2 configuration uses Qwen3-30B-A3B, Attention-TP, one request per second, and 512 input tokens; output length is fixed but its value is not given in the table. SGLang's p99 time to first token is 104.76ms, versus 83.87ms for Sem-MoE. Median complete-response latency moves from 766.80ms to 759.16ms. The p99 is a latency threshold approximately 99% of requests do not exceed. These metrics change by very different amounts, so the first-token improvement should not be presented as an equivalent speedup for the whole generated answer. [§4.4 and Table 2](https://arxiv.org/html/2503.04398v5)

### 6. Do old statistical patterns still help with new requests?

The authors separately test transfer between datasets. With DeepSeek-V2-Lite, tables built using ShareGPT yield a 41.25% local activation rate on LMSYS inputs, compared with 25.01% for SGLang. This measures how much expert computation can stay on the input's device. It is neither answer accuracy nor a direct throughput improvement. It supports some transfer of the learned statistics, without showing that arbitrary new applications behave similarly. [Appendix C.1 and Table 3](https://arxiv.org/html/2503.04398v5)

The main performance tests fix input and output lengths and use one server with fast interconnects. Applying the method to variable-length requests, changing traffic, or multiple servers requires reassessing prediction, queueing, and communication costs. Alongside today's main paper on reducing weight movement through CPU/GPU computation, this work raises another question: can we first reduce how often data must visit remote experts? This is a design option to compare, not a guarantee of superiority for every deployment. [§4.1 and §4.3](https://arxiv.org/html/2503.04398v5)

### 7. Reading route and attribution

Start by tracing which tokens cross between the two devices in Figure 3, then read §3.3's two scheduling variants. On a second pass, inspect device masking in Algorithm 2 and order restoration in Algorithm 3 to understand how scheduling preserves the intended computation. Finish with Table 2 and Appendix C.1, assessing measured latency separately from transfer of the statistical patterns. Solving the full optimization formulation can wait. [Full text and appendices](https://arxiv.org/html/2503.04398v5)
