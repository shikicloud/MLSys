# Making Attention Faster: Less Waiting, Lower Precision, and Better Work Assignment

The main reading is the 2026 FlashAttention-4 paper: as Blackwell matrix multiplication accelerates, why do softmax, data movement, and thread coordination become bottlenecks? SageAttention3 examines the speed–error tradeoffs of FP4 inference and INT8 training. FlashInfer connects efficient kernels to variable-length requests, shared prefixes, and CUDA Graphs. Together they explain computation flow, numerical precision, and workload assignment. Start with the main paper’s example and read the companions as needed. Performance numbers retain their experimental conditions; kernel speedup does not imply equal serving speedup.

Each digest recommends 1 main paper and 2–4 optional papers across LLM inference, RL infrastructure, post-training, RSI (recursive self-improvement), reasoning compute, agent learning and memory, data and evaluation, and model architecture. Explore foundations and current research by theme; a direct connection to current work is not required. A recommendation does not mean it has been read, and there is no need to finish everything in one day.

## Main reading · FlashAttention-4: Algorithm and Kernel Pipelining Co-Design for Asymmetric Hardware Scaling

**Year / publication：** 2026 · MLSys 2026 · arXiv v1, 2026-03-05 · [Original source](<https://arxiv.org/abs/2603.05451v1>)

**Reading guidance：** Worth close reading. Follow one 128×128 tile through Figure 1 and Tables 1–2, then study backward cooperation in Figure 3 and check baseline versions and ablation settings.

### Start with one attention computation: finishing the matmul is not the end

Consider an input whose attention heads have dimension 128. Multiplying 128 query vectors Q by 128 key vectors K produces a 128×128 score tile S. Row-wise softmax turns these scores into weights, which then weight the value vectors V. Softmax subtracts a shared reference value, evaluates exponentials, sums them, and normalizes. Attention therefore links two matrix multiplications with a substantial amount of non-matmul work between them. We will use this tile example throughout the explanation. [§2.1](https://arxiv.org/html/2603.05451v1#S2.SS1)

The FlashAttention family avoids writing the entire sequence-length-squared score matrix to device memory. Instead, it processes K and V in blocks while retaining statistics and accumulated outputs. FA4 still computes this dense attention; it does not reduce the task by dropping supposedly unimportant tokens. Its question is whether the remaining operations can keep up once matrix multiplication becomes much faster on Blackwell. [§1 and §3.1](https://arxiv.org/html/2603.05451v1#S3.SS1)

### Hardware does not accelerate uniformly: exponentials and on-chip transfers become constraints

Tensor Cores specialize in matrix multiply-accumulate. MUFU handles special functions such as exponentials. Shared memory is a small on-chip storage area shared by a thread block. The paper compares resources per SM per clock: from Hopper to B200, BF16 matrix throughput grows from 4096 to 8192 operations, while exponential throughput remains 16 operations and shared-memory reads remain 128 bytes. An SM is a GPU resource group that executes thread blocks. Doubling matrix throughput does not automatically double every intermediate step. [§2.2](https://arxiv.org/html/2603.05451v1#S2.SS2)

For our 128×128 tile with head dimension 128, Table 1 estimates 1024 cycles for the two matmuls, 1024 for exponentials, and 768 for shared-memory reads. These are simplified resource estimates, not measured total latency; they should not simply be added because different units can overlap. The point is that even near-peak matmul execution can leave the overall pipeline waiting on exponentials. Optimization must therefore reduce waiting and redistribute work away from constrained resources. [§3.1.1 and Table 1](https://arxiv.org/html/2603.05451v1#S3.SS1.SSS1)

### The forward pipeline: use two query tiles to interleave matmul and softmax

FA4 assigns two Q tiles, each containing 128 queries, to one thread block. While one tile undergoes softmax, the other can advance its matrix operations: a ping-pong schedule. Blackwell writes matmul results asynchronously into TMEM, on-chip storage dedicated to Tensor Core operations, rather than keeping accumulators in thread registers. Two 128-thread warpgroups handle the two softmax tiles, with one thread processing an entire row. They explicitly stagger their exponential critical sections to avoid contending for the same exponential units. [§3.1.2 and Figure 1](https://arxiv.org/html/2603.05451v1#S3.SS1.SSS2)

A separate warpgroup corrects accumulated-output scaling, removing that work from the softmax critical path. P is also stored into TMEM in stages: its first three quarters are stored and corresponding matmuls launched before the final quarter is stored, reducing simultaneous temporary-register needs. The conference appendix provides an ablation: on B200, noncausal attention with 16 heads, dimension 128, length 16384, and batch 2 takes 2.817 ms in the default forward kernel versus 4.234 ms with only one Q stage. This is a kernel comparison, not a whole-model speedup. [Conference Appendix B, Tables 5 and 7](https://proceedings.mlsys.org/paper_files/paper/2026/file/ae8b0b5838ba510daff1198474e7b984-Paper-Conference.pdf)

### Share exponential work: approximate only a fraction of the elements

Exponentials can be evaluated in base 2. FA4 decomposes 2 to the power x into a power of two for the integer part times a power of two for the fractional part in [0,1). The former uses floating-point bit representation; the latter uses a polynomial approximation. Some exponential work can consequently run on ordinary multiply-add units alongside hardware exponential instructions. The paper applies this to only about 10%–25% of each row, leaving the rest to MUFU. Emulating everything would increase register pressure and latency. [§3.1.3](https://arxiv.org/html/2603.05451v1#S3.SS1.SSS3)

This introduces numerical approximation. Table 2 tests four million random inputs in [0,1) against FP64. A degree-3 polynomial has maximum FP32 relative error about 8.77×10⁻⁵ versus 1.41×10⁻⁷ for hardware exponentiation. After rounding to BF16, the corresponding maximum relative errors are approximately 3.90×10⁻³ and 3.89×10⁻³. BF16 rounding dominates in this test. That does not imply bitwise-identical outputs or comprehensive validation over long training runs, arbitrary input distributions, or final model quality. [Table 2](https://arxiv.org/html/2603.05451v1#S3.SS1.SSS3)

### Avoid repeated rescaling: a shared reference still permits correct combination

To understand conditional rescaling, take just four scores from one row and divide them into two blocks. This is a teaching example with scores already expressed in base-2 units. The first block [10,9], centered at 10, gives exponential weights [1,0.5]; the second block is [11,8]. Standard online softmax raises the reference to 11, multiplies previous accumulations by 0.5, and adds new weights [1,0.125]. FA4 can temporarily retain reference 10 and add [2,0.25] instead. If the weighted output and denominator use the same reference, the final ratio is unchanged: the two weight systems differ only by a common factor of two. [§3.1.4](https://arxiv.org/html/2603.05451v1#S3.SS1.SSS4)

The paper updates the reference only when the newly encountered maximum exceeds the old reference by more than a threshold; in base-2 units, the typical threshold of 8 corresponds to a scaling range of 256. Skipping a correction does not mean forgetting a required multiplier: the reference itself remains unchanged, and numerator and denominator continue accumulating consistently. This algebraic transformation is equivalent in real arithmetic. Floating-point execution still has range and rounding limits, so final normalization cannot be said to remove all numerical errors. Rescaling decisions are made collectively within a warp, a group of 32 threads, to avoid divergent branches.

### Backward has a different bottleneck: reduce transfers of intermediate results

During training, after producing output O, backward computes the loss gradients with respect to Q, K, and V, denoted dQ, dK, and dV. These describe how small changes in their components affect the loss. Because FlashAttention does not retain the entire attention-weight matrix, backward recomputes S and performs matmuls for dP, dV, dQ, and dK, totaling five. For the 1-CTA setting with 128×128 tiles and dimension 128, the paper estimates 2560 cycles of matmul work versus 3328 cycles of shared-memory traffic. Moving intermediate data is now more urgent than exponentials alone. [§2.1, §3.2.1, and Table 3](https://arxiv.org/html/2603.05451v1#S3.SS2)

FA4 keeps more intermediates in TMEM and interleaves the preceding iteration’s dQ and dK matmuls with current elementwise work. Space remains limited: TMEM cannot hold five 128×128 FP32 accumulator tiles. The schedule must determine when each region can be reused; for example, storage for S can later hold P. The improvement comes from designing data placement, lifetimes, and computational dependencies together, rather than merely launching more concurrent tasks. [§3.2.2 and Figure 2](https://arxiv.org/html/2603.05451v1#S3.SS2.SSS2)

### Cooperate across two thread blocks to reduce duplicate reads and global accumulation

A CTA is a cooperating thread block. Blackwell’s 2-CTA mode lets two blocks in a cluster jointly execute a larger matmul, each staging half of operand B and retaining its own output slice. Backward dQ needs additional care: the two blocks initially hold contributions from different K segments, but each query row needs both. FA4 exchanges half of dS through distributed shared memory within the cluster, giving each block both segments for its assigned rows before multiplication and accumulation. The exchange has a cost; the benefits are fewer duplicate reads and half as many global dQ atomic reductions. [§3.2.3 and Figure 3](https://arxiv.org/html/2603.05451v1#S3.SS2.SSS3)

Atomic accumulation prevents lost updates from concurrent blocks, but arrival order can vary, affecting floating-point sums. FA4 separately offers deterministic backward: blocks acquire a semaphore in a predefined order, accumulate, and hand off to the next block. This introduces synchronization and waiting costs. It addresses inter-block reduction order here; it does not automatically guarantee bitwise equality after changing batch shapes, or zero mismatch across an entire training-and-inference system. [§3.2.4](https://arxiv.org/html/2603.05451v1#S3.SS2.SSS4)

### Scheduling must consider work duration and cache reuse together

With causal attention, early queries see little history while later queries process more K and V blocks. Dispatching from shortest to longest can leave most compute units finished while only a few handle the longest remaining jobs. FA4 prioritizes longer work tiles while grouping heads so that reusable K and V data can remain in L2 cache. It does not blindly sort all work by duration regardless of locality. Variable-length inputs can likewise use a reordered index to change execution order without changing the requested outputs. [§3.3](https://arxiv.org/html/2603.05451v1#S3.SS3)

This differs from the special ordering used for deterministic backward, which must also satisfy accumulation-lock dependencies. For causal backward, the paper develops a shortest-processing-time-first arrangement that avoids waiting on the first write. The systems lesson is that a good order depends on duration, reused data, and dependencies; neither the LPT nor SPT label is a universal policy. These are work-tile schedules within an attention kernel, not full serving-system request scheduling. [§3.2.4 and §3.3](https://arxiv.org/html/2603.05451v1#S3.SS2.SSS4)

### Interpreting the benchmarks requires a GPU, shape, precision, and baseline version

The main text evaluates B200 with BF16 inputs, sequence lengths from 1K to 32K, and batch sizes adjusted to keep total tokens at 32K, with and without causal masks, averaging ten measurements after five warmup runs. Figure 4 uses dimension 128 and 16 heads. The paper reports forward speedups of roughly 1.1–1.3× over cuDNN 9.13 and 2.1–2.7× over Triton, reaching 1613 TFLOPs/s, about 71% of the stated theoretical peak. This is attention-kernel throughput calculated from matmul work, not model tokens per second. The appendix identifies Triton 3.6, and FA3 is not a baseline that runs directly on B200. [§5, Figure 4, and Appendix A.1](https://arxiv.org/html/2603.05451v1#S5)

A necessary caveat is that this same paper includes cuDNN 9.19.1.2 and explains that newer versions incorporated related techniques and achieve similar performance. Maximum gains over an older release do not imply the same benefit from changing libraries today. Long-sequence forward/backward kernel results also cannot be directly converted into single-token decode latency or agent end-to-end gains. There is a version discrepancy in the hardware description: the arXiv appendix says B100 while its main text says B200; conference Appendix A.1 specifies B200 180GB SXM6 at 1000W, which this note uses to resolve the description. [Conference Appendix A.1](https://proceedings.mlsys.org/paper_files/paper/2026/file/ae8b0b5838ba510daff1198474e7b984-Paper-Conference.pdf)

## Optional reading · SageAttention3: Microscaling FP4 Attention for Inference and An Exploration of 8-Bit Training

**Year / publication：** 2025 · NeurIPS 2025 · Tsinghua University / Shengshu Technology · first preprint 2025-05-16; arXiv v3 2026-01-14 · [Original source](<https://arxiv.org/abs/2505.11594v3>)

**Reading guidance：** Worth an optional deep read. Start with Figure 2 and Algorithm 1, then the two-level scaling in §3.2. For training, continue with Algorithm 3, Figure 8, and Appendix A.6.

### Accelerating two matrix multiplications, not converting the whole model to FP4

Imagine one step of video generation: a small region of the current frame needs useful information from other positions. Attention first compares its query vector Q with other positions' key vectors K through dot products. Softmax converts those scores into nonnegative weights P that sum to one, and P then forms a weighted sum of value vectors V. The main computation is `S=QKᵀ`, `P=softmax(S)`, and `O=PV`. SageAttention3 targets the two matrix multiplications, using FP4, a floating-point format with four bits per value, which Blackwell GPUs can process quickly. [§2–3 and Figure 2](https://arxiv.org/html/2505.11594v3#S3)

The cost of fewer bits is a small set of representable values: original numbers must be rounded to nearby choices. The paper retains FlashAttention's tiled computation and online softmax to avoid writing the complete score matrix to GPU memory, but quantizes matrix-multiplication inputs and therefore permits approximation. Softmax, scaling, and accumulation are not all performed in FP4. This does not convert every model weight to FP4, nor is it a strategy for storing a persistent KV cache in four bits; the subject is the attention computation path. [§2, §3.1, and Algorithm 1](https://arxiv.org/html/2505.11594v3#S3.SS1)

### Why give every 16 values their own scale factor?

Consider an invented numerical situation: most values are near 0.1, but a much larger value appears elsewhere in the vector. With one shared scale for the entire vector, accommodating the large value can erase distinctions between small values through rounding. The paper chooses NVFP4: each group of 16 values shares an FP8 scale factor, while individual values are stored as FP4. Together, the value and scale approximate the original number. This microscaling confines an outlier's influence to a smaller group. NVFP4 uses E2M1 values and E4M3 scales, denoting the exponent and mantissa bit counts; it differs from MXFP4, which groups 32 values and uses a different scale format. Smaller groups help, but outliers within a group can still cause error. [§3.1 and Table 1(a)](https://arxiv.org/html/2505.11594v3#S3.SS1)

The authors also inherit Q/K smoothing from earlier work: remove shared offsets so the data entering quantization is more concentrated. Subtracting the same mean from every key subtracts one common constant from all scores for a given query; softmax is invariant to this in exact arithmetic. Subtracting a mean from a query block is different, because the removed component contributes differently to different keys. Its product with the keys must therefore be computed separately and added back, explaining Algorithm 1's correction term. Smoothing is not arbitrary deletion of large values, and it does not eliminate subsequent rounding error. [Algorithm 1 and Appendix A.7](https://arxiv.org/html/2505.11594v3)

### A subtler error: the scale factor itself may be inaccurate

The second multiplication faces a small-number problem. The implementation quantizes the temporary exponential values P̃ produced inside online softmax. They still undergo subsequent normalization and should not be confused with final probabilities P. Suppose a block's largest value is only 0.0006, an illustrative example invented here. Dividing by FP4's maximum value of 6 gives a scale of 0.0001. That scale must itself be stored in E4M3 FP8 and can round to zero. Even careful selection of FP4 values cannot recover the original small numbers when they are multiplied by an incorrect scale. [§3.2 and Figure 3](https://arxiv.org/html/2505.11594v3#S3.SS2)

Two-level scaling separates the issues. First compute an FP32 factor for each row, `a=rowmax(P̃)/(448×6)`, divide P̃ by a to enlarge its values, and then apply FP4 quantization in groups of 16. Here, 448 is the largest finite value of the FP8 scale format, and 6 is FP4's largest value. After matrix multiplication, multiply back by a and continue the online-softmax normalization. The higher-precision factor a preserves the overall magnitude of the small numbers, while FP8 scales describe local magnitudes after enlargement. This uses the available representation range more effectively; it does not make FP4 exact. The paper's scaling experiments measure the reduction in error. [Equation 5 and Algorithm 1](https://arxiv.org/html/2505.11594v3#S3.SS2)

### Faster Tensor Cores still require data-movement work and quality trade-offs

Hardware throughput does not automatically become complete-kernel throughput. Quantization needs local maxima and exchanges between threads, while the V layout required for the second multiplication creates transposition work. The paper combines some maximum reductions with online softmax and fuses V transposition into quantization. On an RTX 5090, Figures 4–5 compare attention kernels with head dimensions 128 and 64 across sequence lengths; the text reports approximately 4–5× speedup over FlashAttention2. That applies to these kernel tests, not a blanket 5× improvement for an entire model or single-token decoding. The comparator is the FlashAttention2 implementation used on this GPU in the paper, not FlashAttention3 measured on a different GPU. [§3.3, §5.2, Figures 4–5, and Appendix A.5](https://arxiv.org/html/2505.11594v3)

Quality also needs metric-by-metric inspection. Video generation is evaluated with Open-Sora prompt sets. In Table 2, HunyuanVideo's text-alignment metric improves slightly, but Flow-score, used to assess temporal consistency and marked higher-is-better, drops from 1.4793 with 16-bit attention to 1.232. Similar overall appearance therefore should not be described as unchanged performance on every metric. Appendix A.6 also observes accumulated cross-layer error in CogVideoX-2B and separately tests retaining the three layers with the greatest error growth in FP16. This mitigation suggests that precision choices may need to vary by layer; it does not establish that every main-table result used that same fallback. [Table 2 and Appendix A.3 and A.6](https://arxiv.org/html/2505.11594v3)

### Why does training use INT8 and retain one FP16 multiplication?

SageBwd is a separate design using INT8 integer quantization, not the FP4 inference kernel applied directly to training. Beyond computing outputs, training propagates gradients backward to determine which input changes increase or decrease the loss. The paper counts two forward and five backward matrix multiplications in attention. Six use INT8; `dP=dO·Vᵀ` remains in FP16. Here dO is the loss gradient with respect to the output, and dP is the gradient with respect to attention weights. This operation therefore determines how the model should adjust its allocation of attention across positions. [§4 and Algorithm 3](https://arxiv.org/html/2505.11594v3#S4)

It is protected because its errors propagate: dP affects the score gradient dS, which contributes to the Q and K gradients and can accumulate errors as the backward pass processes sequence tiles. The authors preserve this sensitive operation instead of uniformly reducing precision everywhere. In forward-plus-backward kernel tests on an RTX 4090 with head dimensions 64 and 128, SageBwd achieves up to approximately 1.67× speedup over FlashAttention2. This is not an equal speedup for a complete training step, nor does it mean that weights, optimizer states, and every gradient are stored in eight bits. [§4.2, §5.2, and Figures 6–7](https://arxiv.org/html/2505.11594v3#S4.SS2)

### Similar fine-tuning results do not establish reliable pretraining

The language experiments fine-tune and evaluate Qwen2.5 and Llama3.2 on mathematical QA with GSM8K, reading comprehension with DROP, knowledge questions with MMLU, and commonsense completion with HellaSwag. Appendix A.3 specifies 700 fine-tuning steps. Table 3 and the additional multi-seed experiments show broadly similar task scores for INT8 attention and BF16, with changes in both directions; this is not evidence of zero gradient error. A separate experiment trains a 400M-parameter Llama-style model from scratch on FineWeb-Edu, processing two million tokens per step. Figure 8 shows slower convergence with the eight-bit design. §5.3 separately studies 1,000 fine-tuning steps followed by FP4 inference; those settings must not be conflated with the 700-step experiments, and none establishes suitability for long-running RL. [§5.2–5.3, Figure 8, and Appendix A.3–A.4](https://arxiv.org/html/2505.11594v3)

Read Figure 2, Algorithm 1, and §3.2 first to separate the roles of quantized values and scale factors. Then read Algorithm 3 and Figure 8 to understand why inference error and training error are different questions, before checking the counterexamples in Table 2 and Appendix A.6. This is an explanatory adaptation and commentary; the labeled numerical examples are invented for explanation, not reported experiments.

## Optional reading · FlashInfer: Efficient and Customizable Attention Engine for LLM Inference Serving

**Year / publication：** 2025 · MLSys 2025 · arXiv v1 2025-01-02, v2 2025-04-21 · University of Washington / NVIDIA / CMU / Perplexity AI and collaborators · [Original source](<https://arxiv.org/abs/2501.01005v2>)

**Reading guidance：** Read Figures 2–3, Algorithm 1, and Figure 6; serving work also warrants close reading of evaluation and Appendix G.3.

### Start with serving: one batch does not mean equal work

Imagine a decoding step with three requests containing 1,000, 1,000, and 12,000 past tokens, each asking for one next token. This teaching example shows why assigning one work unit to each request can leave the first two units idle while the last still reads a long KV cache. Fast matrix multiplication inside each unit does not eliminate the straggler. The KV cache contains keys and values computed for earlier tokens, which attention reads during subsequent generation.

FlashInfer addresses this serving environment: lengths change continuously, KV data may occupy scattered pages, and candidate responses may share a prefix. It separates cache access, local computation, and work assignment so that they can be composed. These notes use the April 2025 v2 paper, an MLSys 2025 collaboration including the University of Washington, NVIDIA, CMU, and Perplexity AI. Its value here is connecting the other two papers’ kernel optimizations to real serving workloads. [Paper](https://arxiv.org/html/2501.01005v2); [proceedings](https://proceedings.mlsys.org/paper_files/paper/2025/hash/dbf02b21d77409a2db30e56866a8ab3a-Abstract-Conference.html)

### Finding the data: represent a page table as an access list

For each group of queries, list the KV page IDs it must read. A query is the vector with which a current token looks up relevant information; a page ID locates the stored historical data. FlashInfer represents this access list as a block-sparse matrix: rows correspond to query blocks, columns to cache blocks, and entries indicate accesses. Here, sparsity can simply describe which request accesses which physical pages. It does not automatically discard historical tokens the model should attend to. [§3.1.1, Figure 2](https://arxiv.org/html/2501.01005v2#S3.SS1)

The physical pages can be scattered, while matrix multiplication needs regular inputs. Kernels using Tensor Cores use the indices to gather the relevant KV data from device memory into on-chip shared memory before Tensor Core multiplication. Shared memory is temporary storage used cooperatively within a thread block. The paper also packs queries and outputs without padding every short request to the longest length. This saves unnecessary storage and accommodates different layouts, while retaining index-processing and irregular-transfer costs. A unified page-table representation does not remove those costs. [§3.1–3.2](https://arxiv.org/html/2501.01005v2#S3)

### Why split shared-prefix attention into separate computations?

Consider four candidate answers to one long prompt. Their prefix KV data are identical, while their generated suffixes differ. Storing the prefix once saves capacity, but four independent work units may still load it separately. The paper represents shared and private parts separately: the shared computation groups several queries into one block to reuse KV data loaded into shared memory, while private suffixes use their own indices. This decomposition primarily changes index arrays rather than relocating the full KV cache into a new physical layout. [§3.1.2, Figure 3](https://arxiv.org/html/2501.01005v2#S3.SS1)

The two outputs cannot simply be averaged, because their total attention weights can differ. Each part retains its output and the logarithm of its unnormalized weight sum, called log-sum-exp or LSE. Merging reweights the outputs by those totals. If one query assigns unnormalized weight sums of 9 and 1 to prefix and suffix, the final output weights their separate outputs by 0.9 and 0.1, rather than one half each. These numbers illustrate the equation only. Mathematically this composition preserves full softmax attention; finite-precision rounding can still differ. [§2.2, Equations 1–3](https://arxiv.org/html/2501.01005v2#S2.SS2)

### Split the long request so short work does not leave the GPU idle

Returning to the 1,000/1,000/12,000-token example, FlashInfer estimates work from query and KV lengths, splits long KV ranges into smaller tasks, and assigns them to GPU work units. The paper’s algorithm orders tasks by length and repeatedly assigns a task to the thread block with the lowest estimated load. Chunk size depends on the batch workload and number of thread blocks; requests are not simply split into an equal number of pieces. Several blocks can process a long request, followed by attention-state composition. [§3.3.1, Algorithm 1](https://arxiv.org/html/2501.01005v2#S3.SS3)

Balancing introduces intermediate outputs and a merge step. The interface separates plan from run: the CPU computes assignment metadata and copies it into a fixed GPU buffer, after which the GPU reads the plan and executes. Planning runs for each generation step, but layers with matching length configurations can reuse it within the step. Stable kernel launch sizes and buffer addresses permit CUDA Graph replay—a previously recorded GPU operation sequence—while metadata contents change with requests. CPU planning itself is outside the captured graph. [§3.3–3.4, Figure 6](https://arxiv.org/html/2501.01005v2#S3.SS3)

### Customizable kernels and the actual experimental comparison

Users can also specify query/key transformations, score transformations, and masks. The system inserts these into CUDA templates, compiling and caching kernels during initialization. This can fuse rotary positional encoding, or RoPE, into attention, avoiding separate launches and intermediate device-memory traffic. Customizability has defined interfaces and template boundaries; it does not mean that any Python program automatically becomes an optimal kernel. [§3.2.3, §4.3](https://arxiv.org/html/2501.01005v2#S3.SS2)

The paper evaluates FlashInfer v0.2. Its online-serving experiment integrates it into SGLang v0.3.4 and compares the same framework’s Triton v3.0 backend. Models are Llama 3.1 8B on one H100 and 70B on four H100s. Workloads include ShareGPT and synthetic requests with lengths uniformly distributed between 512 and 2,048 tokens; arrival rates are adjusted to keep P99 time to first token below 200 ms. Under these conditions, the authors report a 29%–69% reduction in inter-token latency. This online-serving experiment uses FP16, CUDA 12.4, and PyTorch 2.4.0. This is not a ranking of today’s framework versions and is not directly comparable with peak single-kernel throughput in the other readings. [§4.1, Figure 7](https://arxiv.org/html/2501.01005v2#S4.SS1)

### What to retain, and what the paper does not guarantee

The useful design principle is to inspect workload structure before executing computation. Without changing the model algorithm, runtime splitting and shared-data reuse can reduce waiting. Their CPU planning, metadata-copy, and result-merging costs still matter; limited prefix sharing or tiny workloads may not justify additional machinery. The paper avoids unordered atomic accumulation and produces a deterministic aggregation order for identical sequence-length information. This does not establish bitwise equality across different batches, hardware, or training and inference engines. That final distinction is our analysis of the guarantee’s scope, not a zero-mismatch claim by the paper. [§3.3.1, §4.4](https://arxiv.org/html/2501.01005v2#S3.SS3)

Reading route: start with Figures 2 and 3 and draw one shared prefix with two private suffixes; then trace one long request through splitting and merging in Algorithm 1 and Figure 6; finish with Figure 7 and the variable-length ablation in Appendix G.3. Prerequisites are softmax as conversion of scores into normalized weights, and a GPU thread block as a group of cooperating threads.
