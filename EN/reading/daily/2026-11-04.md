# Making Training Frameworks Easier for Agents to Modify—and Verify

The main reading, PithTrain, follows a MoBA attention integration task to explain how compact code, direct calls, and task procedures reduce agent debugging effort, and how the changes are checked. Event Tensor examines when a small GPU task can begin; KernelBench separates executable, correct, and genuinely faster code. Start with the main reading’s task example and acceptance rules, then explore the companions as needed. Framework modification cost, training throughput, and inference latency are treated separately.

Each digest recommends 1 main paper and 2–4 optional papers across LLM inference, RL infrastructure, post-training, RSI (recursive self-improvement), reasoning compute, agent learning and memory, data and evaluation, and model architecture. Explore foundations and current research by theme; a direct connection to current work is not required. A recommendation does not mean it has been read, and there is no need to finish everything in one day.

## Main reading · PithTrain: A Compact and Agent-Native MoE Training System

**Year / publication：** 2026 · arXiv 2026 · CMU / NVIDIA / Xlue · v1 2026-05-29 · [Original source](<https://arxiv.org/abs/2605.31463v1>)

**Reading guidance：** Worth close reading. Follow the MoBA integration through Sections 3 and 5.4, inspect Appendix B’s acceptance rules, then compare Tables 4, 7, and 8 to separate training throughput from agent effort.

**Why revisit：** Moving from a research overview to agent maintainability and evaluation: how training-framework design affects the cost of modifying, validating, and debugging code.

### A concrete task: ask an agent to integrate a new attention mechanism

Imagine giving a coding agent the MoBA paper and reference implementation, and asking it to replace a training model’s attention. MoBA partitions historical tokens into blocks, selects relevant blocks for each query, and computes attention over those blocks. The agent must locate model construction, connect forward and backward computation, write a training entry point, run it, and fix failures. PithTrain asks whether a framework can make such changes easier without substantially sacrificing training speed. This integration is an actual task in the paper. [Section 5.4 and Appendix B.3](https://arxiv.org/html/2605.31463v1#S5.SS4)

Here, agent-native means designing the framework around an existing coding agent’s reading, editing, and verification workflow. The experiments do not train that agent’s policy or let it autonomously choose research goals and recursively improve its own capabilities. Humans provide tasks, papers, reference implementations, and acceptance rules; the agent performs engineering within those conditions. This should not be labeled autonomous recursive self-improvement.

### Step 1: narrow the scope and make important calls locally traceable

The paper’s framework is approximately 11K lines across application, training-engine, and operator layers, with deliberately narrower model, feature, and hardware coverage. Each model lives in a self-contained file with direct module construction and calls. After locating attention construction, an agent can continue to the concrete class; a registry or distant runtime specification first requires resolving what a name actually refers to. Compactness and direct calls shorten those understanding paths rather than merely reducing file size. [Sections 3.1–3.2 and Figures 2–3](https://arxiv.org/html/2605.31463v1#S3.SS1)

There is a tradeoff: models need not share one abstraction, so some changes may have to be repeated. Python and Python-DSL components reduce language boundaries and expose readable tracebacks, while underlying GPU computation still depends on compilation and runtime libraries. The paper does not establish that shorter code is always better or that all plugin systems should disappear; it chooses a structure favorable to local modification.

### Step 2: retain the computation and communication schedule needed for performance

Compact code does not reduce distributed training to a single-GPU toy. PithTrain supports pipeline parallelism across model stages, expert parallelism across expert networks, data and context parallelism, checkpointing, and FP8. Its DualPipeV schedule decomposes each layer into five stages around expert-communication boundaries. Expert-token all-to-all runs on a separate communication stream, overlapping one microbatch’s forward computation with another’s backward computation. These are established optimization ideas rather than claimed inventions of the paper. [Section 3.2](https://arxiv.org/html/2605.31463v1#S3.SS2)

Transformer regions with stable full graphs use torch.compile(fullgraph=True), which rejects graph breaks instead of silently falling back to slower execution. MoE forward and backward paths are excluded because expert input sizes depend on routing. Other optimizations include delayed weight-gradient computation, fused operators, deduplicated expert communication, and an FP8 weight cache across microbatches to avoid repeated quantization. These show how agent maintainability and training efficiency can be designed together, with actual value still depending on hardware and configuration.

### Step 3: turn operational knowledge into a procedure with a verifiable result

Understanding code is not the same as knowing how to validate a change. The paper ships skills: on-demand procedure files for recurring tasks. A correctness procedure checks data, environment, and configuration, runs training before and after a change, and calls a script comparing loss curves to return PASS/FAIL. Other procedures cover Nsight Systems capture, adding models, and memory instrumentation. The important properties are a specific scope, explicit prerequisites, and checkable completion—not simply telling an agent to test carefully. [Section 3.3 and Figure 4](https://arxiv.org/html/2605.31463v1#S3.SS3)

Section 5.3 conducts a more controlled comparison on two procedures. The framework, agent, and harness stay fixed; each task runs three times with and without its skill, and disabled procedures are removed from both the working tree and git history. For correctness validation, median Agent Turns drop from 114 to 34, while GPU-active time does not decrease because both versions execute prescribed training checks. Procedures save rediscovery effort without removing necessary computation. The result concerns two specific tasks, not a universal benefit for every skill. [Table 8](https://arxiv.org/html/2605.31463v1#S5.SS3)

### ATE-Bench: keep the agent fixed and change the framework it operates

Agent-task efficiency, ATE, describes task-completion cost rather than one scalar score. The evaluation fixes Claude Code with Opus 4.7 at xhigh effort across PithTrain, Megatron-LM, and TorchTitan. Its 20 tasks comprise 12 code Q&A questions, four operate-and-profile tasks, and four new-feature tasks, each attempted independently three times and summarized by medians. Examples include tracing configuration propagation, recording per-token expert routes, and integrating architectures such as MoBA. All attempts eventually satisfy the requirements, so the central comparison is effort to complete the same work rather than higher success rates. [Sections 4–5.2](https://arxiv.org/html/2605.31463v1#S4)

Runtime and new-feature tasks share DeepSeek-V2-Lite on one eight-H100 node, PP=4 and EP=2—four pipeline stages and two-way expert parallelism—with DP=1, sequence length 2,048, global batch size 1,024, and BF16. Session duration, active GPU time, agent turns, per-turn context, and output tokens are reported separately. A long session may be spent reading code; additional GPU time may come from failed training reruns; output tokens do not directly equal monetary cost. Separating the metrics helps locate where effort changes. [Appendix B](https://arxiv.org/html/2605.31463v1#A2)

### Completion requires evidence, not the agent’s assertion

Q&A answers must cite files, functions, and lines. Two human graders independently open the locations; a third resolves disagreements using the evidence. Runtime tasks check real artifacts: a read-only smoke-training script must reach step five with finite loss; routing logs must cover specified layers and tokens with valid expert IDs and nonnegative, normalized weights; profiler summaries must match the Nsight report. Acceptance is based on inspectable results rather than confidence in the agent’s prose. [Appendices B.1–B.2](https://arxiv.org/html/2605.31463v1#A2.SS1)

New-feature tasks require 64 DCLM training steps with finite, decreasing cross-entropy loss, plus three task-specific architectural rules. For MoBA these cover partitioning K/V into blocks, query-dependent block selection, and attention over selected blocks with causal masking. An independent Opus 4.7 session first judges the diff against the rules, and a human checks each cited justification. This can reject some false successes where an unchanged model still lowers loss. It does not prove elementwise equivalence to the reference or cover every shape, edge case, and long-run training behavior. [Appendix B.3](https://arxiv.org/html/2605.31463v1#A2.SS3)

### Back to MoBA: which work actually becomes cheaper?

For MoBA integration in Table 7, median Active GPU Time is 27.7 minutes on PithTrain, 49.5 on Megatron-LM, and 77.9 on TorchTitan. Session durations are 38.7, 61.6, and 105.1 minutes. These results use the fixed agent and model configuration above, with three attempts each. GPU-active time is the paper’s reported metric; session duration additionally includes exploration and editing. They should not be conflated or directly interpreted as summed per-GPU time or an API bill. [Table 7](https://arxiv.org/html/2605.31463v1#S5.SS2)

Section 5.4 inspects debugging. Two PithTrain attempts finish without runtime failures; the third fixes a tensor-stride error within the same file. Megatron-LM encounters duplicate argument registration or BF16 overflow, with fixes spanning files. TorchTitan’s initial implementation encounters memory exhaustion and repeated edits. Both code structure and runtime memory headroom therefore matter. The MoBA behavior breakdown also excludes thinking tokens unavailable through the API, so reduced visible output does not establish a proportional reduction in all reasoning. The case study helps explain observations without isolating smaller code as the sole cause. [Section 5.4 and Figure 6](https://arxiv.org/html/2605.31463v1#S5.SS4)

### Does the smaller framework sacrifice MoE training performance?

Table 4 starts training from public checkpoints so routing is already trained. Parallelism, sequence length, and precision are matched across frameworks; each experiment runs 25 steps and uses the median time of the last ten to calculate aggregate tokens/s. For Qwen3-30B-A3B on 16 H100 GPUs with PP2/DP1/CP1/EP8, sequence length 2,048, and BF16, PithTrain reaches 124.9K tokens/s versus Megatron-LM’s 126.7K. Performance is close, with PithTrain slightly lower in this configuration. The five reported H100/B200 configurations do not establish superiority on arbitrary models and clusters. [Section 5.1 and Table 4](https://arxiv.org/html/2605.31463v1#S5.SS1)

Training correctness receives a separate check: Qwen3-30B-A3B is trained for 4,096 matched steps on 32 H100 GPUs using DCLM, BF16, sequence length 2,048, and global batch size 1,024, comparing loss trajectories and six downstream tasks. This is stronger evidence than a short smoke test, but remains limited to the tested model and configuration. ATE’s Train and Evaluate task has a different purpose: it trains from random initialization for only 25 steps, and a near-random HellaSwag score can pass because the task checks whether export and evaluation work, not model capability. [Appendices A and B.2](https://arxiv.org/html/2605.31463v1#A1)

### What is supported, and what should not yet be generalized?

The evidence supports a bounded claim: on the selected tasks, framework versions, and hardware, the same strong coding agent often completes PithTrain tasks with less effort while training throughput remains close to production baselines. It does not isolate the contribution of every design principle; only skills receive a dedicated on/off ablation. Multiple agents and all maintenance workloads are not tested. In particular, a shared change propagated across many models could benefit from common abstractions, and ATE-Bench excludes such tasks. [Sections 4 and 5.3](https://arxiv.org/html/2605.31463v1#S4)

A useful systems-research lesson is to specify required evidence before measuring edit cost. For MoE routing instrumentation, first define coverage over layers and tokens, valid expert IDs, and weight checks, then record time spent locating code, editing, verifying, and rerunning GPU jobs. This separates quickly producing a patch from quickly obtaining a trustworthy change. That is a research suggestion derived from the paper; long-term collaborative maintenance, open-ended research, and continuous improvement without human acceptance remain untested.

### Reading route and primary source

Start with Figures 1–3 and Section 3 to understand the four design choices, then follow MoBA debugging in Section 5.4. Read Appendix B.3 and decide which failures its three rules and 64-step run can catch. Finally compare Table 7’s agent costs, Table 8’s skill ablation, Table 4’s throughput, and Appendix A’s training correctness. The questions should remain separate: is the framework easy to modify, is the change adequately checked, and does training run efficiently? They do not collapse into a claim that the agent has become more capable.

The verified source is [PithTrain, arXiv:2605.31463v1, May 29, 2026](https://arxiv.org/html/2605.31463v1). ## Optional reading · Event Tensor: A Unified Abstraction for Compiling Dynamic Megakernel

**Year / publication：** 2026 · MLSys 2026 · CMU / NVIDIA and collaborators · first preprint 2026-04-14; v2 2026-04-21 · [Original source](<https://arxiv.org/abs/2604.13327v2>)

**Reading guidance：** Read Figure 3 and Section 2, then compare Figures 7 and 9 for static waiting versus dynamic task fetching. Finish with Tables 2–3 to determine when dynamic scheduling justifies its additional cost.

**Why revisit：** Moving from a research overview to execution mechanisms: how tasks declare dependencies, and how a compiler turns those dependencies into static or dynamic scheduling inside the GPU.

### Why wait when the next task’s inputs are already available?

Consider our tiled-sum teaching example. P0 and P1 produce the two partial sums needed for output tile C0; P2 and P3 serve a different output tile C1. If one kernel computes every P and a second kernel computes every C, C0 waits for P2 and P3 even after P0 and P1 finish. This wait comes from a coarse synchronization boundary rather than the mathematics. A tile is a small portion of a computation, while an SM is a GPU compute unit that executes such work. [Section 2.2 and Figure 3](https://arxiv.org/html/2604.13327v2#S2.SS2)

Event Tensor aims to start C0 as soon as its own two prerequisites are satisfied, overlapping it with unfinished P2 and P3. The compiler places tiled tasks from multiple operators into a long-running kernel that keeps obtaining work: a persistent megakernel. This reduces repeated CPU launches of small kernels and removes unnecessary waits across operators. Placing operations in one kernel is only a first step. If that kernel still requires every P to finish before any C starts, it has not exposed this fine-grained parallelism. [Section 1 and Figure 1](https://arxiv.org/html/2604.13327v2#S1)

### An event tensor records completion conditions, not model activations

Assign C0 an event E0 with an initial count of two. P0 notifies it on completion, reducing the count to one. P1 notifies it again, reducing the count to zero and indicating that C0’s inputs are ready. A multidimensional array of such events is an Event Tensor. The main novelty is not the counter itself, but making dependencies objects that the compiler can understand and transform: which events a task notifies and which events another task awaits. Dimensions can remain symbolic, such as batch size, allowing a compiled program to determine task ranges from runtime shapes without recompiling for every batch. [Sections 2.1–2.3](https://arxiv.org/html/2604.13327v2#S2)

Mixture-of-experts models, or MoE, also require dependencies to change with data. A router assigns different tokens to different experts, so compilation cannot know which inputs a particular expert will receive. Event Tensors let grouping tasks notify expert events according to the current routing results. Each event’s initial count depends on that expert’s token count, and the number of matrix-computation tiles it activates is determined at runtime. Routing is not bypassed: its results are computed first and then determine downstream events and tasks. The abstraction represents changing dependencies; it does not choose experts for the model. [Section 2.4 and Figure 5](https://arxiv.org/html/2604.13327v2#S2.SS4)

### Wait for the assigned task, or fetch another task that can run?

The same event relationships can compile into two execution strategies. Static scheduling assigns each SM a task queue in advance. If an SM finishes P0 but its next task C0 still awaits P1, it checks the event counter and waits. Dynamic scheduling lets that SM fetch another executable task from a GPU queue instead. Once E0 is satisfied, C0 joins the set of tasks that workers can obtain. This can reduce imbalance between waiting and busy SMs, but costs atomic operations for task acquisition, queue insertion, and shared-counter updates. [Sections 3.1–3.3 and Figures 7 and 9](https://arxiv.org/html/2604.13327v2#S3)

The main text explains the basic semantics using enqueue-after-completion. Appendix E adds an early-enqueue optimization: after all producers have been dispatched, the consumer may enter the queue while those producers still run, overlapping queue operations with computation. Before performing its actual computation, the consumer must still check and wait for completion. A queued task therefore need not already have readable inputs. Scheduling logic is compiled into the megakernel; runtime state mainly consists of integer event arrays and task queues rather than a fully materialized, traversed generic task graph. The paper’s centralized global-memory queue also has potential contention at larger scales. [Section 3.3 and Appendix E](https://arxiv.org/html/2604.13327v2#A5)

### Supporting dynamic work does not make dynamic scheduling universally preferable

Predictable task durations and ordering favor static queues with little scheduling overhead. Uneven token distribution across experts can make dynamic balancing worth the extra operations. The paper includes a useful control using identical operator code: retain one megakernel, but insert global waits between operator stages, then compare it with fine-grained dependencies. Larger inputs to an individual MoE layer benefit from dynamic scheduling. For low-batch Qwen3-32B on four GPUs, however, dynamic scheduling is slower than this coarse-grained control, while static scheduling performs better. Full-model serving consequently uses static scheduling for both dense and MoE models. Those results cannot all be attributed to a dynamic task queue. [Sections 4.3 and 4.5, Tables 2–3](https://arxiv.org/html/2604.13327v2#S4.SS5)

There is also a programming boundary. Compilation starts from tiled operators with explicit Event Tensor dependencies, supplied by developers or compiler builtins. It is not yet a complete solution that turns arbitrary PyTorch programs directly into optimal megakernels. Static scheduling may handle data-dependent dependencies conservatively, sacrificing some parallelism; dynamic scheduling is more flexible but adds queue costs. Event Tensor’s value is that both choices share a dependency representation, rather than that one scheduler is best for every workload. [Sections 3.1, 3.4, and 6](https://arxiv.org/html/2604.13327v2#S3.SS4)

### Separate decoding speed, CPU overhead, and engine startup

The test server has eight NVLink-connected B200 GPUs; individual experiments use different GPU counts. Full-model serving uses synthetic prompts of 512 tokens and generates 100 tokens, with batches from 1 to 128. Baselines are vLLM 0.11.0rc2 and SGLang 0.5.3rc0 with CUDA Graph and torch.compile enabled. On one B200 with Qwen3-30B-A3B at batch one, ETC’s time per output token corresponds to speedups of 1.48× and 1.20× over those systems respectively. This TPOT includes CPU overhead such as framework scheduling, not just GPU kernel time. On four-GPU Qwen3-32B, ETC still has higher end-to-end latency than SGLang. Better isolated kernel results in the appendix do not replace that conclusion. [Section 4.3, Figure 14, and Appendix D](https://arxiv.org/html/2604.13327v2#S4.SS3)

Another benefit comes from ahead-of-time compilation, or AOT: produce a binary supporting multiple shapes before deployment instead of capturing execution graphs for many batch sizes during startup. For Qwen3-32B, elapsed time from engine launch to serving the first request is 35 seconds for ETC, 123 for vLLM, and 583 for SGLang, including model loading and initialization. ETC separately requires 107 seconds of offline compilation, excluded from the 35 seconds. The result shows that compilation work can move outside repeated startups, not that first use has no compilation cost. It is also not the time to the first generated token of an individual user request. [Section 4.4 and Table 1](https://arxiv.org/html/2604.13327v2#S4.SS4)

### Reading route: draw the dependencies, then price the scheduling

Start with Figure 3 and draw the inputs one output tile truly requires. Compare Figures 7 and 9: while a dependency is unresolved, does an SM wait or perform other work? Then inspect Table 3 to determine whether queue costs erase the parallelism benefit. Finish with Table 1 and Appendix D to separate startup time from GPU-only execution. For agent serving, the implication is that even after requests are scheduled, their GPU work may contain further overlap opportunities. The paper does not directly evaluate tool waits, KV-cache eviction, or long-running online arrival processes. Its evidence primarily covers B200 GPUs, two Qwen models, and the described synthetic workloads, rather than other hardware or complete agent workflows.

## Optional reading · KernelBench: Can LLMs Write Efficient GPU Kernels?

**Year / publication：** 2025 · ICML 2025 · Stanford / Princeton · first preprint 2025-02-14; notes use arXiv v1 · [Original source](<https://arxiv.org/abs/2502.10517v1>)

**Reading guidance：** Select Sections 3.1–3.3, Figure 6, Table 1, and Appendix B. Read it for evaluation methodology, not as evidence of present-day coding-agent capability from 2025 model scores.

### Writing CUDA does not by itself complete an optimization

Start with our teaching example: compute x+b and then replace negative values with zero, or ReLU(x+b). An agent could combine both operations into one kernel to reduce intermediate memory traffic and launch overhead. Apparent fusion does not guarantee a useful result: broadcasting may be wrong, or a kernel that wins for a small input may lose on another shape. We need both a correctness test and a precisely scoped speed comparison.

KernelBench makes these questions executable. The input is a PyTorch Model plus functions producing its test inputs; the output is a ModelNew implementing the same computation, potentially through custom CUDA. The reference program supplies semantics and execution supplies feedback. There is no required reference implementation of the optimized code, so different optimization strategies can compete on the same task. [Sections 3.1–3.3](https://arxiv.org/html/2502.10517v1#S3)

### Separate task complexity from correctness coverage

The v1 suite contains 250 tasks: 100 individual operators at Level 1, 100 operator sequences at Level 2, and 50 full model architectures at Level 3. Higher levels are not uniformly harder. A single operator may already call a highly optimized library, while a sequence may expose straightforward fusion opportunities. Scores for the levels are best reported separately. [Section 3.2](https://arxiv.org/html/2502.10517v1#S3.SS2)

Each task uses five random inputs to compare reference and generated outputs. Compilation or execution failures are distinguished from programs that run but return incorrect shapes or values. Passing establishes success on those tests, not mathematical equivalence for every input. For deployment, our recommendation is to reserve unseen shapes, boundary values, and random seeds for final acceptance. That recommendation is not a generalization guarantee demonstrated by the original paper. [Sections 3.3 and 4.2, Appendix B](https://arxiv.org/html/2502.10517v1#S3.SS3)

### fast_1 is a fraction of successful tasks, not an average speedup

Define speedup as reference runtime divided by generated-program runtime. fast_p is the fraction of all tasks whose outputs are correct and whose speedup exceeds p. fast_0 is effectively correctness rate; fast_1 counts correct solutions faster than the baseline. Failed tasks remain in the denominator. Removing them first would conceal reliability problems. [Section 3.3](https://arxiv.org/html/2502.10517v1#S3.SS3)

In our ten-task example, eight outputs are correct but only three solutions are faster. Then fast_0 is 80% and fast_1 is 30%. The latter is neither a 30% average speedup nor the 37.5% obtained by dividing three by eight. With k attempts per task, fast_p@k requires at least one candidate to meet the threshold. Larger k generally consumes more generation, compilation, and measurement resources; one attempt and selecting the best of one hundred are different budgets.

### What improves when errors and timings are returned to the agent?

The paper compares independently generating candidates with sequentially revising candidates after feedback. Refinement receives the previous generation G, execution feedback E, and optionally profiler timings P. A compiler error can first guide a repair that makes the program run; mismatched outputs motivate algorithm repairs; correct but slow execution motivates performance changes. Figure 6 depicts the feedback path. Table 1 compares a fixed budget of ten model calls. [Section 5.1](https://arxiv.org/html/2502.10517v1#S5.SS1)

One historical result has a clear scope: across the 100 Level 2 tasks on NVIDIA L40S against PyTorch Eager, DeepSeek-R1 achieves fast_1 of 36% with one generation and 72% when taking the best candidate across ten generations, including the initial attempt, with G+E+P feedback. This means more tasks succeeded, not a twofold overall kernel speedup or a 2026 capability ceiling. The changed object is task-specific code; feedback comes from human-designed reference programs, the compiler, and timers. Model weights are not trained in this loop. These bounded within-task revisions do not demonstrate sustained recursive self-improvement. [Table 1 and Figure 7](https://arxiv.org/html/2502.10517v1#S5.SS1.SSS2)

### Timing conditions determine what faster actually means

The v1 primary setup uses L40S, PyTorch 2.5.0+cu124, and CUDA 12.4. It measures forward execution with CUDA events over 100 trials after three warmups, averaging the timings and avoiding competing CUDA processes. This measures the computation itself. Code generation, compilation, queueing, and an entire service request are different costs. [Appendix B](https://arxiv.org/html/2502.10517v1#A2)

Baseline choice also matters. Beating PyTorch Eager does not imply beating fused torch.compile or a hardware-specific library. Conversely, default torch.compile can incur runtime overhead on very small operators, so a higher fast_1 against it need not imply a more advanced kernel. Scores can also change when the same code moves to another GPU. Our evaluation recommendation is to fix hardware, software, inputs, baseline configuration, and search budget together. Training use also requires separate gradient tests: forward correctness alone does not establish backward correctness. [Sections 4.1 and 4.4](https://arxiv.org/html/2502.10517v1#S4)

### Why include a 2025 paper in this issue?

PithTrain asks how a framework can support agent modifications, and Event Tensor asks how the GPU executes computations. KernelBench supplies acceptance criteria for the resulting code. Read Section 3 for tasks and metrics, Figure 6 and Table 1 for feedback, and Appendix B for measurement. The lasting lesson is to make success executable and report search cost separately from final program speed; memorizing old model rankings is unnecessary.
