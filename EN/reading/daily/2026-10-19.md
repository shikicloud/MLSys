# Hybrid-model inference: why fixed-size states can still be slow

Start with the ReplaySSM paper submitted on October 9: after a model compresses history into fixed-size state, why can generating each token still require expensive memory traffic? The main note follows standard decoding, speculative rollback, and low-precision state to explain the separation between producing an output and writing back the full state. Gated Delta Networks supplies the mechanism behind retaining, editing, and forgetting information. September's SuffixReplay then examines approximate state reconstruction for finer-grained shared-prefix reuse. The architecture paper is an optional reference for understanding these systems, not a prerequisite curriculum; there is no need to read all three closely today.

Each digest recommends 1 main paper and 2–4 optional papers across LLM inference, RL infrastructure, post-training, RSI (recursive self-improvement), reasoning compute, agent learning and memory, data and evaluation, and model architecture. Explore foundations and current research by theme; a direct connection to current work is not required. ## Main reading · ReplaySSM: Cache SSM Inputs, Not State

**Year / publication：** 2026 · arXiv 2026 · v1 2026-10-09 · [Original source](<https://arxiv.org/abs/2610.13778v1>)

**Reading guidance：** Main reading; allow 35–50 minutes. Follow the example at token positions 100–108 to understand checkpointing and rollback, then study the two computation paths. Use the experiments to decide which workloads benefit. The low-precision section can wait for a second pass.

### What must the model do when one new token arrives?

Suppose the model has processed 100 tokens and now processes token 101. An attention layer retains keys and values for earlier positions in a KV cache that the current step can query. Another type of layer repeatedly incorporates history into a fixed-size numerical matrix: read the old matrix, add the current information, and calculate an output from the updated matrix. This matrix is its recurrent state. **The token positions and small window below are teaching examples, not samples from the paper's benchmark.**

SSM stands for state-space model; Mamba-2 is one SSM studied here. The paper also studies Gated DeltaNet, or GDN, a gated linear-attention model that maintains recurrent state but uses a different update rule. Hybrid models contain recurrent layers alongside ordinary attention layers, so the serving system has to manage both forms of history.

ReplaySSM comes from Princeton and NVIDIA. Paper v1 was submitted on October 9, 2026, and its references date the earlier technical blog to June 2026. This note studies the paper's complete mechanisms and evaluation rather than presenting the idea as something that first appeared in October. [Paper v1](https://arxiv.org/html/2610.13778v1)

### Why can fixed-size state still be expensive?

Fixed size means the matrix at step 101 has the same dimensions as at step 10001; it does not mean the matrix is small. Each step reads the state from HBM, the GPU's high-bandwidth device memory, and writes it back after updating it. The update may involve relatively little arithmetic. Computation can finish quickly while data movement remains the limiting cost.

The paper gives a concrete example: Nemotron-3-Super-120B-A12B has 40 recurrent layers and 8 attention layers, with 4 MiB of FP32 state per sequence per recurrent layer. FP32 stores each number in a 32-bit floating-point format. At a batch of 256 sequences, all these states are repeatedly read and written. In this configuration on one B300, recurrent-state updates remain the largest latency component up to approximately 100K context tokens. [§3.1, Figure 1, Appendix C.2](https://arxiv.org/html/2610.13778v1)

The immediate question is therefore whether processing every token really requires writing the entire updated matrix back to device memory. ReplaySSM changes this storage policy. It does not change the model's weights or remove the attention layers from the hybrid model.

### Keep the state at token 100 and record recent changes separately

Save the full state after token 100 as S100, and temporarily use a window of four steps. When processing token 101, retain S100 and save the small amount of data needed for this update instead of immediately overwriting the checkpoint. At token 102, S100 still exists, now alongside records for steps 101 and 102. Applying these updates to S100 reconstructs the current state whenever it is needed.

These cached inputs are neither integer token IDs nor raw text. For Mamba-2, each record contains a decay coefficient α and vectors v and k for that layer and step: scale the old state by α, then add the matrix formed from v and k. These are values computed by the neural network, and they take much less space than the full state. [§3.4–4](https://arxiv.org/html/2610.13778v1)

In standard decoding, step 104 incorporates all four records into S100, stores the new checkpoint S104, and clears the records. This operation is called a flush. Earlier history remains represented by the checkpoint throughout; the method does not discard everything before token 100 and retain only the last four tokens.

### The saving is in writes, not the elimination of state reads

On a non-flush step, standard decoding still reads the checkpoint and reconstructs the working state in on-chip storage to calculate the output. It simply does not write that full working state back to HBM. Constructing a matrix during computation and storing it persistently in device memory are different operations: the standard algorithm still does the former and mainly avoids the latter. [Algorithm 1, §4](https://arxiv.org/html/2610.13778v1)

Over a window of L steps, conventional decoding performs L full-state reads and L full-state writes. ReplaySSM still performs L reads but only one full-state write, plus reads and writes of the small records. This is why the paper describes roughly halving the dominant state traffic, rather than halving all device-memory traffic of the entire model. Reconstructing the state also takes computation; eliminating writes is not free.

A larger window amortizes full-state writes over more steps but requires reading and applying more buffered records at each step. At batch size 256, the authors compare L=8, 16, and 32; all four models are fastest at 16, which becomes the main experimental setting. This is a choice supported by those configurations, not a universal constant for every GPU and batch size. [Appendix E.2.2, Figure 9](https://arxiv.org/html/2610.13778v1)

### How do you roll back after trying four tokens and accepting two?

Speculative decoding uses a cheaper drafting process to propose several tokens, then checks them together with the target model. Continue the example from S104: try positions 105–108, but accept only the first two. If the recurrent state has already been overwritten through step 108, there is generally no cheap inverse update back to step 106. The conventional vLLM baseline in the paper stores a full state snapshot for each candidate position and selects the appropriate snapshot after rejection.

ReplaySSM first writes the four input records into its buffer. Once verification finishes, it advances the committed-history pointer by only two records. The final two records are outside the committed history and can be overwritten on the next append. Rollback therefore needs neither a collection of full-state snapshots nor a fresh full recurrence solely to recover the accepted position. [§5.1, Algorithm 2](https://arxiv.org/html/2610.13778v1)

One condition is easy to miss. The buffer has capacity L+T: up to L committed records plus room for T candidates. If h records are already committed and h+T>L, the flush incorporates only those h old records into the checkpoint. It must not incorporate this round's T candidates before acceptance is decided. With our L=4, T=4 example, the next round incorporates accepted positions 105 and 106 into the checkpoint while retaining its new candidates separately, then advances the pointer after the new acceptance decision. [Appendix D.1](https://arxiv.org/html/2610.13778v1)

### If verification needs outputs, why construct every full state?

A second optimization follows from the same separation: a candidate position's full state will not subsequently be stored or read, so verification needs only its output. For one Mamba-2 update term, forming a matrix from v and k and then multiplying by query vector q gives (vkᵀ)q. Alternatively, compute the scalar kᵀq first and multiply v by it. The result is the same without expanding the full matrix for that term. The paper calls this output-only evaluation. [§5.2](https://arxiv.org/html/2610.13778v1)

The actual computation also includes the checkpoint contribution, step-dependent decays, and a restriction preventing later candidates from influencing earlier outputs. Verification can then organize the outputs of several positions together without constructing each full intermediate state. This complements pointer-based rollback: output-only evaluation reduces verification work, while the buffer representation reduces state storage and recovery.

GDN cannot simply reuse Mamba-2's records. It first queries what the old state already contains for k, then computes a correction vector u describing what still needs to be written. Consequently, u depends on the prior state, and corrections for later candidates depend on earlier candidates. The authors organize these dependencies into a T×T triangular solve before output-only verification. Algebraic equivalence still permits floating-point differences; the implementation also caches GDN corrections in FP16, so bitwise identity must not be claimed. [Appendix B.1–B.3](https://arxiv.org/html/2610.13778v1)

### Why use low precision for reads but retain high precision for updates?

If the state is compressed to lower precision every step, rounded values become the starting point of the next update, allowing error to propagate through the recurrence. ReplaySSM separates the two uses: most steps calculate outputs from a smaller low-precision copy; a flush reconstructs and updates from the high-precision checkpoint, then independently creates fresh high- and low-precision copies. Error from low-precision reads is no longer directly written back into the long-lived recurrent state. [§6](https://arxiv.org/html/2610.13778v1)

This costs storage for two checkpoints and additional work during a flush. It does not remove all error: high-precision arithmetic still rounds, and outputs calculated from the low-precision copy can still differ and affect generated text. The protected path is the recurrent-state update, not every possible influence of low precision on future generation.

GDN has a crucial exception. Corrections u cached on ordinary steps already depend on the low-precision state; folding them directly into the high-precision checkpoint would reintroduce the error. The two-precision version therefore also retains the original α, β, v, and k inputs, where β controls write strength. At a flush it must recompute u from the high-precision state before updating the checkpoint. Merely keeping an additional high-precision matrix while reusing low-precision corrections does not achieve the claimed separation. [Appendix B.4, Algorithm 6](https://arxiv.org/html/2610.13778v1)

### Under what conditions does standard decoding improve by 1.20–1.47×?

The evaluation covers two hybrid-model families. The Mamba-2 path uses Nemotron-3-Nano-4B and Nemotron-3-Super-120B-A12B; the GDN path uses Qwen3.5-4B and Qwen3.5-122B-A10B. Each 4B model runs on one 80 GB H100; each larger model runs on one B300 with a 1100 W power cap. There is no tensor parallelism across GPUs. The smaller models use BF16 weights and the larger ones NVFP4 weights, while all these performance experiments use FP32 recurrent state. [§7.1, Appendix E.1](https://arxiv.org/html/2610.13778v1)

Both methods run in the same vLLM build with CUDA graphs enabled to reduce GPU-operation submission overhead. The conventional baseline also uses the fastest kernel launch configuration found in a sweep. At batch B=256 and window L=16, whole-model decode-step speedups are respectively 1.47, 1.42, 1.27, and 1.20×. These measurements time one full-model decoding step, not the complete interval from receiving a request to returning its answer. [Table 6](https://arxiv.org/html/2610.13778v1)

The counterexample matters: at B=1, the whole step reaches only 0.96–0.99× baseline speed and is slightly slower. A single request need not saturate memory bandwidth with state traffic, so the traffic reduction cannot offset the extra work. Gains are also limited as attention takes more of the step at long context lengths. The paper flags some B=512 results as inflated by the B300 power cap; they are not the headline evidence used here.

### About 1.8× speculative throughput does not mean every online request is 1.8× faster

Speculative experiments use the two larger models, each on one B300, drafting with its own multi-token prediction, or MTP, head. Requests come from the GSM8K math-word-problem dataset and run at a fixed batch size. Every request produces exactly 256 tokens, ignoring early termination signals. After warmup, timing includes prefill, the processing of the input; throughput is the total generated-token count divided by elapsed wall time. [Appendix E.3](https://arxiv.org/html/2610.13778v1)

With B=256, L=16, and T=4 tokens verified per step, throughput is 1.77× conventional vLLM speculative decoding for Nemotron and 1.79× for Qwen. Mean committed tokens per step change only from 3.43 to 3.44 and from 3.56 to 3.57, respectively. The benefit therefore comes principally from state management and verification rather than a substantially different acceptance rate. [Tables 8–10](https://arxiv.org/html/2610.13778v1)

This establishes a system benefit for the fixed-batch workload, but it does not measure an online service with stochastic arrivals, mixed request lengths, and tool waits. Time to first token, tail latency for the slowest requests, and adherence to latency targets cannot be inferred directly from these throughput ratios. The ratios also use a different timing metric from the per-step latency in the preceding section.

### What does the low-precision evidence establish?

The authors separately evaluate the quality effects of low-precision state. They feed the same fixed text to each configuration and compare next-token probability distributions, then also generate answers on knowledge, scientific-reasoning, and mathematics tasks. The fixed-text experiment uses four PG-19 books, with a 512-token prompt followed by teacher-forced continuations. Each configuration uses one seed and averages the final 256 positions at the specified length. The first comparison uses KL divergence: a lower value means closer agreement with the FP32 reference distribution, not an equivalent proportional improvement in answer accuracy. [§7.4, Appendix E.4](https://arxiv.org/html/2610.13778v1)

For example, Qwen3.5-4B after processing 128K teacher-forced PG-19 tokens at L=16 has KL 0.136 when NVFP4 serves both reads and recurrence. Keeping FP32 recurrence and using NVFP4 only for reads reduces it to 0.0038. Separating the paths does reduce propagated error, but it is not lossless on every task: in Table 2, one NVFP4-read/FP16-recurrence configuration with stochastic rounding still loses 6.7 percentage points on GPQA-Diamond scientific question answering for Nano-4B.

These quality experiments use standard decoding and emulated quantization, which simulates the rounding caused by low-bit representations. Low-precision read latency is measured using separate dedicated kernels. These results must not be spliced together with the earlier FP32-state whole-model measurements to claim universally lossless low precision plus a particular additional end-to-end speedup. [Appendix E.1, E.4.1–E.4.2, Table 2](https://arxiv.org/html/2610.13778v1)

### Which serving problem does this solve, and what should you read closely?

ReplaySSM manages recent updates and rollback within an active sequence. It does not automatically solve arbitrary prefix sharing between requests, decide which old checkpoint to evict, or choose where to place state while a tool call is pending. Rolling back to a recent position represented by the buffer is not the ability to reconstruct any earlier historical state from the current matrix.

**An engineering inference is** that pausing and restoring a request using this representation requires more than its old checkpoint: unflushed input records and the committed position must also be preserved correctly. A hybrid model's attention cache still needs management. This can inform an agent runtime's state interface, but the paper does not measure benefits for tool waits or pause-and-migrate operations; the inference is not an experimental result.

For close reading, follow Figure 1 → §3–4 and Algorithm 1 → §5 and Appendix D.1 → Tables 6 and 8–10. On a second pass, read §6, Appendix B.4, and Table 2. Establish which data must survive and when it can be committed before working through the formulas. This note reports the implementation and results in paper v1; it does not infer that all current serving frameworks deploy the method by default. [Fixed-version full text](https://arxiv.org/html/2610.13778v1)

## Optional reading · Gated Delta Networks: Improving Mamba2 with Delta Rule

**Year / publication：** 2025 · ICLR 2025 · first preprint December 2024 · MIT CSAIL / NVIDIA · [Original source](<https://arxiv.org/abs/2412.06464>)

**Reading guidance：** Worth a focused close read: start with Fig. 1 and §3.4, then Eq. 10 in §3.1, followed by Table 4 and Fig. 3. Leave §3.3's matrix derivation until you need to understand the kernel. Allow 30–40 minutes.

### An order changes its address: what should the model remember?

**Teaching example, not a paper benchmark:** a conversation first assigns an old delivery address to order A, then replaces it with a new address. Asked where order A should go, the model must identify the order and use the later information. Ordinary attention can retain keys and values for previous tokens and consult them again. A recurrent model instead keeps updating a fixed-size state and subsequently reads primarily from that state.

Think of the state as working notes that are continually rewritten, although it is actually a collection of numbers rather than an order table with individually accessible rows. Model weights determine how those notes are read and written; request state represents this conversation so far. Updating state during inference does not mean training every user's conversation into the model weights.

The paper by Songlin Yang, Jan Kautz, and Ali Hatamizadeh first appeared on December 9, 2024, and was published at ICLR 2025. Its purpose in today's reading is to explain the state manipulated by the new systems papers. [Preprint and version history](https://arxiv.org/abs/2412.06464); [official conference record](https://proceedings.iclr.cc/paper_files/paper/2025/hash/4904fad153f6434a7bcf04465d4be2cc-Abstract-Conference.html)

### Read the old prediction, then correct the difference

In the order example, a key is what you look something up with, and a value is what you want to retrieve. Actual keys and values are vectors computed from the current input, not literal order identifiers and address strings. A state matrix S maps a key to a predicted value. Associations can interfere with one another, so this is not a lossless database. To use the memory, the model computes a separate query vector q and reads the information it needs through Sq.

The delta rule first reads the existing state using the current key, compares the prediction with the new value, and corrects the state along that key's direction. 'New address minus old prediction' refers to a vector difference, not subtraction on text. Unlike unconditional accumulation, the update checks what the state already predicts.

Gated DeltaNet also decays the previous state before making this correction. Calling the decayed state A and the current key and value k and v, one update can be written as `A = αS`, `r = v − Ak`, and `S_new = A + βrkᵀ`. The input-dependent α controls retention and β controls the correction's magnitude. This is an equivalent expansion of Eq. 10, arranged to connect the formula to concrete actions.

### Why remembering requires a way to forget

Writing indefinitely into the same-size state can make newer and older information interfere, reducing retrieval accuracy. But aggressively decaying that state at every sentence might erase the delivery address after a long stretch of unrelated conversation. Forgetting addresses the first problem while creating a risk of the second.

Section 3.2 separates these situations: retrieving one item from repetitive, simple surroundings differs from finding numbers or identifiers in an essay containing many distinct pieces of information. Its experiments do not show that adding forgetting improves every situation. Having a forgetting mechanism does not establish that the model reliably knows which information is unimportant.

A gate is not a human-written rule that knows which order must be remembered forever. It is a learned numerical computation. For a serving system, fixed-size state means that this component's storage does not continually increase with one request's length. It guarantees neither unlimited retention nor constant memory as the number of concurrent requests grows.

### How a recurrence can still use the GPU efficiently

Computing the update token by token seems to leave the GPU waiting for every preceding step. The paper reorganizes a sequence of updates into matrix operations: chunks pass state to subsequent chunks, while computation within a chunk is parallelized where possible. Chunkwise computation changes execution organization; it does not reveal future content that the model is not allowed to use.

As a teaching picture, the previous chunk leaves a state S. The next chunk must account both for S and for interactions among its own tokens; computing every chunk independently and concatenating the results would be incorrect. Section 3.3 rewrites these dependencies into GPU-friendly matrix multiplications rather than simply removing them.

This also distinguishes processing an input that has already arrived from generating a response one token at a time. In the first case, an entire segment is available for organized computation; in the second, the next token is still unknown and generation continues by updating state. Training additionally computes gradients. Their costs differ, so training throughput cannot be copied into an online generation speedup claim.

### Why bring attention layers back?

If a user changes an address several times in quick succession, directly consulting the recent sentences remains useful. H1 alternates Gated DeltaNet and sliding-window attention; H2 also includes Mamba2. The main experiment uses a 2K-token window: windowed layers consult recent content directly, while recurrent layers carry forward the influence of earlier inputs. [§3.4, Fig. 1](https://proceedings.iclr.cc/paper_files/paper/2025/file/4904fad153f6434a7bcf04465d4be2cc-Paper-Conference.pdf)

'Hybrid' therefore does not specify one universal cache layout. This design requires both recurrent state and windowed KV. A different architecture that mixes in global attention will retain KV that continues growing with the sequence. The presence of linear attention or an SSM does not make every component of a request's cache constant-sized.

The original block also contains short convolutions that depend on recent positions. An implementation restoring a request therefore cannot assume that copying the matrix S is sufficient: it must check for convolution history, attention caches, and position information. This is an engineering deduction from computational dependencies, not a serving design already demonstrated by this paper.

### What the experiments establish—and their limits

The main architecture comparison uses approximately 1.3B parameters, 100B FineWeb-Edu training tokens, and a 4K training length. Table 4 reports mean scores over six retrieval tasks with inputs truncated to 2K: 30.6 for pure Gated DeltaNet, 37.0 for Transformer++, and 40.1 for hybrid H2. Under this setup, improving recurrent updates still does not fully replace direct retrieval, while the hybrid addresses some of that gap.

These are task scores for pretrained models, not a general capability ranking for modern instruction models or end-to-end agent success rates. A mean also hides differences between tasks; it does not show H2 winning on every question or dataset. Model size, training budget, and input length belong alongside the comparison.

Figure 3 measures training throughput on one H100. Gated DeltaNet is close to DeltaNet, while Mamba2 is faster; efficient short-window attention also allows hybrids to outperform purely recurrent models in throughput. The paper does not supply prefix-hit rates, state-restoration times, or multi-request serving results for today's systems questions. [§4, Table 4, Fig. 3](https://proceedings.iclr.cc/paper_files/paper/2025/file/4904fad153f6434a7bcf04465d4be2cc-Paper-Conference.pdf)

### Return to today's systems papers with a restoration problem

**The following is our serving analysis:** if two requests share an identical opening and the complete state at that opening's end has been saved, they may continue separately from it. But suppose only the state after token 1,000 is available and another request diverges at token 800. The last 200 tokens cannot simply be sliced out of the current state as one might truncate token-wise KV.

One approach is to restore an earlier saved state and process tokens again up to the branching point: that repeated computation is replay. Branch isolation matters too. A shared prefix can be reused, but diverging requests must not keep mutating the same state. Which positions to save, how much to recompute, and how to batch that computation are the systems questions in today's readings.

Start with Fig. 1 to identify the hybrid layers and Eq. 10 to understand state updates, then take the token-800 branching example into SuffixReplay. For ReplaySSM, instead ask how much state must be read and written per generated token. Read §3.3 when you need kernel details. Finally revisit Table 4 and Fig. 3 to assess model quality and computational efficiency separately.

## Optional reading · Just Let Linear States Forget the Distant Past: Prefix Caching via Suffix Replay for Hybrid LLMs

**Year / publication：** 2026 · arXiv 2026 · v1 2026-09-27 · [Original source](<https://arxiv.org/abs/2609.33477v1>)

**Reading guidance：** Worth an optional close read; allow 25–35 minutes. Start with Figures 1–4 to identify what is cached, then Table 3's quality losses and Figures 9/11's positive and negative performance cases, followed by Section 5's execution path.

### Why sharing a text prefix can still require recomputation

**Teaching example, not a paper measurement:** one request has processed 16,384 tokens, and a new request branches at position 12,288. If complete historical state copies exist only at positions 8,192 and 16,384, recovery requires computing another 4,096 tokens from the earlier copy. Such a saved copy is a checkpoint; its placement determines which historical positions can be restored immediately.

Full-attention layers store per-token keys and values for later lookup: the KV cache. Linear layers instead overwrite a fixed-size recurrent state, without keeping a separate copy for every old position. A hybrid model interleaving these layers needs both forms of state before it can reuse a prefix. A KV hit alone is insufficient. [Sections 1–2, Figure 1](https://arxiv.org/html/2609.33477v1)

SuffixReplay instead retains some inputs needed for reconstruction. Version 1 appeared on September 27, 2026, with authors from China Telecom's TeleAI, Shanghai Jiao Tong University, Tsinghua University, and independent researchers. This note presents it as a preprint. [Version and team](https://arxiv.org/abs/2609.33477v1)

### Store intermediate vectors and replay a recent subset of computation

Each layer receives vectors representing the information computed so far, rather than raw text. The paper calls retained input vectors anchors. Consecutive linear layers form a group, with records stored only at the group entrance. Recovery independently replays the necessary computation within each group, without crossing the full-attention layers between groups. Reconstruction errors therefore do not propagate from an earlier group into the next during recovery. [Section 4.1, Figure 2](https://arxiv.org/html/2609.33477v1)

Inputs are also sampled across positions: the default keeps only the final four input rows of each 64-token page. Replaying 128 retained rows consequently does not mean replaying the last 128 original tokens; many intervening positions were not retained. Recovery supports cache-page boundaries, not arbitrary tokens. The main serving experiments cap replay at 512 rows for the 4B model and 256 for the 27B model, with actual length also depending on the matched prefix. [Sections 4.2–4.3 and 7.1](https://arxiv.org/html/2609.33477v1)

### Why omitting history can work, and what it does not guarantee

These linear layers decay or erase some old information before adding the current input. The paper therefore tries replaying recent inputs from an empty state while approximately ignoring the earlier state's influence. Full-attention layers still reuse the complete prefix KV, and retained input vectors already contain information from earlier computation. This does not delete all distant content from the document. [Sections 2.1 and 4](https://arxiv.org/html/2609.33477v1)

**A derivation example for understanding the condition:** suppose the contiguous suffix inputs are identical, and each update retains at most half the influence of a difference in the old state. Each additional replay step then halves the bound on the initial error. Only after sufficiently many steps might discarding the starting state be reasonable. Having forgetting gates does not establish such strong contraction for every input in a real model.

The implemented method also skips inputs and recomputes later layers inside each group. The simple condition above cannot prove that this entire sparse replay process is lossless. The paper provides neither a universal output-error bound nor one replay length suitable for all models. It selects budgets through offline quality experiments and does not directly cover recurrences that preserve all historical contributions without the required forgetting behavior. [Sections 4.3 and 9](https://arxiv.org/html/2609.33477v1)

### Avoid moving the saved work into another waiting stage

A prefix hit requires fetching KV, fetching input records, and rebuilding linear states. The paper stores records separately: they enter and leave the cache with their KV pages but may occupy different memory tiers. Record transfers start early and overlap KV movement and scheduling. Normal execution waits only when it reaches a group whose reconstructed state is needed. If the previous turn's live state remains available, it can be reused without replay. [Section 5](https://arxiv.org/html/2609.33477v1)

This also affects non-hit traffic because ordinary prompt processing and generation must write records. The authors put these writes into a pre-recorded GPU execution path to reduce repeated calls and synchronization. Missing or incompletely published records trigger full prefill. That prevents consuming incomplete cache data; it is not an online test that an approximate answer is correct. [Sections 5.1–5.2](https://arxiv.org/html/2609.33477v1)

In Table 2, Qwen3.5-4B's additional input records occupy about 2.2 KiB per token, versus about 6.1 KiB of amortized baseline checkpoints. This compares extra state storage beyond KV, not total GPU memory reduced to 36%. Replay also has fixed costs: the 4B model's captured execution graphs consume approximately 1.1 GB of device memory. [Table 2, Section 6](https://arxiv.org/html/2609.33477v1)

### Look below the average when judging preserved quality

The quality experiment first fully processes the context, then simulates a cache hit at the query boundary and pairs approximate recovery with a full-recomputation reference. Tests use one 80 GB H800 and cover OLMo-Hybrid-7B, BF16 Qwen3.5-4B, and Qwen3.6-27B-FP8. Reported values divide the replay task score by the full-prefill score; they are not percentages of textually identical answers. [Sections 7.1–7.2](https://arxiv.org/html/2609.33477v1)

Table 3 reports that at 128 replayed rows, the 4B model retains 100% and 99.7% of the LongBench QA and RULER averages, but only 94.8% on GovReport summarization. At 512 rows, OLMo retains 91.4% on RULER on average, with only 81.7% on the 128K-context variable-tracking task. A strong average does not establish lossless performance on every task. A single simulated hit also does not prove that repeated approximate recovery over long usage cannot accumulate effects. Budgets need validation for the particular model and target tasks. [Table 3](https://arxiv.org/html/2609.33477v1)

### Which requests improve, and which can become slower?

Serving tests cover only the two Qwen models because the paper's SGLang v0.5.18 does not support OLMo-Hybrid. Baseline and modified systems run alternately on the same 80 GB H800, using the same scheduler, KV implementation, and default 8,192-token chunked prefill. This comparison concerns the paper's version and configuration, not every current SGLang deployment. [Sections 6–7.1](https://arxiv.org/html/2609.33477v1)

The farther a branch lies beyond a checkpoint, the more work the baseline must repeat and the more replay may help. Under Figure 9's open-loop ToolMind workload with caches resident in GPU memory, the 4B model's median time to first token falls by about 66% near 16K context, where continuation lies roughly three to four thousand tokens beyond the latest checkpoint. TTFT measures waiting before the first output, not a 66% improvement for every generated token. [Section 7.3, Figure 9](https://arxiv.org/html/2609.33477v1)

The counterexample matters equally. With the 4B model, a 35K prefix, eight concurrent sessions, and fixed output lengths, branches land exactly on native checkpoints. Median TTFT rises from the baseline's 121 ms to 174 ms with a 512-row replay cap. Fixed lengths synchronize request completion and subsequent hits, exposing replay overhead together; varied output lengths remove the measured gap. Traffic that simply continues the previous turn and can reuse a live state likewise offers less room for large speedups. [Figure 11, Table 4, Section 9](https://arxiv.org/html/2609.33477v1)

### Read alongside ReplaySSM by identifying what each one saves

The main reading ReplaySSM targets decoding, combining state checkpoints with short-term input buffers to reduce frequent writes of the complete state. SuffixReplay targets prefix reuse: it removes persistent internal historical-state checkpoints and approximately reconstructs earlier branch boundaries from sparse inputs. Both use replay, but their starting points, retained material, and precision assumptions differ. An exactness conclusion from one cannot simply be transferred to the other. [SuffixReplay Sections 4–5](https://arxiv.org/html/2609.33477v1); [ReplaySSM](https://arxiv.org/html/2610.13778v1)

**A systems-oriented reading suggestion:** first determine whether actual traffic mostly continues forward or branches from earlier positions. Then measure how many input records preserve task quality, and include recording, transfer, replay, and fixed device memory in the cost. Read Figures 1–4, Table 3, and Figures 9/11 before Section 5 to connect cache hits, approximation quality, and the waiting time users actually experience.
