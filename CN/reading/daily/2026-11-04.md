# 让 Agent 改训练框架，怎样做到省力又可信？

主读 PithTrain：从给模型接入 MoBA 注意力的任务出发，解释紧凑代码、直接调用和操作流程如何减少 Agent 的调试成本，以及改动怎样验收。选读 Event Tensor，看 GPU 上一小块计算何时可以开始；再读 KernelBench，分清代码能运行、结果正确和确实更快。今天先读主读的任务例子与验收规则，另外两篇按兴趣展开；框架修改成本、训练吞吐和推理延迟分别讨论。

每天推荐 1 篇主读与 2–4 篇选读，覆盖 LLM Inference、RL Infra、Post-Training、RSI（递归自我改进），以及推理计算、Agent 学习与记忆、数据评估和模型架构。经典与前沿并行，按主题逐步展开；不要求与当前工作直接相关。候选不等于已读，无需一天读完。

## 主读 · PithTrain: A Compact and Agent-Native MoE Training System

**年份 / 发表信息：** 2026 · arXiv 2026 · CMU / NVIDIA / Xlue · v1 2026-05-29 · [原文](<https://arxiv.org/abs/2605.31463v1>)

**阅读建议：** 值得精读。先沿 MoBA 改动例子读 §3、§5.4，再看附录 B 的验收规则；最后核表 4、7、8，把训练吞吐与 Agent 工作成本分开。

**再次推荐的原因：** 从研究概览进入 Agent 可维护性与评估机制：训练框架怎样影响 coding agent 修改、验证和调试代码的成本。

### 先看具体任务：让 Agent 把一种新注意力接进训练框架

假设你给编程助手（coding agent）一篇 MoBA 论文和参考实现，要它把训练模型原有的注意力换掉。MoBA 会把历史 token 分成块，为当前查询选择相关块，再在这些块里计算注意力。Agent 必须找到模型构造位置，接好前向与反向计算，写训练入口，运行并修复错误。PithTrain 问的是：能不能把框架设计得更容易完成这类改动，而不明显牺牲训练速度？这也是论文真正测试的一项任务。[§5.4、附录 B.3](https://arxiv.org/html/2605.31463v1#S5.SS4)

标题中的 agent-native 指框架为现有 coding agent 的读代码、改代码和验证过程而设计。实验没有训练这个 agent 的策略，也没有让它自主选择研究目标、反复提升自己的能力。人提供任务、论文、参考代码和验收规则，Agent 在这些条件下完成工程工作；因此不能把它直接称为自主递归自我改进。

### 第一步：缩小范围，让关键调用能在附近看懂

论文版本的框架约 1.1 万行，分成应用、训练引擎、算子三层，主动收窄模型、功能和硬件覆盖。每种模型集中在独立文件里，直接构造和调用模块。例如，Agent 找到 attention 的构造位置后，能继续读到具体类；如果构造依赖注册表或另一文件中的运行时配置，就要先追出“这个名字最后指向谁”。紧凑和直接调用减少的是这些理解路径，而不只是文件体积。[§3.1–3.2、图 2–3](https://arxiv.org/html/2605.31463v1#S3.SS1)

这种设计也有交换条件：多个模型不一定通过同一套抽象复用实现，某些修改可能需要分别做。主体和自定义算子采用 Python 或 Python DSL，目标是让 Agent 少跨语言边界、能从可读的错误栈定位问题；底层 GPU 计算仍依赖编译和运行库。论文没有证明“代码越短越好”或“所有插件系统都应该删除”，而是选择了更适合局部修改的一种框架组织方式。

### 第二步：保留高效训练需要的计算与通信安排

代码紧凑不等于把分布式训练简化成单卡玩具。PithTrain 支持流水线并行，把模型不同部分放到不同设备；专家并行，把不同专家分到不同设备；也支持数据并行、上下文并行、检查点和 FP8。论文中的 DualPipeV 调度把每层在专家通信边界拆成五个阶段，将专家间传 token 的 all-to-all 放到独立通信流，让一个小批量的前向与另一个的反向尽量重叠。这些都是已有优化思路，论文没有声称重新发明它们。[§3.2](https://arxiv.org/html/2605.31463v1#S3.SS2)

框架还对能稳定形成完整计算图的 Transformer 部分使用 torch.compile(fullgraph=True)；这个模式遇到图断裂会报错，避免悄悄退回较慢执行。专家收到多少 token 随路由变化，因此 MoE 的前后向不走这条编译路径。其他优化包括延后部分权重梯度计算、融合算子、减少重复专家通信，以及在小批量之间缓存 FP8 权重以避免反复量化。它们说明“便于 Agent 改”与“训练快”可以共同设计，实际是否划算仍要看对应硬件和配置。

### 第三步：把操作经验写成有验收结果的流程

读懂代码不等于知道怎样正确验证一次改动。论文为常见任务提供 skills，也就是按需读取的操作流程文件。例如验证训练正确性时，先检查数据、环境和配置，再运行修改前后两份训练，最后由脚本比较 loss 曲线并返回 PASS/FAIL。捕获 Nsight Systems 性能分析、添加新模型、打印显存也有对应流程。关键是范围明确、前提写清、结束条件可检查；不是给 Agent 一句“请仔细测试”。[§3.3、图 4](https://arxiv.org/html/2605.31463v1#S3.SS3)

§5.3 对两个流程做了更受控的对照：同一份框架、同一 agent 和测试环境，每项有无 skill 各做三次，禁用时连 git 历史中的流程也移除。验证正确性任务的 Agent Turns 中位数从 114 降到 34，但 GPU 活跃时间没有下降，因为两边都要执行规定的训练验证。流程主要减少了探索操作方法的往返，不会让必要的计算凭空消失；这个结果来自两项具体任务，不能直接推广成所有 skills 的统一收益。[表 8](https://arxiv.org/html/2605.31463v1#S5.SS3)

### ATE-Bench：固定同一个 Agent，换它要操作的框架

ATE 是 Agent Task Efficiency，指完成框架任务所需的成本，不是一个单一分数。评测固定 Claude Code、Opus 4.7 和 xhigh effort，分别操作 PithTrain、Megatron-LM、TorchTitan。任务共 20 个：12 个代码问答、4 个运行与分析任务、4 个新功能任务，每项独立尝试三次并报告中位数。任务包括追踪配置怎样传入模型、记录每个 token 被分到哪些专家，以及集成 MoBA 等新结构。所有尝试最终都通过要求，因此这里比较的重点是完成同样工作花多少力气，而不是哪种框架成功率更高。[§4–5.2](https://arxiv.org/html/2605.31463v1#S4)

运行和新功能任务统一使用 DeepSeek-V2-Lite、单节点 8 张 H100、PP=4 与 EP=2，分别是四段流水线和两路专家并行；DP=1，序列长 2,048、全局 batch 1,024、BF16。作者分别记录会话耗时、GPU 活跃时间、Agent 轮次、每轮上下文和输出 token。这些量回答不同问题：长会话可能在读代码，更多 GPU 时间可能来自反复跑失败的训练，输出 token 也不能直接等于金钱成本。把指标拆开，才能看出变化发生在哪一段。[附录 B](https://arxiv.org/html/2605.31463v1#A2)

### 不是 Agent 说完成就算完成：三类任务怎样验收？

问答任务要求给出文件、函数和行号，两名人工分别打开这些位置确认；有分歧再由第三人看证据。运行任务检验实际产物：启动任务要让只读训练脚本跑到第 5 步且 loss 有限；路由日志要覆盖指定层和 token，专家编号在合法范围，权重非负且归一化；性能分析还要把导出的热点名称与 Nsight 报告对上。这些检查是在看可复核的结果，不是根据答案语气评分。[附录 B.1–B.2](https://arxiv.org/html/2605.31463v1#A2.SS1)

新功能任务要求在 DCLM 上完成 64 步训练，交叉熵 loss 有限且下降，同时满足三个任务专属的架构规则。MoBA 的规则是按块组织 K/V、按查询得分选择块、在选中块上计算注意力并保留因果遮罩。独立的 Opus 4.7 会话先检查代码差异和规则，人再逐条核对它引用的依据。这个组合能排除一些“代码没有真正改但 loss 也下降”的假成功；它仍不是与参考实现逐元素等价的证明，也没有覆盖所有形状、边界情况和长训练行为。[附录 B.3](https://arxiv.org/html/2605.31463v1#A2.SS3)

### 回到 MoBA：节省来自哪些实际工作？

表 7 的 MoBA 集成任务中，PithTrain 的 Active GPU Time 中位数为 27.7 分钟，Megatron-LM 为 49.5，TorchTitan 为 77.9；完整会话耗时分别是 38.7、61.6、105.1 分钟。这些是前述同一 agent、同一模型配置、各三次尝试的结果。前一项是论文报告的 GPU 活跃时间，后一项还包括探索、编辑等过程，不能混用，也不能直接解释成每张卡耗时之和或 API 账单。[表 7](https://arxiv.org/html/2605.31463v1#S5.SS2)

§5.4 继续查看调试过程：PithTrain 三次中两次无运行失败，另一次的张量 stride 错误在同一文件修复；Megatron-LM 遇到重复参数注册或 BF16 溢出，修复跨多个文件；TorchTitan 的初始实现曾显存不足，引出反复修改。这里既有代码结构的影响，也有运行时显存余量的影响。MoBA 行为分解还排除了 API 未暴露的 thinking tokens，所以可见输出减少不能证明总推理量同比例下降。案例用于解释观测，不足以把全部收益归因于“代码更短”。[§5.4、图 6](https://arxiv.org/html/2605.31463v1#S5.SS4)

### 代码更短以后，MoE 训练性能有没有退步？

表 4 用公开模型检查点启动训练，让专家路由处于已训练的状态；各框架匹配并行方式、序列长度和精度，运行 25 步，取最后 10 步的中位步时计算整体 tokens/s。一个具体配置是 Qwen3-30B-A3B、16 张 H100、PP2/DP1/CP1/EP8、序列长 2,048、BF16：PithTrain 为 124.9K tokens/s，Megatron-LM 为 126.7K。这里性能接近，但 PithTrain 略低；不是每个配置都胜出。论文总共列了五种 H100/B200 配置，不能外推到任意模型和集群。[§5.1、表 4](https://arxiv.org/html/2605.31463v1#S5.SS1)

作者还单独检查训练正确性：Qwen3-30B-A3B 在 32 张 H100 上按相同配置训练 4,096 步，使用 DCLM、BF16、序列长 2,048、全局 batch 1,024，比较 loss 轨迹和六个下游任务。这比只跑几十步更有说服力，但仍是有限模型与配置的证据。ATE 中的“训练并评估”任务又不同：它只从随机初始化训练 25 步，HellaSwag 得分接近随机也允许通过，因为那里检验的是导出和评估流程能否跑通，不是模型能力。[附录 A、B.2](https://arxiv.org/html/2605.31463v1#A1)

### 哪些结论已经有证据，哪些还不能推广？

证据支持的是：在作者选择的这些任务、框架版本和硬件条件下，同一个强 coding agent 往往能用更少工作完成 PithTrain 的任务，同时框架保有接近生产方案的训练吞吐。它没有隔离四项设计原则各自贡献多少；只有 skills 做了专门的有无对照。也没有测试多种 agent 或覆盖全部维护场景。尤其是一次共享修改要传播到许多模型时，共用抽象可能反而减少工作，而这类任务未纳入 ATE-Bench。[§4、§5.3](https://arxiv.org/html/2605.31463v1#S4)

对系统研究更有用的借鉴是：先写清一次改动要交付哪些证据，再衡量修改成本。例如要给 MoE 加路由日志，先规定每层每个 token 的覆盖、编号范围和权重检查，然后记录定位代码、修改、验证和 GPU 重跑各用了多少。这样才能区分“Agent 很快写完”与“系统很快获得一个可信改动”。这是从论文得到的研究建议；论文尚未验证长期多人维护、开放式研究任务或无需人工验收的连续自我改进。

先读图 1–3 和 §3，弄清这四个设计原则改变了什么；再沿 §5.4 的 MoBA 例子看 Agent 为何来回修改。接着读附录 B.3，自己判断三条规则与 64 步训练能覆盖哪些错误。最后对照表 7 的 Agent 成本、表 8 的 skills 对照、表 4 的吞吐和附录 A 的训练正确性。读完应能分别回答：框架是否易改、改动是否被充分检查、训练是否跑得快，而不是把三件事压成一个“Agent 更强”的结论。

## 选读 · Event Tensor: A Unified Abstraction for Compiling Dynamic Megakernel

**年份 / 发表信息：** 2026 · MLSys 2026 · CMU / NVIDIA and collaborators · first preprint 2026-04-14; v2 2026-04-21 · [原文](<https://arxiv.org/abs/2604.13327v2>)

**阅读建议：** 值得精读 Figure 3 和 §2，再并排看 Figures 7、9 的静态等待与动态取任务；最后用 Tables 2–3 检查动态调度何时值得付出额外开销。

**再次推荐的原因：** 从研究方向概览进入执行机制：理解任务如何声明依赖，以及编译器怎样把这些依赖变成 GPU 内部的静态或动态调度。

### 后一步需要的结果已经齐了，为什么还在等？

先看一个自拟的分块求和例子：P0、P1 产生输出块 C0 所需的两个部分和；P2、P3 则服务于另一个输出块 C1。若程序先启动一个 kernel 计算所有 P，再启动另一个 kernel 计算所有 C，那么即使 P0、P1 已完成，C0 仍要等 P2、P3。等待不是数学要求，而是程序把同步边界设得太粗。这里的 tile 就是一小块数据对应的计算任务；SM 是 GPU 上执行这些任务的计算单元。[§2.2 与 Figure 3](https://arxiv.org/html/2604.13327v2#S2.SS2)

Event Tensor 希望让 C0 在自己的两个前提满足后即可开始，与仍在计算的 P2、P3 重叠。为此，编译器把多个算子的分块任务放进一个长期运行、持续领取工作的 kernel，这类程序称为 persistent megakernel。它减少 CPU 反复启动小 kernel 的开销，也能移除不必要的跨算子等待。把多个操作放进同一个 kernel 只是第一步；如果内部仍强制所有 P 结束后才能执行任何 C，就没有得到这种细粒度并行。[§1 与 Figure 1](https://arxiv.org/html/2604.13327v2#S1)

### 事件张量记录的是完成条件，不是模型激活

给 C0 设置一个事件 E0，初始计数为 2。P0 完成就通知一次，使计数变为 1；P1 再通知一次，计数归零，表示 C0 的输入已经准备好。许多这样的事件排成多维数组，就是 Event Tensor。它的创新重点不是发明计数器，而是把依赖关系变成编译器能理解、变换的对象：一个任务会通知哪些事件，另一个任务又要等哪些事件。数组维度还可以用 batch 大小等符号表示，同一份编译结果据运行时形状确定实际任务范围，而不用为每个 batch 重新编译。[§2.1–2.3](https://arxiv.org/html/2604.13327v2#S2)

MoE，即混合专家模型，进一步要求依赖随数据改变。例如路由器把不同 token 分给不同专家，编译时无法提前知道某专家会收到哪些输入。Event Tensor 允许分组任务按照本次路由结果通知相应专家的事件；事件的初始计数取决于该专家本次收到的 token 数，随后要启动多少矩阵计算块也在运行时确定。这没有跳过路由计算：仍是先得到路由结果，再决定后续事件与任务。它表达的是变化的依赖关系，并不替模型选择专家。[§2.4 与 Figure 5](https://arxiv.org/html/2604.13327v2#S2.SS4)

### 等待固定任务，还是先取一个已经能做的任务？

同样的事件关系可以编译出两种执行方式。静态调度事先给每个 SM 排好任务队列：一个 SM 完成 P0 后，如果排在下一位的 C0 还在等 P1，它就检查事件计数并等待。动态调度则允许这个 SM 先从 GPU 上的共享队列取另一个可执行任务；等 E0 满足后，再把 C0 放进可领取的任务集合。这样可以减少某些 SM 等待、另一些 SM 忙碌的情况，代价是领取任务、入队和更新共享计数所需的原子操作。[§3.1–3.3 与 Figures 7、9](https://arxiv.org/html/2604.13327v2#S3)

论文正文用“生产者完成后再入队”解释基本语义，Appendix E 还给出提前入队优化：一旦所有生产者都已分派，就可先把消费者入队，把队列操作与生产者计算重叠；消费者真正执行计算前仍必须检查并等待依赖完成。因此，任务已进入队列不总等于输入已经可读。调度逻辑最终被编进 megakernel，运行时主要保存整数事件数组与任务队列，而不必完整展开并遍历通用任务图。当前论文设计使用集中式全局内存队列，也承认规模增大时可能产生竞争。[§3.3 与 Appendix E](https://arxiv.org/html/2604.13327v2#A5)

### 支持动态任务，不代表所有场景都该动态调度

如果任务时长与顺序容易预测，静态队列可以省掉大量调度操作；若各专家收到的 token 数很不均匀，动态队列才更可能抵消这些开销。论文用相同算子代码做了一个重要对照：保持一个 megakernel，但在算子之间加入全局等待，再与细粒度依赖比较。单层 MoE 的较大输入能从动态调度获益；四卡 Qwen3-32B 的低 batch 场景中，动态调度却慢于这个粗粒度对照，静态调度更好。因此，完整模型推理实验最终对稠密与 MoE 模型都选择了静态调度，不能把这些结果全归功于动态队列。[§4.3、§4.5 与 Tables 2–3](https://arxiv.org/html/2604.13327v2#S4.SS5)

这里也有编程边界。论文的编译输入已经包含分块算子及显式 Event Tensor 依赖，可以由开发者或编译器内建实现提供；它还不是把任意 PyTorch 程序直接变成最佳 megakernel 的完整自动化方案。静态方式处理数据相关依赖时可以采取保守同步，牺牲部分并行机会；动态方式更灵活，却增加队列成本。Event Tensor 的价值是让这两种取舍共享同一种依赖表示，而不是宣称一种调度器适合所有负载。[§3.1、§3.4 与 §6](https://arxiv.org/html/2604.13327v2#S3.SS4)

### 实际快了多少，要把解码、CPU 与启动时间分开

测试平台是一台有八张 NVLink 互联 B200 的服务器，各实验使用不同卡数。完整推理测试采用合成输入：提示词 512 token，生成 100 token，batch 从 1 到 128；对照是 vLLM 0.11.0rc2 与 SGLang 0.5.3rc0，已启用 CUDA Graph 和 torch.compile。单张 B200、Qwen3-30B-A3B、batch=1 时，ETC 的每输出 token 耗时相对两者分别对应 1.48 倍与 1.20 倍加速。这里的 TPOT 包含框架调度等 CPU 开销，不只是 GPU kernel 时间。四卡 Qwen3-32B 中，ETC 的端到端延迟仍高于 SGLang；不能用附录中更好的纯 kernel 结果替代这一结论。[§4.3、Figure 14 与 Appendix D](https://arxiv.org/html/2604.13327v2#S4.SS3)

另一项收益是提前编译，即 AOT：先生成可处理多种形状的二进制，启动服务时不再为许多 batch 逐一捕获执行图。Qwen3-32B 从启动引擎到服务首个请求，ETC 为 35 秒，vLLM 为 123 秒，SGLang 为 583 秒；该时间包括加载模型和初始化。但 ETC 还有单独的 107 秒离线编译，不在 35 秒内。因此，结果说明可把编译工作移出每次启动，并非首次使用完全没有编译成本；它也不是单个用户请求的首 token 延迟。[§4.4 与 Table 1](https://arxiv.org/html/2604.13327v2#S4.SS4)

### 精读路线：先画依赖，再判断调度是否值得

建议先照 Figure 3 画出一个输出块真正需要哪些输入，再并排看 Figures 7、9：在依赖尚未齐备时，SM 是等待还是能做别的工作？之后读 Table 3，检验队列开销是否吃掉了并行收益，最后读 Table 1 与 Appendix D，分别检查启动时间和纯 GPU 时间。对 agent serving 的启发是：即使请求层已经排好队，GPU 内部还可能有可重叠的小任务；但论文没有直接评估工具等待、KV cache 驱逐或长期在线请求到达。结果主要覆盖 B200、两个 Qwen 模型及上述合成负载，不能直接当成其他硬件或完整 agent 工作流的收益。

## 选读 · KernelBench: Can LLMs Write Efficient GPU Kernels?

**年份 / 发表信息：** 2025 · ICML 2025 · Stanford / Princeton · first preprint 2025-02-14; notes use arXiv v1 · [原文](<https://arxiv.org/abs/2502.10517v1>)

**阅读建议：** 选读§3.1–3.3、Figure 6、Table 1与Appendix B即可。推荐它是为了学评测方法，不是用2025年的模型成绩判断今天的代码Agent能力。

### 写出一段CUDA，还不算完成优化

用一个自拟例子开始：原程序先算 x+b，再把负数变成零，即 ReLU(x+b)。Agent可以尝试把两步放进一个kernel，减少中间结果的读写和启动开销。但看起来做了融合，不等于真的有收益：它可能处理错广播维度，也可能在小输入上更快、换个形状就更慢。我们需要同时回答“结果对不对”和“在什么条件下更快”。

KernelBench把这两个问题变成可执行任务。输入是一份PyTorch Model及生成测试输入的函数，输出是实现同一功能的ModelNew；Agent可以调用自定义CUDA等实现。参考程序提供计算语义，实际执行提供反馈，评测不要求生成代码长得像某份标准答案。这让不同优化方法可以在同一个任务上比较。[§3.1–3.3](https://arxiv.org/html/2502.10517v1#S3)

### 任务难度与正确性检查，要分开看

论文v1包含250个任务：Level 1是100个单独算子，Level 2是100个算子序列，Level 3是50个完整模型结构。层级更高不意味着每个任务都更难：单算子可能已经调用高度优化的库，反而很难超过；算子序列则可能留下融合机会。不同层级的得分最好分别报告。[§3.2](https://arxiv.org/html/2502.10517v1#S3.SS2)

每题用五组随机输入比较参考与生成实现的输出，并区分两类失败：编译或运行失败，以及能运行但结果形状或数值不对。通过这些检查只说明通过了这组测试，不是对所有输入的数学证明。将它用于真实项目时，我建议另设未暴露给Agent的形状、边界数值与随机种子作为最终验收；这是本文的测试建议，不是原论文已完成的泛化保证。[§3.3、§4.2与Appendix B](https://arxiv.org/html/2502.10517v1#S3.SS3)

### fast_1是成功任务占比，不是平均加速比

先定义 speedup=参考程序耗时/生成程序耗时。fast_p统计全部任务中“输出正确且speedup大于p”的比例：fast_0相当于正确率，fast_1统计正确且快过基线的任务。这里的分母包含失败题，不能先删掉错误程序再计算，从而把不可靠的方法包装成高成功率。[§3.3](https://arxiv.org/html/2502.10517v1#S3.SS3)

举一个自拟的十题例子：八题结果正确，只有三题更快，那么fast_0=80%，fast_1=30%。后者既不是平均加速30%，也不是成功程序占八题中的37.5%。如果每题尝试k次，fast_p@k只要求其中至少一个候选达到门槛；k越大用掉的生成、编译和测量预算通常也越多，所以不能把一次生成与一百次挑最好者当成相同成本。

### 把报错和耗时交还Agent，究竟改进了什么

论文比较独立生成多个候选，以及看过反馈后顺序修改候选。后一种循环给出上一版代码G、执行反馈E，以及可选的profiler耗时P。比如编译器指出未定义变量，Agent先修到能运行；输出不一致时修算法；结果正确但耗时高时，再检查慢的算子。Figure 6展示了这个反馈路径，Table 1比较固定十次模型调用的预算。[§5.1](https://arxiv.org/html/2502.10517v1#S5.SS1)

一个有明确条件的历史结果是：在100个Level 2任务、NVIDIA L40S、PyTorch Eager基线上，DeepSeek-R1一次生成的fast_1为36%；含初次生成在内共尝试十次，利用G+E+P反馈并保留过程中最好候选时为72%。这是完成更多任务，不是kernel整体提速两倍，也不是2026年的能力上限。改进对象是单题代码，反馈来自人为设计的参考程序、编译器与计时器；模型权重未在这个循环中训练。这种有限次数的任务内修正，不能据此宣称持续递归自我改进。[Table 1与Figure 7](https://arxiv.org/html/2502.10517v1#S5.SS1.SSS2)

### 计时条件决定“更快”到底指什么

论文v1的主要测试使用L40S、PyTorch 2.5.0+cu124和CUDA 12.4。对forward做三次预热，再用CUDA events重复计时100次并取平均，同时避免其他CUDA进程争用GPU。它衡量的是这段计算的执行时间；生成代码、编译、排队和完整服务请求的耗时不在同一个数字里。[Appendix B](https://arxiv.org/html/2502.10517v1#A2)

基线也会改变结论。超过PyTorch Eager，不一定超过融合后的torch.compile，更不一定超过目标硬件的专用库。反过来，默认torch.compile在某些很小算子上可能被运行时开销拖慢，不能仅凭一个较高fast_1断言生成代码更先进。论文还发现同一批代码换GPU后得分会变化。因此复用这套方法时，应一起固定硬件、软件版本、输入、基线配置和搜索预算；训练用途还要单独检查梯度，不能用forward正确代替反向传播正确。后两点是本文对验收范围的推导。[§4.1与§4.4](https://arxiv.org/html/2502.10517v1#S4)

### 为什么今天选读这篇2025年的论文

PithTrain关注“框架怎样方便Agent修改”，Event Tensor关注“GPU怎样执行这些计算”，KernelBench补的是“修改结果怎样验收”。读§3理解任务与指标，再看Figure 6和Table 1理解反馈，最后读Appendix B理解测量。没有必要背旧模型排名；真正值得带走的是把成功条件写成可执行检查，并把搜索成本与最终代码速度分开报告。
