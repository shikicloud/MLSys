# FP8 rollout 为什么会影响学习：从 Jet-RL 看精度、长尾与异步训练

同一份权重，为什么生成端和训练端还会给同一个 token 不同的概率？本期主读 Jet-RL，逐步解释量化尺度、统一前向流程和剩余误差。两篇选读分别看 TLT 如何利用长尾空闲资源训练草稿模型，以及 VCPO 如何控制旧策略样本带来的更新波动。先读主读的概率例子和图 5，选读按兴趣展开；三者处理不同问题，不能把各自加速比直接相乘。

## 主读 · Jet-RL: Enabling On-Policy FP8 Reinforcement Learning with Unified Training and Rollout Precision Flow

**年份 / 发表信息：** 2026 · arXiv 2026 · NVIDIA / MIT / UC Berkeley / independent researcher · v1 2026-01-20; v2 2026-01-24 · [原文](<https://arxiv.org/abs/2601.14243v2>)

**阅读建议：** 值得精读：先看图 5、§4.1，再读 §4.2、表 2–4；对照 §3 的失败案例，最后梳理仍未验证的一致性条件。

**再次推荐的原因：** 此前在研究方向导读中简要介绍过；这次展开量化流程、反向传播、实验条件与数值一致性的边界。

### 同一份权重，为什么生成端和训练端还会意见不一致？

假设模型正在解一道数学题。生成端用 FP8，也就是每个数只用 8 位浮点格式参与部分计算，来加速生成回答；训练端保留 BF16，用 16 位浮点格式重新计算这段回答的概率，再根据答对与否更新模型。两边即使刚同步过同一份权重，也不一定算出相同的概率，因为舍入和量化发生在不同位置。

下面只是教学例子：某个已生成 token 在 rollout 端的概率是 0.20，训练端重算为 0.16。用训练概率除以实际生成概率，会得到 0.8。此时权重尚未更新，这个偏离已经存在。它来自执行数值差异，不能全算作模型学习之后的正常策略变化。Jet-RL 研究的正是怎样减少这一类差异，同时保留 FP8 的速度收益。

### 先分清三件事：量化误差、旧权重和随机采样

策略是给定已有文字时，模型对下一个 token 的概率分布。On-policy 可以先理解为：训练数据由所针对的当前策略生成。实际 RL 经常也会重复使用数据或进行重要性修正，所以不能把所有策略差异都直接称为错误；关键是明确数据究竟来自哪个分布，训练目标如何处理它。

权重落后几个版本，是时间上的策略差异；同一版本在两套数值实现上算出不同概率，是执行上的差异；即使概率完全相同，两次随机采样也可能抽出不同 token。检查 mismatch 时应固定权重、输入 token 前缀和采样前的概率计算，再比较同一个位置。只比较两段自由生成的文字，很难分清这三种原因。后一段是本笔记的诊断建议。

### FP8 量化不是只换一种存储类型

FP8 能表示的数值有限。量化通常先选一个尺度，把原来的数除以尺度、舍入到可表示的值；使用时再结合尺度恢复它的大致大小。Jet-RL 使用 E4M3 格式，其最大有限值是 448。尺度越粗糙，少数很大的数就越容易占用表示范围，让其他较小的数被表示得不够精细。

论文因此采用较小的分组：前向激活按 1×128 一组，权重按 128×128 一块，各自使用局部尺度。可以把一行激活理解成某个 token 的一串特征：每连续 128 个特征共享尺度，而不是所有 token 和所有特征共用一个尺度。分组方式也是模型执行的一部分；仅确认两边都写着 FP8，还不足以确认它们做了相同的计算。

### 核心改动：训练时也经过同样的低精度前向路径

普通的 BF16-train / FP8-rollout 配置，在生成端把线性层的输入和权重量化后做乘法，而训练前向仍沿 BF16 路径计算。Jet-RL 把训练前向也改成对应的 FP8 路径：算子之间传什么精度、哪里量化、按多大一组量化，都尽量与生成端对齐。图 5 用计算图表达这一点：推理使用的前向计算被包含在训练图里，边上的精度与量化粒度保持一致。

训练仍保留 BF16 的主权重，用于承接参数更新，再为前向计算得到量化权重。这样不会让每次很小的更新都直接受限于 FP8 可表示的离散值。生成端的权重量化放在参数更新阶段完成；训练端的激活量化可以与前一个算子融合，减少单独启动和搬运开销。这里解释的是论文 §4 的设计，未声称今天任意 verl 或 vLLM 配置已经自动做到这一点。

### 反向传播也加速，但没有把整条链路都变成 FP8

一个线性层除前向矩阵乘法，还要在反向计算两件事：权重应怎样调整，以及输入应接收怎样的梯度。论文把这两类矩阵乘法也交给 FP8 输入的算子，输出保留 BF16；算子之间传递的梯度也保留 BF16，以减少下溢和量化噪声。前向保存、供反向使用的部分激活则保持 FP8。

反向乘法会改变矩阵的使用方向。按一行分组量化的激活，在另一种乘法里可能需要按列分组，因而要重新量化；不能总把转置看成只改一个索引。权重的 128×128 对称分块更方便转置复用。阅读原文时还有一个值得留意的细节：v2 的图 6 图注与 §4.2 正文对 DGrad/WGrad 的两种布局对应关系写反了。本篇不据这一冲突给出可直接照抄的 kernel 配方；实现前应按 §2.2 的矩阵维度和具体源码核对。

### 它减少了什么 mismatch，又没有证明什么？

Jet-RL 主要对齐线性层量化带来的前向差异。相同量化设计仍不自动固定矩阵归约顺序、attention 实现、批次形状、KV cache 精度或分布式通信的数值行为。尤其在 MoE 模型里，专家路由是否一致还需要单独检查；本文评估的主要训练模型不是用来验证大规模 MoE 路由一致性的实验。

所以应把论文支持的结论表述为：在作者所测的配置中，统一精度流程改善了稳定性，并缩小与 BF16 的质量差距。它没有提供所有层、所有 batch 与所有推理引擎逐比特相同的证明。与此前介绍的零差异参考实现对照阅读时，先问“对齐了哪个误差来源”，再问是否满足更强的精确一致性要求。

### 实验怎样做：先看模型、任务和真实的质量差距

论文在 NVIDIA H100 上评估 Llama3.1-8B、Qwen2.5-7B 和 Qwen3-8B-Base 等模型。训练数据包括 GSM8K 与 MATH 的混合，以及更难的 DeepMATH；混合数学任务每个问题生成 4 个回答，DeepMATH 生成 16 个。论文给出学习率 10⁻⁶、batch size 256、KL 系数 10⁻³，并比较 BF16、BF16 训练配 FP8 rollout、Jet-RL。KL 项用于限制模型相对参考策略的偏离。

最直观的一组是表 2：Qwen3-8B-Base、8K rollout、GSM8K+MATH 训练时，所列四个评测的平均分分别是 BF16 63.8、混合方案 60.9、Jet-RL 62.7。Jet-RL 缩小了差距，但仍低 1.1 个百分点。表 3 的同模型 16K 设置里，混合方案未收敛，Jet-RL 得到 61.3，而 BF16 是 64.0，仍差 2.7 个百分点。稳定下来与完全没有质量损失，是两项不同要求。

这些是作者报告的具体任务结果，不是所有 FP8 RL 配置必然崩溃的定理。原文 §3 的部分模型名称、图注与正文也有不一致，本篇采用表 2–3 明确列出的配置作定量比较。它提供了值得复现的风险场景；复现实验还应报告多随机种子的波动，并区分生成长度限制和实际生成长度。

### 速度收益要分清：推理吞吐、单步耗时与最终训练成本

表 4 的 rollout 测速使用 vLLM、H100、512 个 prompt，每个输入 512 token，最大并发 128。32B 模型在 TP=2、8K 输出长度配置下，FP8 相对 BF16 的 token 吞吐是 1.33 倍；同样 32B、8K，TP=4 时只有 1.07 倍。TP 是张量并行，把一次模型计算分到多张 GPU。通信和其他未加速部分占比变大后，低精度矩阵乘法的收益会被稀释。

端到端部分另测 Qwen3-8B、8K rollout：作者报告 RL 单步耗时对应 1.16 倍加速。它不能写成“所有训练都快 33%”，也不能把 32B 的独立推理吞吐直接当成 32B RL 的总收益；论文明确把更大模型的完整训练扩展留作后续工作。若目的是降低科研训练成本，还应衡量达到同一评测目标要多少小时，因为每一步更快与需要多少步共同决定总成本。最后这一指标建议是本篇的系统分析。

### 读完可以提出一个具体、可验证的问题

可以设计如下小实验；这是本篇提出的研究问题，不是论文已经完成的结果。固定一份权重和一批 token 前缀，分别运行 BF16/BF16、BF16/FP8、统一 FP8 三种训推组合。记录每个位置的 log-prob 差值、分布距离及异常值比例，再逐项改变 batch、序列长度、并行度与 attention 实现。这样能查出“统一 FP8 后剩余误差来自哪里”。

之后再把权重版本落后这一因素独立加入。不要一开始同时改变精度、异步程度与采样参数，否则很难把训练崩溃归因到某一机制。最后才做短程 RL，检查数值诊断能否预测质量变化。这个顺序能把系统调试连接到科学问题：需要多强的一致性，才足以稳定学习？

值得精读，先读图 5 和 §4.1，把“BF16 主权重”和“FP8 前向计算”区分开；再读 §4.2，理解分组尺度与反向布局；最后看表 2–4，分别回答稳定性、质量差距和吞吐收益。§2.2 的三个矩阵乘法公式可以在第二遍手推，不需要第一遍先背完整的 GRPO 推导。

## 选读 · Taming the Long-Tail: Efficient Reasoning RL Training with Adaptive Drafter

**年份 / 发表信息：** 2026 · ASPLOS 2026 · MIT / NVIDIA / ETH Zurich / MIT-IBM AI Lab / UMass Amherst · first preprint 2025-11-20; v3 2026-03-20 · [原文](<https://arxiv.org/abs/2511.16665v3>)

**阅读建议：** 值得精读 Figure 8 与 §4.2，理解 drafter 从哪里取数据、在哪些 GPU 上训练、何时让出资源；再读 Figure 14、§5 和 §6.1，分别看调度收益与测量条件。

**再次推荐的原因：** 从研究方向概览转入机制精读：结合 Jet-RL，比较利用长尾空闲资源训练 drafter 与低精度加速的不同取舍。

### 大多数答案已经写完，整轮训练为什么还不能继续？

先看一个自拟例子：四组 GPU 分别为一批数学题生成候选答案。三组已经完成，第四组还剩两道题，一直在尝试不同解法。这一轮需要等所有回答结束才能更新主模型，因此前三组开始等待；第四组虽然仍在工作，却只同时处理很少几个请求。这里的生成过程叫 rollout。少数很长的回答决定了整轮何时结束，这就是长尾问题：既有整组 GPU 闲置，也有仍在生成的 GPU 因并行请求太少而利用不足。[Figure 1 与 §2](https://arxiv.org/html/2511.16665v3#S2)

TLT 同时处理这两种浪费：让仍在生成的请求一次向前推进多个 token；让已完成工作的 GPU 训练一个帮助预测后续 token 的小模型。这个小模型叫 drafter。主模型仍按原来的 RL 流程等待、更新，提前训练的是辅助 drafter，而不是用未收齐的回答提前更新主模型。这个区别决定了它与允许旧策略样本参与更新的异步 RL 是不同方案。[§3 与 §7](https://arxiv.org/html/2511.16665v3#S3)

### 先让小模型提议，再让大模型检查

普通生成每次只向前走一个 token。投机解码则先让 drafter 快速提出多个候选，再让主模型在一次前向计算中并行检查。被接受的一段可以直接成为后续输出；不合适的候选不会因为小模型提出了就强行保留。因此，小模型猜得准主要影响速度，输出仍由主模型的验证规则决定。论文强调保留目标采样分布；这属于算法层面的目标，不能直接当成所有 GPU 内核和精度配置都逐位一致的证明。[§2.2](https://arxiv.org/html/2511.16665v3#S2.SS2)

RL 又带来一个部署推理中没有的麻烦：主模型每轮都会更新，昨天很好用的 drafter 可能越来越猜不中。TLT 默认使用 EAGLE 风格的单层 drafter：可训练核心是一个含 attention 和前馈网络的 Transformer 解码层，复用主模型的词嵌入与输出层，训练 drafter 时冻结这些复用部分。它读取主模型的内部向量来预测后续 token，并随着 RL 继续学习。这里的关键并不是找一个参数更少的完整语言模型，而是减少 drafter 必须串行执行的层数，让一次提议足够便宜。[§4.1 与 Figure 7](https://arxiv.org/html/2511.16665v3#S4.SS1)

### 利用空闲时段训练，也要防止只学到短答案

回到四组 GPU 的例子。协调器发现某组已完成 rollout 并释放推理显存后，才把它切换成辅助训练任务；一个 worker 可以是共同运行一个模型实例的整组 GPU，不一定是一张卡。辅助训练使用已经完成的回答以及主模型生成的内部向量。等待最后的长回答结束后，协调器会停止辅助训练，让主 RL 流程继续。论文把这种可被打断、只利用空闲资源的训练叫 Spot Trainer；它还只保存 drafter 的可训练部分，并异步写检查点，减少被打断时丢失的工作。[§4.2 与 Figure 8](https://arxiv.org/html/2511.16665v3#S4.SS2)

如果只拿最先完成的回答训练，drafter 恰好很少见到最需要加速的长回答。TLT 因此保留跨轮 DataBuffer，把本轮已完成的回答与上一轮的长回答混合起来，同时复用缓存的内部向量，减少重复运行大模型的成本。上一轮的数据略旧，但用途是训练辅助模型，不是直接把旧回答塞进当前主模型的 RL 更新。这里的“利用闲置资源”也不表示计算免费：论文仍报告额外显存、启用投机时重新处理前缀，以及偶发资源竞争等开销。[§4.2 与 §6.4](https://arxiv.org/html/2511.16665v3#S6.SS4)

### 请求越少，值得多猜几步；请求多时可能反而要少猜

一轮开始时，主模型已经能同时处理许多请求；再为每个请求扩展大量候选，可能多花计算、占满显存，甚至变慢。到长尾只剩几个请求时，增加候选才更容易用上闲置算力。TLT 默认在剩余请求数低于 32 时启用投机，并继续调整候选深度及交给主模型检查的 token 数。选择器按 batch 大小划分配置，偶尔试用其他方案，通常选择近期测得吞吐更好的方案。这种在尝试和利用已有经验之间取舍的方法叫多臂老虎机；它追求的是单位时间真正向前推进多少 token，不是单独追求接受率。[§5.1–5.2 与 Figure 14](https://arxiv.org/html/2511.16665v3#S5)

频繁换配置还会遇到 CUDA Graph 的显存成本。CUDA Graph 把一串 GPU 操作预先记录下来，以减少后续逐次启动的开销，但不同形状常需不同的记录。TLT 将相近 batch 大小分组，分别记录 drafter 和主模型，并合并可复用的记录，避免每种组合都额外占一整份空间。训练初期 drafter 尚未准备好时，还可以从同一问题已经生成的回答中检索常见短片段作为候选，再由主模型验证。这是检索式后备方案，不是直接复制答案。[§5 与 Figure 10](https://arxiv.org/html/2511.16665v3#S5)

### 测到了怎样的提速，哪些时间没有被这个数字回答？

实验主要使用最多八台 DGX H100、共 64 张 GPU，也在 A100 上测试。模型覆盖 Qwen2.5-7B、DeepSeek-R1-Distill-Qwen-7B、Qwen2.5-32B 和 Llama-3.3-70B-Instruct；主训练数据是 Eurus-2-RL 的数学与代码子集。采用 GRPO，即比较同一道题的一组回答来形成训练信号，生成温度为 0.9，回答长度上限为 32K token，训练使用 BF16。drafter 另外使用 OpenThoughts2-1M 的子集预热。对照包括论文当时的 VeRL、Open-R1，以及关闭自适应 drafter 的 TLT-Base。[§6.1](https://arxiv.org/html/2511.16665v3#S6.SS1)

Figure 11 报告相对 VeRL 约 1.7–2.1 倍的端到端吞吐，但指标是“一个全局 batch 的提示词与回答 token 总数 ÷ 一个 RL step 耗时”，预热后只平均三个 step，并使用已训练的 drafter。因此，它包含每步的生成和训练阶段，却不能回答冷启动、预热和完整收敛总共能省多少时间。规模也会改变收益：Table 3 的 Qwen2.5-7B 从单节点的 1.21 倍增至八节点的 1.76 倍。Figure 12 中两种 Qwen 模型的平均 reward 曲线接近，支持所测训练行为没有明显受损；它不是所有任务上最终能力完全相同的保证。[§6.1–6.3、Figures 11–12 与 Table 3](https://arxiv.org/html/2511.16665v3#S6)

### 读完之后，怎样把它变成自己的系统问题？

先看 Figure 8，画出主模型与 drafter 各自何时训练；再看 Figure 14，理解为什么投机策略应随剩余请求改变；最后读 §6.1 的测量方法和 §7 的适用范围。论文在 §7 提到：agent 等待工具执行时可能仍占用 KV cache，却不做 GPU 解码；这会减少活跃请求，为投机解码创造机会。但这只是提出的后续方向，没有在本文中完成多轮工具实验。一个可继续研究的问题是：等待期间保留多少缓存、是否真有可供训练的空闲 worker、候选验证还剩多少显存；这些是本文引出的系统问题，不能直接套用论文提速数字。

## 选读 · Stable Asynchrony: Variance-Controlled Off-Policy RL for LLMs

**年份 / 发表信息：** 2026 · ICML 2026 · MIT / NVIDIA · PMLR 306 · [原文](<https://proceedings.mlr.press/v306/huang26ca.html>)

**阅读建议：** 值得精读 §2.2、§3.2–3.5；先看图 1–2，再核表 1、附录 B 与 F.4。

**再次推荐的原因：** 从研究方向概览转入机制精读：结合 Jet-RL，区分数值实现差异与旧策略样本造成的更新波动。

### 为什么旧模型生成的好答案，也可能让训练不稳定？

想象一台机器还在生成第 10 版模型的解答，另一台已经把参数更新到第 12 版。参数就是决定模型如何预测的数值；同一道题，两版模型选择各个 token 的概率可能不同。这叫使用旧策略样本：生成答案的策略与正在训练的策略不同。异步训练允许两边同时工作，减少等待，却也让这种差异持续存在。

训练通常乘上重要性权重 w＝当前策略生成这条完整解答的概率÷实际采样策略生成它的概率，修正“这些解答来自另一种分布”。教学例子：某条解答在当前模型下的概率是采样时的 20 倍，它就可能得到 20 倍权重。整段概率又由逐 token 概率相乘，长回答中的小差异可以累积成大差异。于是看似有很多解答，一次更新却主要由少数几条决定；换一批解答，更新方向和幅度就可能大幅波动。这种波动叫方差大，并不是说那些答案一定错误。[§2.1–2.2](https://arxiv.org/html/2602.17616v2#S2.SS2)

### 第一道控制：实际只剩几条样本在起作用，就少走一步

VCPO 用有效样本量 ESS＝(Σw)²/Σ(w²) 衡量权重是否集中。B 条样本权重一样时，ESS＝B；几乎全靠一条时，ESS 接近 1。它是权重退化的诊断量，不是在重新数正确答案，也不是对梯度方差的无条件精确测量。论文观察到，ESS 比例下降往往早于策略差异暴涨和训练成绩崩塌，因此用它决定这一步该有多谨慎。

先计算 ρ＝ESS/B，再把学习率改为 η_eff＝η×√(ρ_off/ρ_on)。学习率控制本次参数移动的幅度；ρ_on 来自开始时一次或几次同步更新，而非一律假定等于 1。教学例子：若同步参考为 1，本批 100 条样本的 ESS 只有 4，学习率变成原来的 0.2 倍。这是有实验支持的缩放规则，不是保证永不崩溃的定理。最终更新还会截断过大的权重，但计算 ESS 使用未截断的权重，避免把危险程度也一起遮住。[§3.2、§3.5](https://arxiv.org/html/2602.17616v2#S3.SS2)

### 第二道控制：奖励减去什么数，才能让更新少抖一点？

奖励基线 b 是从奖励 R 中减掉的参考值：模型根据 R−b 学习，而不只是看到一个绝对分数。常见办法是取一组奖励的均值。VCPO 注意到，异步时各条轨迹对更新的影响相差很大，因此用 w²×||g||² 给奖励加权，再求平均作为基线；g 表示让这条解答更可能出现时，参数应朝哪个方向变化，||g|| 是这个向量的大小。被重要性权重放大、同时梯度又大的轨迹，更应该影响这个降噪用的参考值。[§3.3](https://arxiv.org/html/2602.17616v2#S3.SS3)

“最小方差”有范围：附录 B 在完整重要性采样等假设下，对一个标量基线推导最优值；实际用当前小批量的数据代替总体期望，是估计值。完整 VCPO 还使用权重上限 8 的序列级截断，所以不能把最终算法整体说成严格无偏，也不能把基线说成预测每一步价值的额外模型。正式版也指出，这个最优基线形式已有先例；本文的实际贡献包括高效获取精确的逐轨迹梯度统计，并与 ESS 调步长结合。[正式版 §3.3–3.5、附录 B](https://raw.githubusercontent.com/mlresearch/v306/main/assets/huang26ca/huang26ca.pdf#page=6)

### 怎样得到梯度统计，又不为基线多做一轮反向传播？

直观做法要先算每条轨迹的梯度大小，求出基线，再重新反向传播一次。论文把更新展开成两份累计量：一份累计 wR·g，另一份累计 w·g。每条轨迹只反向传播一次，同时保存这两份和梯度大小；等基线求出后，组合成“第一份−b×第二份”。数据并行的梯度同步也延后，先保留本地轨迹统计，最后再汇总组合后的梯度。[§3.4、附录 C](https://arxiv.org/html/2602.17616v2#S3.SS4)

这仍有成本。图 3 的 Qwen2.5-7B、4 张 H100、张量并行 TP=4、序列长 8,192 的测量中，单步时间开销为 19%，内存开销为 14%；省掉的是朴素方案额外的一轮反向传播，不是把开销变成零。因此判断它值不值，要看训练达到目标质量的总时间，而不能只比较一次更新有多快。

### 2.5 倍加速，和 128 步滞后，分别说明什么？

最贴近 agent 的实验用 Qwen2.5-7B Base，在 DAPO-17K 上按 SimpleTIR 方式训练交替推理和调用工具的能力，在 AIME 2025 检查最终答案。每批 128 道题、每题 16 条回答，回答上限 12,288 token，最多 5 次工具调用；2 张 B200 生成、2 张训练。这里策略最多落后 2 步。图 1 中，VCPO 约 42 小时达到同步方案约 105 小时的最佳验证准确率，因此报告约 2.5 倍的到达目标质量加速。这不是生成 token 吞吐提高 2.5 倍，也不是同样更新次数的纯系统比较。[图 1、§4.5、附录 F.4](https://arxiv.org/html/2602.17616v2#S4.SS5)

另一个实验把 Qwen2.5-7B 的策略滞后提高到 128 步，观察是否还能稳定学习，这是图 6 的压力测试。作者说明相关实验的异步提速在约 10 步滞后时已经饱和，继续加大滞后主要是在检验稳定性。不能把这项结果改写成“工具 agent 可以放心落后 128 步”，更不能把 128 当成加速倍数。[§4.4、图 6](https://arxiv.org/html/2602.17616v2#S4.SS4)
