## 主读 · HybridFlow: A Flexible and Efficient RLHF Framework

**年份 / 发表信息：** 2025 · EuroSys 2025 · preprint 2024 · [原文](<https://i.cs.hku.hk/~cwu/papers/gmsheng-eurosys25.pdf>)

**阅读建议：** 本期主读，值得精读。先花约 30 分钟画出生成回答、准备训练数据、更新模型这三个阶段，再标出每个阶段使用哪些 GPU、权重什么时候搬动。最后读单/多控制器与 3D-HybridEngine。

### 先认清这篇论文：HybridFlow 就是 verl 的论文

**HybridFlow 就是 verl 框架对应的那篇论文。** 它来自香港大学与 ByteDance，预印本发表于 2024 年，正式发表于 EuroSys 2025。理解它，可以先从一轮训练的操作入手：让模型生成回答，给回答打分，用这些结果更新模型，再把更新后的模型交给生成引擎，开始下一轮。

这一轮里不只有“模型生成回答”在花时间。几个模型要互相交接数据，训练后的权重还要变成生成引擎能用的形式。因此，即使生成快了，等待、搬运和切换阶段的时间仍可能让整轮很慢。HybridFlow 分别处理三件事：怎样指挥多个模型协作；怎样减少训练与生成切换时的重复工作；怎样把这些模型安排到 GPU 上，让整轮更早结束。[原论文 §3、Fig. 4](https://i.cs.hku.hk/~cwu/papers/gmsheng-eurosys25.pdf#page=6)

### 为什么一个模型变快，整轮训练还可能很慢

先以 PPO 为例。它是一种根据奖励反馈来更新模型的强化学习算法，这里的训练流程有四个角色：actor 是要训练的模型，负责生成回答；reference 是参照模型，提供它生成同一回答时的概率信息；reward model 为回答打分；critic 则预测从当前状态继续，预期能获得多少奖励。这种对未来奖励的估计叫价值，用来帮助判断实际表现比预期好还是差。最后需要训练的是 actor 和 critic。一个模型完成工作后，其他模型还要接着处理，所以只加速其中一个环节，并不等于整轮按相同比例加速。[原论文 §2.1–2.3、Fig. 1–3](https://i.cs.hku.hk/~cwu/papers/gmsheng-eurosys25.pdf#page=3)

这些工作使用 GPU 的方式也不同。生成要一个 token 接一个 token 地往后算；训练则要反向传播，并保存梯度和优化器状态。为生成选的多卡分工，未必也适合训练。所谓“并行配置”，就是决定哪些 GPU 合作算一个模型、哪些 GPU 各自处理不同样本。

三个缩写可以这样记：DP（数据并行）放置多个模型副本，让它们处理不同样本；TP（张量并行）把同一层的计算拆给多张卡；PP（流水线并行）把不同层分到不同阶段。先知道各自在拆什么即可，不要求先推完 PPO 的损失函数。

读图时还要注意 node 的含义。论文图中的一个节点表示一次分布式模型计算，可能已经横跨多台机器。因此 intra-node / inter-node 在这里说的是“这次模型计算内部”与“不同模型计算之间”，不能直接翻译成“同一台服务器内”与“跨服务器”。

### 跟着一批问题，走完生成、打分和更新

**第一步：生成回答。** 把一批输入问题（prompts）分给 actor 的生成副本，用当前权重产生回答（responses）。这一步就是 rollout 的主要生成工作。要看每个副本分到了多少请求、能同时生成多少条，以及 KV cache 是否装得下。KV cache 保存已经计算过的历史信息，供后续 token 继续使用。

**第二步：准备训练要用的数据。** 把问题和回答交给 reference、reward model 和 critic，分别取得参照概率、奖励分数和价值估计。再据此计算 advantage 等训练量。这里可以先把 advantage 理解为“这次表现比预期好还是差”的估计，训练用它决定怎样调整生成回答的模型。PPO 还需要生成这批回答时的策略概率；官方例子中显式保留了 `old_log_prob`。[原论文 Fig. 1、Fig. 6](https://i.cs.hku.hk/~cwu/papers/gmsheng-eurosys25.pdf#page=7)；[官方 PPO 示例](https://verl.readthedocs.io/en/latest/hybrid_flow.html#ppo-main-loop)

交接数据本身也需要安排。如果 actor 和 reward model 的副本数不同，actor 原来分好的那几批数据，就不能直接原样交给 reward model。框架要按接收方各个副本的分工重新分配。论文中的 collect/distribute，处理的就是这类收集与分发。

**第三步：更新模型。** actor 与 critic 用准备好的数据执行训练。若两个计算共用一批 GPU，通常要先后执行；若使用各自的 GPU，且所需输入都已就绪，就可以并行。**第四步：准备下一轮生成。** 把更新后的 actor 权重交给生成引擎，并按引擎的多卡分工重新组织。reference 并不会每轮都跟着 actor 一起更新；GRPO、ReMax 等算法的角色和步骤也不同，不能把 PPO 的四模型图套到所有算法上。

### 谁来指挥这些工作：大步骤集中安排，模型内部各自执行

可以先把 controller 理解为“发出工作指令的进程”。只用一个控制进程，容易写出“先生成、再评分、再训练”的程序，这叫 single-controller。但如果连模型内部的大量算子也要由它逐个安排，中心进程的调度就会成为负担。

另一种方式是让多个 worker 进程各自运行分布式程序，这叫 multi-controller。它减少了逐个调度算子的开销，但程序员也更容易把模型计算、多卡集体通信（collective）和模型之间的数据收发混在一起。HybridFlow 结合两种做法：多个模型之间的大步骤由一个控制器安排，每个模型内部的多卡计算仍交给各个 worker 执行。[原论文 §2.2、§4、Fig. 2](https://i.cs.hku.hk/~cwu/papers/gmsheng-eurosys25.pdf#page=3)

对应到接口，ParallelWorker 封装模型计算，ResourcePool 记录可用 GPU 及模型放在哪，transfer protocol 规定数据怎样收集和分发。Fig. 5 中控制器传递的 data future，可以理解为“稍后取得结果的引用”。接收方 worker 根据自己的 DP rank，也就是副本编号，取到该处理的数据。图中箭头经过控制器，不代表所有大张量都要先绕到控制器的 CPU。[原论文 §4.1、Fig. 5](https://i.cs.hku.hk/~cwu/papers/gmsheng-eurosys25.pdf#page=7)

这里的异步调用表示发出指令后不必立刻等结果，输入准备好后相应工作才能推进。它本身还不能说明整个 RL 训练已经允许不同策略版本的生成和训练完全异步运行。

### 3D-HybridEngine：同一批 GPU，为何需要两套分工

论文让 actor 的训练和生成轮流使用同一组 GPU，但不强求它们采用相同的分工。训练可能适合让更多卡合作算一个副本；生成则可能适合减少每个副本占用的卡数，多放几个副本同时处理请求。这种“每张卡保存哪部分权重、和哪些卡合作”的安排，就是这里说的布局。

论文把训练配置写成 `(p,t,d)`，依次是 PP、TP、DP 的数量；生成配置写成 `(p_g,t_g,d_g,d)`。其中 `d_g` 表示一个训练副本拆成了多少个生成副本，论文称为 micro-DP。GPU 总数不变，因此 `N_a = ptd = p_g t_g d_g d`，也就有 `d_g = pt/(p_g t_g)`。这些符号只是用来数清楚卡怎样重新分组。[原论文 §5.1–5.2、Fig. 7](https://i.cs.hku.hk/~cwu/papers/gmsheng-eurosys25.pdf#page=8)

不过，每个生成副本少用几张卡，也会改变每张卡要保存的模型权重和 KV 数量。减少 TP/PP 可以增加副本、降低某些通信成本，却不是越小越好。Fig. 15 固定使用 16 张 GPU、训练配置 `(1,8,2)`，7B 和 13B 模型各自较好的生成 TP 就不同。

### 怎样少存一份权重：让生成需要的分片包含已有分片

先把“权重分片”理解为每张 GPU 保存的那部分模型参数。切换到生成时，如果新分工需要的参数和卡上原有参数对不上，就可能既留着训练那份，又准备另一份生成用的参数。3D-HybridEngine 要减少的，正是这种切换造成的重复保存。

Fig. 8 使用 8 张卡。训练时，TP 组是 `[G1,G2,G3,G4]` 和 `[G5,G6,G7,G8]`；生成时希望每组只用 2 张卡。若直接把相邻编号的卡组成生成 TP 组，部分卡就会遇到上述错位。HybridFlow 改用 `[G1,G3]`、`[G2,G4]` 等生成 TP 组，再让 `[G1,G2]`、`[G3,G4]` 等 micro-DP 组做 all-gather，也就是互相收集对方持有的权重。这样每张卡保留已有训练分片，只补上生成所缺的部分。[原论文 §5.3、Fig. 8](https://i.cs.hku.hk/~cwu/papers/gmsheng-eurosys25.pdf#page=8)

![一个训练副本的四张 GPU：训练时四卡合作，生成时改为 G1/G3 与 G2/G4 两组；交换补齐权重后，每张卡仍保留原有训练分片。](CN/reading/figures/hybridflow-layout.png)

这张图按论文 Fig. 8 原理简化，只画一个训练副本的 4 张卡。A/B/C/D 表示权重分片，不包括 KV、梯度或优化器状态。读图时只跟踪两件事：每张卡原有哪一份参数，以及重新分组后还缺哪一份。

Table 2 所说的“零冗余”，范围仅限切换分片造成的额外 GPU 权重存储。模型权重的峰值存储量等于生成分片大小 `M/(t_g p_g)`，其中 M 是模型权重总量。它不表示不用通信、训练全程不需要额外显存，也不表示实现中只有一个物理 buffer。§7 仍描述了分开的训练／生成 buffer、把数据移到 CPU 的 offload，以及通过多卡通信库 NCCL 收集数据。[原论文 §5.4 Table 2、§7](https://i.cs.hku.hk/~cwu/papers/gmsheng-eurosys25.pdf#page=9)

同样，把 KV 暂时搬到 CPU 保存，只说明保存位置变了；它不能证明模型权重更新以后，旧权重算出来的 KV 或其他激活仍可直接使用。

### 模型共用 GPU 还是各用一组，要算整轮多久结束

如果两个计算共用 GPU、先后执行，这个阶段的时间要把两项加起来；如果它们在不同 GPU 上同时执行，就要等较慢的一项结束。再把各阶段时间加起来，才得到一轮训练的预计耗时。这里关心的是最后什么时候能开始下一轮，而不是某一项单独跑得多快。

§6 的 auto-mapping 在训练开始前尝试不同方案：哪些模型共用 GPU、每个模型分几张卡、采用什么并行配置，再用模拟器估算整轮时间。Fig. 12–13 表明，较好的方案会随 GPU 总数和模型组合变化。因此论文没有给出“永远共用”或“永远分开”的答案。这套搜索也不是工具调用发生后，立刻在线重排资源的调度器。[原论文 §6 Algorithm 1、§8.3](https://i.cs.hku.hk/~cwu/papers/gmsheng-eurosys25.pdf#page=10)

### 加速数字成立在哪些实验条件下

主实验最多使用 16 台机器、128 张 A100-80GB，每台 8 张卡。论文报告机内 NVLink 带宽为 600 GB/s，机间为 200 Gbps。模型是 7B–70B Llama，算法覆盖 PPO、ReMax、Safe-RLHF。主要端到端比较使用同规模的 actor、reference、critic 和 reward model；另有模型大小不同的放置实验。[原论文 §8.1–8.3](https://i.cs.hku.hk/~cwu/papers/gmsheng-eurosys25.pdf#page=10)

**输入与输出长度各固定为 1024 token，一整批共 1024 个样本；先预热 10 轮，再取 5 轮平均。** 论文计算吞吐时，把整批输入和输出的 token 总数，除以完整一轮 RL 的耗时。作者让输出等长，是为了控制各基线支持连续批处理的能力差异，而不是模拟所有真实请求都一样长。[原论文 §8.1](https://i.cs.hku.hk/~cwu/papers/gmsheng-eurosys25.pdf#page=11)

摘要中的 1.53–20.57× 来自不同模型规模、算法和基线，不能理解为对同一个当前最强基线都能提升这么多。比较的版本分别是 DeepSpeed-Chat 0.14.0、OpenRLHF 0.2.5、NeMo-Aligner 0.2.0。Fig. 9–11 看整轮收益，Fig. 14 看切换时间，Fig. 15 把切换和生成一起算。局部少花了多少时间，最终还要放回整轮里核对。

还有两条限制需要保留。自动放置的基本设定是 GPU 同质，并依赖对输入形状和各阶段耗时的估计；吞吐提升也不等于已经证明训练收敛更快或最终奖励更高。换负载、硬件或基线版本后，应重新测量到底在等哪一步，并同时检查训练质量。[原论文 §6、§8](https://i.cs.hku.hk/~cwu/papers/gmsheng-eurosys25.pdf#page=10)

### 用它排查 rollout/refit：先分清到底在等什么

**以下是系统分析，不是论文新增实验。** refit 在这里指把训练后的新权重交给推理引擎使用。可把它拆成四段计时：从训练端导出权重并重新分片；传到目标位置；由推理引擎装载；恢复继续执行所需的缓存和状态。3D-HybridEngine 主要处理分片与搬运中的重复工作。具体引擎的装载、量化格式转换等成本，仍需单独量。

多轮 agent 还会等待工具返回。一条“轨迹”就是一次任务中连续发生的生成与工具交互；不同轨迹完成时间可能差很多。如果训练更新要等整批轨迹都结束，少数最慢的轨迹就会拖住下一阶段。比较共卡切换和分卡同步时，应同时记录最慢请求的等待、训练端空等时间、每秒有效轨迹数、采样策略比当前训练版本落后多少，以及最终任务质量。**原论文固定等长生成的实验，没有证明这些长尾问题已经解决。**

实际排查可以按三个问题走：GPU 是否还在等最后一条轨迹？新权重是否已经备好，却卡在推理引擎装载？下一批是否因为缓存失效而重新处理整段前缀，也就是重复 prefill？这些现象都可能被笼统地称为“rollout 慢”，但分别涉及整批等待、权重更新和缓存重建，只调一个 TP 数值并不能覆盖它们。

### 当前 verl 怎样实现，还要和老论文分开看

截至 2026-10-15 查阅的官方文档，worker 入口已经统一到 `engine_workers`。其中 `update_weights` 区分两条路径：训练与生成共置时直接更新；分离时通过 `checkpoint-engine` 传输权重。所以，论文中的旧类名和 3D 分组方式，不能直接当作每个当前后端的实现说明。本节只依据文档，没有声称实际运行并验证过某一配置。[Engine Workers](https://verl.readthedocs.io/en/latest/workers/engine_workers.html)

当前 Agent Loop 另外描述了多轮交互。`response_mask` 用于区分哪些 token 由模型生成、哪些来自工具返回。V1 Async Trainer 还处理未完成轨迹的恢复，以及同一轨迹跨越策略版本时的版本跨度和陈旧度；恢复执行时可能需要重建前缀 KV。它们都是论文之后的发展，不能倒写成原始 HybridFlow 已经完成的实验。[Agent Loop](https://verl.readthedocs.io/en/latest/advance/agent_loop.html)；[V1 Async Trainer](https://verl.readthedocs.io/en/latest/advance/v1_async_trainer.html)

### 精读时只抓三件事：谁发指令、数据去哪、权重怎么分

先看 Fig. 1/2/5，画出一批问题经过哪些模型，并分清指令和大张量各自走哪条路。再看 Fig. 7/8，手算一次切换：每张卡原有什么权重、生成时还需要什么。最后对照 Table 2 和 §8，确认节省的是哪部分内存或时间，以及实验用了什么条件。

读完后尝试回答三个问题：控制器实际传递了什么，大张量又由谁取得？切换前后，每张 GPU 保存的参数分别是什么？如果生成过程夹着很慢的工具调用，原论文计算整轮时间的方式还缺了哪些等待？能讲清这三件事，就抓住了它与你当前系统工作的连接。

## 选读 · SGLang: Efficient Execution of Structured Language Model Programs

**年份 / 发表信息：** 2024 · NeurIPS 2024 · [原文](<https://proceedings.nips.cc/paper_files/paper/2024/hash/724be4472168f31ba1c9ac630f15dec8-Abstract-Conference.html>)

**阅读建议：** 值得结合源码精读。先分清 Full/SWA/Mamba 各自需要保存什么，再看 HiCache 把它们放在哪里，最后跟着工具返回的例子检查能从何处继续。源码核验日期为 2026-10-15，固定到 commit f2b73d4。

### 先看具体问题：第二次调用，为什么还要重算旧对话

**值得精读，第一次先聚焦缓存。** 多次调用模型时，输入的开头常常相同。前缀缓存想做的是：把这段历史已经算出的状态留下，下次直接接着用，减少重新处理输入的工作。处理输入前缀的这一步叫 prefill。

原论文中的 RadixAttention 用基数树组织这些公共前缀，可以先把它理解成“相同的开头走同一条树路径，后面不同的内容再分叉”。系统还要决定哪些缓存留下、哪些驱逐，以及请求先后怎样执行，才能把重复 prefill 减少下来。[原论文 §3](https://arxiv.org/html/2312.07104v2#S3)

2024 年论文帮助理解复用的动机；下面读的是固定提交 `f2b73d4` 的代码，重点是当前实现保存什么状态、满足什么条件才能继续计算。两者不能当作同一版本的说明书。

### 缓存先问两件事：要保存什么，保存在哪里

先看“保存什么”。Full 对应全注意力层保存的历史 KV；SWA 是 Sliding Window Attention，即滑动窗口注意力，只需要相应窗口内的 KV；Mamba 这类递推层则需要在某个位置保存的循环状态快照。可以先把快照理解为“算到这里时留下的一份内部状态”，后面要从它继续。三种状态不能只按 token 数一概而论。

再看“保存在哪里”。HiCache 处理 GPU、CPU 主存和存储之间的分层。Full/SWA/Mamba 说明模型运行需要什么，HiCache 说明这些东西目前在哪，因此两者可以组合。普通 full-attention 模型也可走 UnifiedRadixCache，并不是只有混合模型才用这棵统一树。

固定提交的 [registry.py](https://github.com/sgl-project/sglang/blob/f2b73d4f9b4e64415b8d775b0f811c7801f1728b/python/sglang/srt/mem_cache/registry.py#L150-L199) 在这条路径中装配 Full 组件；模型需要 SWA 或 Mamba 时，再加入对应组件，并按配置接入 HiCache。[纯 SWA 还有单独的选择分支](https://github.com/sgl-project/sglang/blob/f2b73d4f9b4e64415b8d775b0f811c7801f1728b/python/sglang/srt/mem_cache/registry.py#L127-L130)，所以不能说所有模型都只走这一种实现。

查缓存时，“找到相同的 token”只是开始。[树核心](https://github.com/sgl-project/sglang/blob/f2b73d4f9b4e64415b8d775b0f811c7801f1728b/python/sglang/srt/mem_cache/unified_cache/unified_tree_core.py#L917-L970) 还会让各组件检查：我在这个位置继续计算所需的状态齐了吗？必须全部通过，才能把它当成可直接恢复的位置。代码因此分别记录 Full-KV 命中了多长，以及整个模型能从哪里恢复；前者可能更长。

另外，即使所需状态都在 CPU 主存里找到了，也还不能立即在 GPU 上执行。把它搬回 GPU 是另一步。这就是为什么缓存命中长度、可恢复位置和实际恢复耗时需要分开看。

### 工具返回后，为什么相同的 4096 个 token 还不够

**下面是教学例子，数字仅作示意。** 一个编码 agent 写到第 4096 个 token 时调用测试工具，等结果回来后，把工具输出接到原有历史后面。假设模型和输入设置都没变，旧的 4096 个 token 完全相同，示意位置也都已对齐。我们要问的不是“文字一样吗”，而是“各层继续计算需要的状态还在吗”。

先看 Full 层。如果这整段历史的 KV 都保留着，它就有复用 4096 个 token 的基础。再看窗口长度为 1024 的 SWA 层：它需要的是对应窗口内完整的状态。假如最后一窗少了一页，Full 层保留得再完整，也补不上 SWA 这一页；模型不能因此直接从 4096 处继续，而要找到有效窗口边界或补算缺失状态。

这个例子依据 [SWA 检查与结果处理](https://github.com/sgl-project/sglang/blob/f2b73d4f9b4e64415b8d775b0f811c7801f1728b/python/sglang/srt/mem_cache/unified_cache/components/swa.py#L355-L421)：遇到缺失状态时，连续覆盖长度会重新计起。因此 Full 命中可以长于 SWA 可用的边界。主存副本可以参与匹配，但使用前仍要恢复到设备。这里说的是树保存窗口状态的路径；代码还单独处理了每个请求独占的环形缓冲区，不能混为同一种情况。

如果模型还有 Mamba 层，再检查它的快照。假设只保留了 3072 处的循环状态，那么即使历史 token 一字不差，也不能宣称拥有 4096 处的状态。需要从有效检查点继续计算。[Mamba 的检查与分支位置逻辑](https://github.com/sgl-project/sglang/blob/f2b73d4f9b4e64415b8d775b0f811c7801f1728b/python/sglang/srt/mem_cache/unified_cache/components/mamba.py#L147-L190) 要求节点上实际有状态；[把树节点拆开](https://github.com/sgl-project/sglang/blob/f2b73d4f9b4e64415b8d775b0f811c7801f1728b/python/sglang/srt/mem_cache/unified_cache/components/mamba.py#L309-L319)，也不会自动算出新边界的快照。

因此，混合模型要同时满足它包含的所有组件。能直接继续的位置，不能只由 Full 的最长命中决定；但较长的 Full 命中也不是毫无用处，它仍可能帮助后续恢复。

### HiCache：在主存找到缓存之后，还要把它搬回来

HiCache 处理的是存放和搬运。[控制器](https://github.com/sgl-project/sglang/blob/f2b73d4f9b4e64415b8d775b0f811c7801f1728b/python/sglang/srt/mem_cache/hybrid_cache/hybrid_cache_controller.py#L964-L1035) 会把主存到设备的恢复工作加入队列，也会提交从存储提前读取的预取请求；[查询存储的逻辑](https://github.com/sgl-project/sglang/blob/f2b73d4f9b4e64415b8d775b0f811c7801f1728b/python/sglang/srt/mem_cache/hybrid_cache/hybrid_cache_controller.py#L1348-L1412) 还分别处理各状态池的命中信息。

所以，“CPU 内存里还留着”只说明不用从头重算那一份状态，不等于“GPU 现在已经能继续”。恢复过程中仍可能有排队和搬运。测量时应把找到状态与完成恢复分开，不能只用一个命中率代表两者，也不能把 HiCache 当成与 Full/SWA/Mamba 并列的第四种模型状态。

### 对 agent 缓存调度的启发：保住哪些东西才有用

**以下是系统推导，不是上述文件给出的实测结论。** agent 等工具时，可以选择把状态留在 GPU、搬到主存，或者释放后重新计算。但做选择之前，应先问：要让这个模型低成本地继续，究竟必须保住哪几份状态？只记录“留下多少 token”会漏掉窗口缺页或循环快照缺失的问题。

可以分别记录：能从第几个 token 恢复；Full、SWA、循环状态各保留了多少；恢复搬运花多久；缺失部分又补算了多久。再用这些量比较保留、下放和重算的实际代价。这里说的恢复只覆盖模型一侧，工具容器、会话已经产生的副作用，以及训练优化器状态，都仍需另行管理。

### 源码阅读顺序：先确定组件，再跟一次恢复

先读原论文 §3 和 Figure 3，看懂公共前缀为什么值得复用。然后打开 registry，确认某个模型选中了哪些缓存组件；接着看 SWA/Mamba 的检查条件，最后沿控制器的 load/prefetch 路径，追踪状态怎样从主存或存储回到 GPU。

第一次读到能解释上面的工具返回例子即可：文字相同，为什么仍可能要搬运或补算？这能帮助你把 agent KV 调度需要管理的状态说清楚。但这些文件本身没有证明，工具等待期间究竟哪一种保留策略最优；那仍要结合负载测量。

## 选读 · Ray: A Distributed Framework for Emerging AI Applications

**年份 / 发表信息：** 2018 · OSDI 2018 · [原文](<https://www.usenix.org/conference/osdi18/presentation/moritz>)

**阅读建议：** 选择性阅读 task/actor 和调度设计。先尝试解释：rollout worker 为什么要长期存在，模型引擎放在哪里，一批输出又怎样交给下一步。

### HybridFlow 安排训练步骤，Ray 让远程进程做这些事

在控制进程里写下“生成回答，然后计算 reward”还不够：生成可能在另一台机器，评分又可能由另一组进程完成。还需要一种方式发出远程调用、找到执行它的 worker，并把结果交给下一步。Ray 提供的就是这层基础能力。

2018 年论文把 task 和 actor 放进同一框架，也允许后续任务随着前面的结果动态出现，并把工作调度到不同机器。阅读时先分清三个问题：训练算法规定什么时候进入下一步；执行框架安排哪个进程来做；数据传输机制负责把张量送过去。它们相关，但不是同一件事。[OSDI 原论文与报告](https://www.usenix.org/conference/osdi18/presentation/moritz)

### 从远程函数到常驻 worker：task、actor 和结果引用

如果只想“请另一进程执行一次函数”，可以用 task。如果想“让另一进程先加载模型，以后多次调用都继续用这个模型”，就需要长期保存状态的 actor。actor 的方法可以读取或修改此前留下的状态。对初始化很贵的 rollout 引擎，后者的价值就在于后续请求能够继续使用已经初始化的引擎。[当前 actor 文档](https://docs.ray.io/en/latest/ray-core/actors.html)

注意同名词的区别：Ray 的 actor 指一种常驻、有状态的进程；PPO 的 actor 指被训练的策略模型。前者讲程序怎样运行，后者讲训练里的模型角色，不能见到 actor 就混成一个概念。

远程调用通常先返回一个 ObjectRef，即结果的引用。可以把它理解成领取结果的凭据：此刻结果未必已经算完，但后续工作可以声明“我要用这个结果”，不必立刻把整份数据取回控制进程。这种尚未完成也能传递的结果引用，通常叫 future。

Ray 的远程对象不可变，数据可能保存在不同机器的对象存储中。控制进程拿到了引用，不代表大张量已经搬到了控制进程所在机器。读代码时，要把“引用传到了哪”与“实际数据存在哪”分开。[当前对象文档](https://docs.ray.io/en/latest/ray-core/objects.html)

### 调试例子：generate 已经提交，GPU 为什么还没有工作

**下面是排查思路，不是论文实验。** 假设控制进程提交了 `generate`，之后准备算 reward。提交调用只表示发出了工作请求。先查执行它的 worker 是否启动、资源是否拿到；再查输入是否都已生成，或是否仍在从另一台机器传过来；最后才查模型计算是否真正开始。三种等待原因不同，不能都归结为“Ray 慢”。

即使某个 ObjectRef 对应的结果已经就绪，也不能据此断定生成时用了正确版本的策略权重。可以为每批数据附上 policy version，也就是生成它的模型版本，并记录五个时刻：请求提交、输入就绪、第一项 GPU 工作开始、整批生成结束、新权重安装完成。这样才能把发指令、搬数据、计算和切换权重的时间拆开。这个观测方案需要在应用中实现和验证，不是 Ray 自动保证的性质。

### 声明半张 GPU，为什么不会自动得到半份显存

写 `num_gpus=0.5`，是告诉调度器这个 actor 需要多少逻辑资源，从而允许多个 actor 共享一张可见 GPU。它不等于“显存已经切成两半，双方互不影响”。Ray 通过 `CUDA_VISIBLE_DEVICES` 设置进程可以看到的设备；模型、KV、临时张量和通信 buffer 实际占多少显存，仍由应用负责。[资源与 fractional GPU 文档](https://docs.ray.io/en/latest/ray-core/scheduling/resources.html)

**以下是系统推导：** trainer 和 rollout 引擎若轮流使用同一批 GPU，还得约定交接步骤：谁先释放 KV，优化器状态什么时候移到别处，哪些进程建立通信组，新权重何时才算更新完。资源声明只帮助安排进程放在哪，不能替代这些操作。因此，把两个进程各写成半张 GPU，还不足以证明它们可以安全、高效地共用设备。

### 先读到能画出自己的 worker 和数据流就够了

建议先选读 task/actor、任务如何等待输入，以及调度器怎样安排执行，不必一开始追完全部故障恢复实现。先修只需进程、远程调用和刚才解释的 future。读完后画自己的程序：哪些模型状态一直留在 actor 内，哪些批数据只传递引用，哪些模型之间的通信另走专用路径。

论文用来理解 2018 年的设计，本文提到的 API 行为依据 2026-10-15 查阅的官方文档。论文每秒能执行多少 task，不能直接换算成 LLM rollout 每秒能生成多少回答；你仍需分别测量调度、传输和模型计算。也可对照站内 [[CN/wiki/rl-infra/rl-training-frameworks|RL 训练框架]]，看清 Ray 与上层训练算法框架各负责什么。

## 选读 · DistServe: Disaggregating Prefill and Decoding for Goodput-optimized Large Language Model Serving

**年份 / 发表信息：** 2024 · OSDI 2024 · [原文](<https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin>)

**阅读建议：** 值得精读，可以放在主读之后另找时间。先弄懂“处理得多”和“在规定时间内处理得多”的区别，再看分开配置 GPU 的收益能否覆盖 KV 传输。

### Orca 和 PagedAttention 之后，再问两种计算要不要分开

Orca 讨论请求怎样随每轮生成进入或离开 batch，PagedAttention 讨论历史 KV 怎样更有效地使用显存。DistServe 继续问：处理输入和逐个生成输出，是否一定要挤在同一组 GPU 上，并采用相同的多卡分工？

这里先分清两个阶段。prefill 处理输入前缀，decode 在已有状态上继续逐 token 生成。用户从发出请求到看到第一个 token 的等待，叫 TTFT；后续每个 token 的平均耗时，叫 TPOT。DistServe 把两阶段分开，再根据这两种延迟要求，分别选择资源和并行方式。[OSDI 2024 论文页](https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin)

### 每秒处理更多 token，用户仍可能觉得更慢

**一个假想例子：**几位用户正在看回答逐字出现，这时又来了一条很长的输入。如果同一组 GPU 还要处理这条新输入，系统总共处理的 token 可能更多，但原有用户可能更久才等到下一个 token。具体会不会发生、影响多大，要看 batch 怎样组合和 GPU 算子怎样执行；这里用它说明为什么总 tokens/s 不能独自代表体验。

在线服务通常会约定延迟要求，例如首 token 和后续 token 应在什么时间内给出，这类要求叫 SLO。DistServe 关心的是：在规定比例的请求满足要求时，每秒最多能接住多少新请求，并把容量按 GPU 数量归一化比较。这对应的是达标情况下的有效吞吐，通常称为 goodput。读图时要先固定 SLO 和达标比例；把时间要求放宽，也会让可接住的请求数变多。[论文 §6.1–6.2](https://www.usenix.org/system/files/osdi24-zhong-yinmin.pdf#page=10)

### 分开以后可以各自配置，但必须交接 KV

两个阶段分开后，prefill 可以选择适合自己的 GPU 数量和并行分工，decode 也可以独立选择。不过，一次请求不能凭空从第二阶段开始：decode 要拿到 prefill 算出的 KV，才能接着生成。因此，收益要和这次数据搬运一起算。

论文的 placement 就是决定两阶段各放在哪些设备上，也把机器之间的连接速度考虑进去。如果跨机器带宽不够，就把对应阶段安排在同一台机器的 GPU 上，利用机内高速连接。于是，“分开两个阶段”不等于“随便放到两台机器就更快”。[论文 §3–4](https://www.usenix.org/system/files/osdi24-zhong-yinmin.pdf#page=4)

**一个自行计算的容量规划例子，不是论文实测配置：**假设每个请求要搬 1 GiB KV，每秒到来 8 个请求，单是 KV 就需要约 8 GiB/s。这个数还没算协议开销、其他通信和带宽争用。如果可用带宽比它低，来不及传完的请求就会越积越多；即使稍高，也不能保证最慢那些请求的延迟一定达标。

### 论文实际测了什么，用到 rollout 时还缺什么

实机环境是 4 台机器、32 张 A100 80GB，机内使用 NVLink，机间带宽为 25 Gbps。实验使用 OPT 模型，负载包括聊天、代码补全和摘要。§6.4 对高带宽方案的比较包含仿真，不能把所有结果都当成这套实机集群测出的数字。读 Table 1 查延迟目标，读 Figure 7 查输入输出长度分布，读 Figure 11 查消融条件。[实验与消融](https://www.usenix.org/system/files/osdi24-zhong-yinmin.pdf#page=10)

**以下是系统推导：**训练 rollout 的完成标准与聊天体验不同。还要把整条轨迹画出来：模型生成、等待工具、恢复 KV、计算 reward，最后等一批训练数据凑齐。首 token 更快、后续 token 更流畅，不一定让最后一条轨迹更早结束；最慢的部分可能在工具，也可能在“等整批完成”这一步。比较方案时，除了各阶段延迟，还要记录传输量、GPU 利用率和整批轨迹完成时间。

### 阅读路线：先算收益和搬运，再决定是否值得分开

值得精读，但今天先抓住一条顺序即可：两个阶段需求不同，所以允许分别配置；分别配置以后，又要支付传 KV 的成本。已有 Orca/PagedAttention 基础，补清 TTFT/TPOT 后，就可以按 §2 动机、§3 代价分析、§4 设备放置、§6 实验的顺序读。

读完后再问自己的系统：现在主要是在处理输入、生成输出、传数据，还是等工具？答案决定了先测哪一项、阶段分离是否有希望，不能只看论文最大的加速数字。还可以和站内 [[CN/wiki/llm-serving-for-agents/infercept|InferCept]] 对照：这里讨论把 prefill/decode 分开，那里可以进一步思考工具等待期间怎样管理 KV。
