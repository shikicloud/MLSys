# 训练与 rollout 怎么才能真正一致：从 VeXact 到梯度校正

同一份权重、同一段输入，生成端和训练端为什么仍会给出不同概率？今天主读 VeXact：通过统一模型与算子、固定归约顺序，建立一个训练与 rollout 数值一致、可用于诊断 RL 训练的参考实现。两篇选读分别补清批次怎样改变计算结果，以及 Score Centering 如何在分布仍不一致时校正梯度。重点区分同权重数值一致、旧权重造成的离策略，以及梯度平均漂移为零这三件事。先读主读的具体例子和实现路径，算法推导可以留到第二遍。

## 主读 · Diagnosing Training-Inference Mismatch in LLM Reinforcement Learning via a Zero-Mismatch Reference

**年份 / 发表信息：** 2026 · arXiv 2026 · v1 2026-05-14 / v2 2026-09-29 · ByteDance & University of Virginia · [原文](<https://arxiv.org/abs/2605.14220v2>)

**阅读建议：** 值得精读。先理解同一前缀重新打分的例子，再读论文 §3.1 与固定版本源码；随后看 Table 2、训练曲线和 §4 的概率分母。本文以 2026 年 9 月 29 日的 v2 为准，代码则单独注明当前核验的 commit。

### 先固定一道题：两套系统为什么会给同一个 token 不同概率？

设模型正在回答一道数学题，已经写完相同的一段推理。生成系统接下来采到了 token A，并记录它的概率。训练时，我们把这条已经写出的回答送进训练系统，要求它给 A 重新打分。这里不让模型重新抽一个答案；我们固定前面的所有 token，只比较“在这个前缀后出现 A”的概率。以下 A 和概率数值都是教学例子。

这种把已知 token 序列送回模型、逐位置计算概率的做法叫 teacher forcing。训练通常一次处理整条序列，生成则逐步使用缓存，但因果遮罩应保证 A 只能看到同一段前文。如果权重和输入相同，生成端算出 0.400，训练端却算出 0.404，这个差异就不能归因于模型已经学到了新东西。

训练常保存概率的自然对数，称为 log-probability，简称 log-prob；比较对象仍是同一个条件概率。VeXact 研究这种训练与推理不一致，即 TIM。它追求两条路径给出相同的浮点结果，不追求与无限精度实数计算完全相同。[论文 v2](https://arxiv.org/html/2605.14220v2)

### 第一步：把模型实现和算子一起对齐

权重只是计算的输入。两份程序可以读相同的权重，却使用不同的归一化实现、不同的中间精度，或把几步计算合成一个 kernel。kernel 是在 GPU 上执行一段计算的底层程序。只要中间结果的舍入位置不同，最终概率就可能不同；复制权重文件并不能自动统一这些路径。

VeXact 的训练端入口会先开启它的算子替换，再注册模型补丁。这个顺序很有意义：模型层要选对实现，层里面的矩阵乘法等运算也要选对实现。它不是只在训练结束后拿两张概率表做修正。[训练端入口](https://github.com/verl-project/vexact/blob/6c170209f334f2cd59147436ef22740878e49437/vexact/integrations/verl/fsdp_enable_invariant.py#L17-L29)

这里须区分两个版本。论文描述的是其 FSDP2 实验系统；FSDP 是把模型状态分片到多张 GPU 的训练方式。本文于 2026 年 10 月 20 日核验的代码 commit 为 `6c170209f334f2cd59147436ef22740878e49437`，当前集成以 VeOmni FSDP 为主。当前模型注册明确接入 VeOmni 的 MoE 实现，不能把这套代码直接说成论文当时的全部实验环境。[模型注册](https://github.com/verl-project/vexact/blob/6c170209f334f2cd59147436ef22740878e49437/vexact/models/register.py#L29-L72)

### 为什么同一份矩阵乘法也需要固定加法顺序？

先看一个刻意放大的浮点教学例子。用 float32 计算 `(1e20 + (-1e20)) + 3`，可以得到 3；改成 `1e20 + ((-1e20) + 3)`，小数 3 会在中间舍入时丢失，结果变成 0。这不是论文里实际偏差的大小，只说明有限精度的加法不能随意换括号。

矩阵乘法要把很多乘积相加，这种求和称为归约。GPU 可以先算不同小块，再合并部分和。单条请求运行时和很多请求一起运行时，库可能选择不同分块。即便每次重跑同一个批次都得到相同结果，换一批同行请求后仍可能改变结果。因此“重复运行确定”与“结果不受批次组成影响”是两个要求。

VeXact 为矩阵乘法等路径固定计算安排，并替换 `mm`、`addmm`、`log_softmax` 和按维求均值等算子；入口还限制低精度归约并开启 PyTorch 的确定性设置。真正起作用的是这些具体路径共同受到约束，不能把一个确定性开关当作完整答案。约束也不意味着跨 GPU 架构天然一致。[算子注册与设置](https://github.com/verl-project/vexact/blob/6c170209f334f2cd59147436ef22740878e49437/vexact/batch_invariant_ops/batch_invariant_ops.py#L741-L759)

### Attention：保留 KV cache，但不让历史分块改变合并方式

接着看 A 如何查询前面的推理。Attention 会使用历史 token 的 key 和 value；把它们留下来，避免每生成一个 token 都重算历史，这就是 KV cache。历史很长时，一种实现会把它分给多个计算块，各块算出部分结果，再合成最终输出。分几块、怎样合并，都可能影响浮点舍入。

当前 VeXact 的两条 FlashAttention 调用路径都显式传入 `num_splits=1`，固定这部分计算安排。代码仍传入分页缓存的 `page_table`。因此它限制的是 KV 分块计算与合并这一路径，不是删除 KV cache，也不是禁止分页存储。[两条 attention 路径](https://github.com/verl-project/vexact/blob/6c170209f334f2cd59147436ef22740878e49437/vexact/batch_invariant_ops/flash_attention.py#L172-L206)

回到那道题，生成端可能带着一整段缓存只处理新 token，训练端则把整段回答一起送入模型。要比较两者，除了权重，还必须让有效前缀、位置编号和遮罩一致。固定归约解决的是计算顺序问题；若两边本来就看了不同上下文，它不会替你修好输入。这里是由机制推出的核验要求。

### MoE：专家选对了，还要保证专家内部算得一样

MoE 是 mixture of experts，即混合专家模型。可以把一层看成若干个不同的子网络：路由器为每个 token 选少数几个专家，再按权重合并它们的输出。服务批次改变时，落到某个专家上的 token 数也会改变，于是专家的矩阵乘法可能选择不同的计算安排。

因此，仅核对“训练和生成选中了同几个专家”还不够。当前 Qwen3 MoE 路径直接调用 VeOmni 的 `fused_moe_forward`；源码注释说明，目的是让 rollout 与训练端的专家计算采用相同算术。这里的关键是共享实际执行的专家实现，而不只是共享模型名称或路由结果。[Qwen3 MoE 的实际调用](https://github.com/verl-project/vexact/blob/6c170209f334f2cd59147436ef22740878e49437/vexact/models/qwen3_moe/modeling_qwen3_moe.py#L69-L100)

这也解释了支持范围为什么需要逐模型说明。当前 README 不支持旧 FSDP 路径的 MoE，对线性注意力等不同计算路径也不作全面保证。“已有一种 MoE 对齐”不能推出任意混合架构都已对齐；换模型时需要重新核验执行到了哪些补丁。[固定版本 README](https://github.com/verl-project/vexact/blob/6c170209f334f2cd59147436ef22740878e49437/README.md)

### 最后一道关口：相同隐藏状态还不等于相同 log-prob

模型最后先给词表中每个 token 算一个分数，称为 logit，再用 softmax 把所有分数转成总和为 1 的概率。A 的概率因此不只取决于 A 自己的分数，还取决于整张词表的归一化计算。若一边把中间分数提升到 float32，另一边保留 bfloat16，即使前面的层已经一致，这里也仍可能出现差异。

当前推理器就显式处理了这个选择：源码说明训练中的融合线性层与交叉熵路径会提升 logits 精度，而另一路径可能保留较低精度，并通过配置控制。读到这里要检查实际启用的分支，不能只检查模型主体。[推理器的精度说明](https://github.com/verl-project/vexact/blob/6c170209f334f2cd59147436ef22740878e49437/vexact/inferencer/inferencer.py#L78-L85)

“测试通过”也要看断言。仓库的一个 FA4 批次不变性测试使用 `diff < 1e-5`；重新核验 log-prob 的脚本还可指定容差。这些测试很有用，但容差内接近不是逐位相同。论文的严格结论与某个具体单元测试分别证明什么，应分开阅读。[FA4 测试](https://github.com/verl-project/vexact/blob/6c170209f334f2cd59147436ef22740878e49437/tests/batch_invariant_ops/test_flash_attention_4_batch_invariance.py#L120-L135) · [可配置核验脚本](https://github.com/verl-project/vexact/blob/6c170209f334f2cd59147436ef22740878e49437/tests/scripts/verify_logits_vs_native_hf.py#L913-L1033)

### 零不一致不等于 rollout 永远来自当前策略

现在把时间加入例子。生成系统在权重版本 θ₀ 下写出回答，训练器随后更新到了 θ₁。用 θ₁ 重新计算 A 的概率，本来就应当可能不同。这个变化代表模型参数真的变了；它与同为 θ₀ 时两套程序算出不同结果，是两件事。

异步 rollout 可能在训练器已经前进后才返回；同一批回答也可能被重复用来更新多次。这些都会使数据来自较旧策略，通常称为 policy staleness。即使 VeXact 让每个固定版本的两条计算路径完全一致，θ₀ 生成的数据也不会自动变成 θ₁ 生成的数据。

因此，对接系统时应分别记录权重版本和数值差异。前者回答“是不是同一个策略”，后者回答“同一策略有没有被两套程序算成不同概率”。与本期选读的 Score Centering 相比，这里改变的是数值执行路径；把某个估计量的期望漂移归零，并不等价于让这两张概率表一致。

### 实验的作用：先拿走一个干扰因素，再看训练会怎样

强化学习会根据回答的奖励，提高较好回答中 token 的概率、压低较差回答的概率。REINFORCE 是直接用奖励构造这种更新的一类方法。论文用每批 rollout 做一次更新的设置研究数值不一致，减少把现象与多轮 PPO 更新混在一起的机会；这仍是一个特定训练设置。

论文 Table 2 中，稠密模型 REINFORCE 使用 16 张 H100，GRPO 使用 8 张 H100；MoE REINFORCE 使用 64 张 H100。后者使用 Qwen3-30B-A3B，在 DAPO-Math-17k 上训练、用 AIME2024 评测，训练批大小参数为 512，提示和回答长度上限分别为 2,048 与 20,480 token。上限不是每条样本的实际长度。[论文 §3 与 Table 2](https://arxiv.org/html/2605.14220v2)

在这个 MoE 设置中，论文报告 VeXact 的 AIME2024 验证奖励达到 0.534，而 vLLM 运行中的验证奖励下降至 0.067。这支持作者在所测条件下对 TIM 的担忧，但不能读成任意任务都提升同样幅度。它是该训练过程的结果，不是吞吐数字，也不能单凭它断言别的训练崩溃都由 TIM 引起。[论文训练曲线与实验说明](https://arxiv.org/html/2605.14220v2)

### 一个分母例子：为什么训练端重新打分会掩盖差异？

继续用教学数值。令 q_old = 0.400，表示真正生成 A 时记录的概率；p_old = 0.404，表示训练端用同一份旧权重重新算出的概率。在更新前，当前训练端概率 p_new 也等于 0.404。于是 p_new / p_old = 1，而 p_new / q_old = 1.01。

第一个比值准确表达“训练端这份程序还没改变”，却看不出它与真正产生数据的程序有差别。第二个比值把这个差别显露出来。论文 §4 讨论的 recompute 与 bypass，正涉及用哪个旧概率作分母。比值可以进入更新中的重加权和裁剪，因此分母选择不只是日志格式。[论文 §4](https://arxiv.org/html/2605.14220v2)

但换分母也没有把模型内部的算术统一起来。这不意味着重要性采样的数学原理失效，而是说具体训练算法还包含裁剪、近似和其他实现条件。这个小例子只解释两种比值为何不同，既不证明某种修正永远无效，也不保证精确对齐之后每一步更新都会变好。

### 读结果时要保留的三条边界

第一，逐位一致是指定计算路径下的性质。换 GPU、算子版本、精度、模型结构或补丁是否生效，都可能改变前提。两边可以执行同样的浮点舍入，因此得到相同结果；这并不说明它们等于更高精度参考答案。“零数值误差”不是这里合适的表述。

第二，一致性与效率需要分别测量。固定某些并行分块可能改变性能，chunked prefill、CUDA Graph 等服务优化又可能节省时间。不能把机制上减少不确定性直接换算成某个未测量的加速百分比。工程上应同时记录概率差异、生成耗时和训练达到目标质量所用的总时间，这是本文给出的评估建议。

第三，论文中的证据范围不能被仓库更新悄悄扩大。大多数报告实验使用 seed 42，补充的多 seed 检查主要针对部分 GRPO 设置。当前 VeOmni 集成也不是论文 FSDP2 环境的同义词。读者应把论文实验、后续代码支持范围以及自己的新配置视作三层证据。

### 如何精读，以及怎样把它变成自己的诊断实验

建议先读 §3.1，回答一个问题：两边到底在哪些层、哪些算子上共享了实现？然后按本文的固定链接查看训练端入口、基础算子、attention 和 MoE 调用。接着对照 Table 2 看训练曲线；最后读 §4，拿纸写清每个概率来自哪个权重版本、哪一套程序。这个顺序比一开始追所有损失公式更容易建立判断。

若要在自己的系统里做一个最小诊断，可以先冻结一份 checkpoint，保存一条 rollout 的 token、有效长度、位置与遮罩，再让训练端对同一序列打分。随后只改变批次组成、长度和 prefill/decode 路径，检查差异是否出现。这个实验流程是本文的建议，不是我们已经替读者跑过的验证。

输出至少保留最大绝对差和出现非零差异的位置，并区分严格相等与容差内接近；只看平均差或最终答案是否相同，会漏掉问题。通过后再加入权重更新和异步流水线，单独检查策略过期。这样得到的是一条能定位问题的证据链，而不是一句“同权重，所以应该没问题”。

## 选读 · Defeating Nondeterminism in LLM Inference

**年份 / 发表信息：** 2025 · Thinking Machines Lab · technical article · 2025-09-10 · [原文](<https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/>)

**阅读建议：** 值得精读机制部分，特别是 attention 的固定切分长度；结合固定版本代码看矩阵乘法，再回读 VeXact §3.1。

### 1. 同一个请求，只换旁边一起算的请求

先看一个教学例子，并非原文实验：你两次提交相同问题，模型权重也没更新。第一次服务器只处理你的请求，第二次把它和另外七条请求一起计算。这组一起执行的工作叫 batch。即使各条请求不读取彼此内容，矩阵形状也变了，底层可能因此换一种算法。PyTorch 的[数值精度说明](https://docs.pytorch.org/docs/main/notes/numerical_accuracy.html)明确指出，整批计算后取一行，与单独计算那一行，不保证逐比特相同。

假设两个候选词的分数原本非常接近，细小误差就可能交换第一名。温度设为 0 时采用 greedy，也就是每次选当前分数最高的 token；它不会把两次算出的分数变成一样。第一个词一旦不同，后续输入也不同，回答便可能越走越远。要排查这种问题，应固定目标请求，主动改变同批请求数量，再比较该请求的数值结果。

### 2. 相同 dtype，没有规定先加哪几个数

用只保留三位有效数字的十进制玩具计算器说明舍入：计算 1000＋1－1000，若先算 1000＋1，1001 会舍入成 1000，最后得到 0；若先算 1－1000，得到可表示的 −999，再加 1000，结果是 1。这是教学算例，不是 BF16 的精确模拟。实际浮点数同样只能保存有限精度；[NVIDIA 的浮点说明](https://docs.nvidia.com/cuda/floating-point/index.html)解释了运算顺序为何影响结果。

dtype 是数值存储格式，例如 BF16；它不规定所有中间运算的顺序和精度。把很多项合成一个和称为归约。GPU 可以让一组线程加完整行，也可以先分几段各自相加再合并。两条路线在实数数学里相等，实际舍入可能不同。因此，固定同一完整 batch 重跑稳定，与改变 batch 后目标请求仍稳定，是两个不同要求；固定随机种子也不能指定这些加法顺序。

### 3. 前两处修复：按行求和与矩阵乘法

先看 RMSNorm：它用一个 token 向量中各元素平方的平均值调整整行大小。教学向量 [1, 2, 3, 4] 的平方和是 30；在真实长向量里，重点是怎样把这些平方项加起来。若固定每行的处理方式，旁边多出几行只增加工作量，不改变本行的加法路线。这有助于实现 batch invariance，即本行结果不随同批工作改变。

矩阵乘法也要为每个输出累加很多乘积。代码可以固定每块输出的形状以及沿内部维度累加的顺序，避免只因 batch 变小就改成另一套计算。下面链接的实现按 dtype 选择固定配置，不按 batch 大小选择配置；因此不能误读成所有 dtype 都使用同一配置。代价也容易理解：小 batch 仍使用较大的计算块时，部分工作可能用不上。[固定版本算子源码](https://github.com/thinking-machines-lab/batch_invariant_ops/blob/f22b1fbe534b1fe045080f44a970a441caaf3c4f/batch_invariant_ops/batch_invariant_ops.py)。

### 4. 第三处修复：attention 怎样读取旧内容

attention 会利用前面 token 的 K/V 向量；保存它们避免重算的空间就是 KV 缓存。这里还要控制缓存边界：教学例子中，每块处理 4 个位置，旧缓存有 6 个、新增有 6 个。两部分分别处理需要 2＋2 块，先接成 12 个再处理只需 3 块，归约路径可能不同。文章的处理方式是先更新缓存和页表，再让 attention 按统一的逻辑位置读取。

长上下文常被分段计算，称为 split-KV。为什么固定段数仍不够？看另一个教学例子：同一因果 attention 查询位于第 8 个 token，在长度为 8 的 chunk 中，两段均分的边界是 4；若把它放进长度为 12 的 chunk，边界变成 6，尽管它仍只能看前 8 个位置。固定每段 4 个位置，才能保持它看到的分组为 1–4、5–8；后面位置被遮住。实际实现还须固定段内与合并时的运算方式。[FlashInfer 的相关接口说明](https://docs.flashinfer.ai/api/attention.html)也把固定切分长度与确定性的结果合并联系起来；这不表示所有后端默认启用。

### 5. 代码实现了哪些部分

本次于 2026-10-20 核对代码，固定在提交 f22b1fbe534b1fe045080f44a970a441caaf3c4f。库通过 torch.Library 替换矩阵乘法、带偏置矩阵乘法、log-softmax 和部分均值运算。log-softmax 把候选分数转换为对数概率，也包含需要控制的归约。[该版本 README](https://github.com/thinking-machines-lab/batch_invariant_ops/blob/f22b1fbe534b1fe045080f44a970a441caaf3c4f/README.md)把 vLLM 示例定位为概念验证。

不要把这个算子包等同于完整服务系统。原文发表时，固定切分长度所需的内部 FlexAttention 修改尚未包含在发布代码中，这是当时的状态。实际接入时仍要核对模型使用的算子与 attention 后端；能导入库，不等于每条执行路径都已被替换。本文也不据历史示例判断你当前安装的框架默认行为。

### 6. 代价是多少，哪些条件还不知道

原文性能实验是单 GPU 的 Qwen3-8B API 服务，完成 1000 个请求，每个输出 90–110 token：默认 vLLM 总耗时 26 秒，未优化的确定性版本 55 秒，改进 attention 后 42 秒。文章没有注明该测试的 GPU 型号，也没有给出完整输入长度与到达负载协议。因此这些数值只能说明该演示有成本，不能变成普遍适用的开销比例。[原文 Performance](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)。

从机制看，需要关注的是稳定性要求限制了哪些优化选择，以及你的实际负载会不会常碰到这些选择。另一个边界是 TP，即把一个算子的工作拆到多张 GPU 上：它需要跨卡合并结果，而原文把并行通信带来的归约排除在讨论范围之外。单卡算子处理好，不自动保证换 TP 数量、硬件或软件版本仍逐比特相同。

### 7. 回到 VeXact：同一句话，还要比较概率

把这篇接到今天主读，可以提出两个检查：第一，同一生成端换 batch，结果是否变化；第二，同一权重和同一段 token，生成端与训练端计算的对数概率是否一致。VeXact 针对第二个问题建立参照，在统一模型和算子实现的基础上使用 batch-invariant 算子；它的 attention 选择直接关闭 KV splitting，上文固定每段长度是另一种处理方式。只得到相同的 greedy 文本还不够：两个分布可以第一名相同、其余概率不同。[VeXact v2 §3.1](https://arxiv.org/html/2605.14220v2#S3.SS1)。

所以，权重没有过时，只排除了参数版本造成的差异，不能排除训练和推理计算不一致造成的差异。建议先读本文的矩阵乘法与 attention 机制，再看固定版本代码，最后回到 VeXact 的对齐检查。对系统工作最有用的追问是：这次缓存、调度或并行优化改变的，是否也包括同一 token 的计算路径？这是读完材料后可带回代码审查的问题，并非声称现有系统已经出错。

## 选读 · Score Centering Stabilizes Off-policy Reinforcement Learning

**年份 / 发表信息：** 2026 · arXiv 2026 · v1 2026-09-17 · Together AI · [原文](<https://arxiv.org/abs/2609.20807v1>)

**阅读建议：** 值得选读，建议 25–35 分钟。先读本文的记录数据与尾部例子，再看固定版本 README、losses.py 和 tests/test_loss.py，最后核对论文 §5 与附录 B 的实验边界。

### 两边概率还不同，训练为什么可能先稳下来

生成器写出回答，训练器随后重新计算这些 token 的概率并更新权重。量化、不同计算顺序或旧权重，都可能让两边概率不同。VeXact 尝试对齐计算路径；Score Centering 接受差异仍在，改动的是训练更新。因此这里的 zero 指消去一种平均推动，不是让两边输出概率完全一致。

score 也不是奖励分数，而是“让某个 token 的对数概率增大，需要怎样改变参数”的梯度方向。若所有结果都得到相同奖励，本来没有理由偏爱哪个结果；但采样来自另一套概率时，这些方向的平均值仍可能不为零。中心化先减去这个平均方向，再用奖励或 advantage 加权；advantage 表示奖励相对比较基准的好坏程度。论文作者为 Together AI 的 Martin Marek、Max Ryabinin，v1 发布于 2026 年 9 月 17 日，按预印本介绍。[论文记录](https://arxiv.org/abs/2609.20807v1)

### top-k 是记录哪些概率，不是只准生成哪些词

以下按官方仓库提交 `64842967077ea105470ca73fc5d714366d3f7bdb` 阅读，源码核验日期为 2026 年 10 月 20 日。logits 是转换为概率前，每个候选 token 的原始得分。生成时仍从完整 logits 对应的分布采样；另存每个位置概率最高的 k 个 token 的编号和 logprob，即概率的对数。被实际抽中的 token 即使不在这 k 项中，它的 logprob 也单独保留。后者让训练器知道这次真实选择原来有多大概率，供重要性权重使用。[采样代码](https://github.com/martin-marek/score-centering/blob/64842967077ea105470ca73fc5d714366d3f7bdb/models/sampling.py)

收集过程先缓冲 32 步，再在各个词表分片选局部 top-k，从候选集合选全局 top-k。这些高概率项本身是精确选出的；近似发生在未保存的长尾。训练器必须查询相同 token 编号的概率，不能另选自己的 top-k，也不能把已保存项重新归一化为总和 1，否则会抹掉尾部还占多少概率。[收集实现](https://github.com/martin-marek/score-centering/blob/64842967077ea105470ca73fc5d714366d3f7bdb/models/topk.py)；[接口要求](https://github.com/martin-marek/score-centering/blob/64842967077ea105470ca73fc5d714366d3f7bdb/README.md)

记录也有真实存储成本：该实现的头部编号是 int32，logprob 是 float32。按 k=128 计算，每个位置仅这两项就约 1 KiB，另外还有 32 步的完整词表环缓冲。这是按代码形状计算的开销，不是论文的吞吐测量；接入分离部署的训练与生成服务时，还要测传输成本。[缓冲布局](https://github.com/martin-marek/score-centering/blob/64842967077ea105470ca73fc5d714366d3f7bdb/models/topk.py)

### 没有保存的尾部，怎样进入校正

**教学例子，不是实验结果：**已保存项占采样器概率的 80%，却占训练器的 90%。剩余概率分别是 20% 和 10%，于是令 `rho = 0.20 / 0.10 = 2`。对未保存项，暂时用训练器的概率乘二，凑出采样器的尾部。这只匹配总量，不保证尾部每个 token 都估计准确。

设 p 是训练概率、q 是采样概率。实现为每个已保存项计算 `q − rho × p`，乘该项的训练 logprob 后求和，得到可从普通训练项中扣除的校正。尾部无需逐项保存，是因为完整训练分布下 score 的平均为零，可以把尾部平均换成头部平均的负值。[损失实现](https://github.com/martin-marek/score-centering/blob/64842967077ea105470ca73fc5d714366d3f7bdb/losses.py)

这些系数必须 stop-gradient，即本次反向传播把它们当常数，梯度只穿过最后相乘的 logprob；否则会额外对系数求导，得到另一种更新。实现还保护接近零的尾部质量，并分块计算完整词表的训练 log-softmax。因此“只保存 k 项”节省的是采样历史，并不代表整个训练只计算 k 个词。[MIT 许可证实现](https://github.com/martin-marek/score-centering/blob/64842967077ea105470ca73fc5d714366d3f7bdb/losses.py)

### 官方零漂移测试，为什么不能证明任意尾部都精确

官方测试枚举三个 token，按真实采样概率加权各自的梯度，检查平均是否接近零。top-k 测试取 k=2，尾部只剩一个 token：知道尾部总量，就知道它的概率，所以近似在这里恰好精确。这是有意义的实现检查，但没有覆盖复杂尾部。[测试条件](https://github.com/martin-marek/score-centering/blob/64842967077ea105470ca73fc5d714366d3f7bdb/tests/test_loss.py)测试算的是枚举后的期望；一次有限批量仍会有采样波动，不能要求每步实际梯度都为零。

**独立推导例子：**若四词表中两个尾部 token 的真实概率都是 0.10，建模后却是 0.15 和 0.05，总量仍正确。对于直接以 logits 为参数的教学模型，奖励恒为 +1 时校正后的平均更新等于真实概率减去建模概率：这两个位置还剩 −0.05 和 +0.05。因此尾部总量正确，不等于漂移精确为零；实际模型还要经过参数到 logits 的导数，影响大小需实测。

### 为什么还要和重要性采样一起用

重要性采样用 p/q 调整样本的权重，试图把来自 q 的数据换算成来自 p 的统计。完整、未截断的修正与只减平均方向，目标不同：后者仍然依据 q 中哪些结果更常出现来学习。实际常把过大权重截断，或丢掉超出范围的权重，以减少极端样本的影响。

代码组合二者时，先确定权重函数 f，再中心化“加过权的 score”，而不是原来的 score。尾部所有建模概率都等于 rho×p，所以尾部的 p/q 都是 1/rho；校正中使用 `alpha = rho × f(1/rho)`。这说明组合需要重新计算平均，不能随意把两个独立损失相加。固定版本给出截断重要性采样（TIS，截断过大的权重）和掩码重要性采样（MIS，把指定区间外的权重置零）的入口；实际按 token 修正也不应直接说成恢复了完整轨迹分布。[组合实现](https://github.com/martin-marek/score-centering/blob/64842967077ea105470ca73fc5d714366d3f7bdb/README.md)

### 实验把失配放大了，配置还要读到代码

公开配置用 Qwen3-0.6B 做 Countdown、Qwen3-30B-A3B-Base 做 INTELLECT-2 数学。总序列缓冲分别为 512、1024 token，每题八个回答，每批 64、16 道题；每批做一次随机梯度下降（SGD），学习率 0.01。训练计算用 BF16，故意对采样侧施加较强量化或旧权重。这是受控训练实验，不是长程工具调用服务的完整复现。[小模型配置](https://github.com/martin-marek/score-centering/blob/64842967077ea105470ca73fc5d714366d3f7bdb/sweeps/06b_quant_stale.yaml)；[30B 配置](https://github.com/martin-marek/score-centering/blob/64842967077ea105470ca73fc5d714366d3f7bdb/sweeps/30b_math.yaml)

论文的旧权重实验描述为每 64 个训练步刷新采样器，且此时与重要性采样组合优于单独中心化。要注意固定代码的配置是 `staleness=64`，刷新条件却是 `step % (staleness + 1) == 0`，实际间隔 65 步；不能把两者写成完全一致，更不能解释成异步系统任意样本的最大延迟。[论文 §5.3](https://arxiv.org/html/2609.20807v1)；[刷新逻辑](https://github.com/martin-marek/score-centering/blob/64842967077ea105470ca73fc5d714366d3f7bdb/train_rl.py)

论文明确用短序列、较大失配来加快区分方法；量化与旧权重图主要报告训练准确率。小模型实验多种子，30B 部分方法只有一个种子。因此这些结果支持继续验证这一修正，不能直接推出在长序列、轻微数值误差或真实异步队列中同样有效。[§5、附录 B](https://arxiv.org/html/2609.20807v1)

### 带回自己的训练系统，先测哪三个问题

**以下是工程推导：**先用相同前缀核对采样器记录的概率，确保它对应实际生成时的权重和采样规则；再检查头部覆盖率、尾部近似与恒定奖励下的剩余平均梯度；最后在真实序列长度和权重更新节奏下比较奖励、方差与吞吐。前两项定位校正是否算对，最后一项判断是否真的有用。

精读顺序可从 README 的输入张量开始，顺着 sampling.py、topk.py 到 losses.py，再读测试和实验配置。与 VeXact 并读时始终分开两个问题：能否让两套计算得出相同概率，以及概率仍不同时如何减少有害更新。稳定性改善是结果证据，不能自动替代数值一致性的检查。
