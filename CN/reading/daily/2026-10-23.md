# MoE 推理：少算一些，为什么还不够快？

MoE 每次只调用部分专家，却仍可能花很多时间等数据。今天主读 RapidMoE：低精度权重留在 GPU，少数关键专家由 CPU 补充计算，减少搬动大块权重。选读 Stepped MoE，看能否通过训练让一段生成共用专家；再用 Sem-MoE 理解专家与请求共同放置，怎样减少设备间的激活传输。三篇处理的硬件条件、可改动范围和精度取舍不同，不能直接横比速度。先读主读的具体流程，其余按兴趣选择。

每天推荐 1 篇主读与 2–4 篇选读，覆盖 LLM Inference、RL Infra、Post-Training、RSI（递归自我改进），以及推理计算、Agent 学习与记忆、数据评估和模型架构。经典与前沿并行，按主题逐步展开；不要求与当前工作直接相关。候选不等于已读，无需一天读完。

## 主读 · RapidMoE: Exploiting Cross-Asymmetry via Adaptive Residual Offloading for Large-Scale MoE Inference

**年份 / 发表信息：** 2026 · arXiv 2026 · Tsinghua University · v1 2026-10-01 · [原文](<https://arxiv.org/abs/2610.01265v1>)

**阅读建议：** 值得精读 Figure 7/9 与 §4.4–4.5，先弄懂一次专家计算怎样拆开，再看 §4.3 的精度选择和 Tables 8–10 的吞吐、服务延迟与内存。不要只记住摘要的加速倍数；单请求速度、批量总吞吐和服务达标率回答的是不同问题。

### 只算八个专家，为什么仍然装不下整个模型？

一个 MoE 层包含许多前馈网络，称为专家。处理一个 token 时，路由器只选其中几个，再把它们的输出加权合并。例如 DeepSeek-R1 的路由从 256 个专家中选八个，此外还有共享专家。因此每步计算的参数少了，但下一步可能选到另外八个，全部专家的权重仍要有地方保存。

设想一台 GPU 显存有限、CPU 内存较大的工作站。以下贯穿全文的教学例子只看某一层选中的八个专家：当前 token 到来后，系统必须决定怎样算完它们。把缺失专家的整块权重搬到 GPU，会等待 PCIe 传输；直接在 CPU 上算，又可能让 GPU 等待较慢的计算。RapidMoE 改的是这项分工。[§1–2 与 Table 2](https://arxiv.org/html/2610.01265v1)

### 八个专家都保留，但不一定都用同样精度

路由器给出的八个权重通常并不一样。论文观察到，一些专家的贡献更值得保留精度，另一些可以承受更强压缩。量化就是用更少的比特表示权重，节省存储和读取量，同时引入近似误差。RapidMoE 不直接删掉较低权重的专家，而是保留它们的低精度计算。

继续教学例子：假设这一层有两个专家需要较高精度，其余六个只使用低精度权重。GPU 适合处理压缩后能放进显存的主体，CPU 只承担重要专家的补充工作。这里的“两对六”用于说明流程，不是全模型固定配置；重要专家数量会随输入、层和推理阶段变化。路由权重也是选择依据，不是单个专家误差的严格保证。[§3–4.2](https://arxiv.org/html/2610.01265v1)

若用符号表示，k 是路由器选中的专家数，r 是其中需要补精度的数量。在这个例子里 k=8、r=2，另外 k−r=6 个专家仍参与输出加权。它与跳过六个专家的剪枝不同：本次执行省下的是额外精度修正的计算与权重读取，代价是接受低精度近似；残差仍可存放在 CPU 内存中，供以后需要时使用。

### 残差怎样补精度：先看一个可以算清的小例子

对原权重 W，系统先得到低精度主体 Q，再将差值 W−Q 量化成残差 R。较高精度版本是 Q+R，低精度版本只用 Q。教学例子：原数 1.03 被粗略表示为 1.00，剩余 0.03 又近似为 0.02，合起来得到 1.02。比只保留 1.00 更接近原值，但仍有误差。

如果输入 x=2，GPU 算主体得到 2.00，CPU 算残差得到 0.04，相加是 2.04；原始乘法则是 2.06。对矩阵，依据同样的线性关系 x(Q+R)=xQ+xR，两边可以分别计算再相加。这解释了为什么不必把完整高精度矩阵传给 GPU，也说明“补残差”不等于恢复原始浮点结果。

实际格式不是上述十进制例子：主体平均 1.75 bit，残差平均 2.5 bit，合计平均 4.25 bit。这里的“高精度”是相对主体而言，仍是量化表示；平均位数来自压缩格式，不能理解成每个数有一个普通的 1.75 位整数类型。[Algorithm 3 与 §5](https://arxiv.org/html/2610.01265v1)

### 真正的专家不是一次乘法：非线性决定在哪里汇合

常见专家先做 gate 和 up 两个投影，把输入映射到中间表示，再经过非线性函数与逐元素乘法，最后由 down 投影映射回来。这里的 gate 是专家内部的投影，不是选择专家的路由器。gate/up 的矩阵乘法能按主体与残差拆开；但不能把完整专家粗暴拆成两个独立网络，再把最终输出相加，因为中间的非线性通常不满足这种分配关系。

RapidMoE 先在 GPU 上计算两个重要专家的 gate/up 主体，将这些中间结果传给 CPU。CPU 计算相应残差、合并结果，再做非线性与较高精度 down；与此同时，GPU 完整执行另外六个低精度专家。最后两边汇合输出。这条时间线比“CPU 只算残差”更准确：CPU 还承担重要专家后半段计算。

为避免多次跨设备往返，论文只对 gate/up 使用残差拆分，down 仍保存高低两种版本。因此它减少了重复存储，但没有彻底消除所有双份权重，也没有消除同步。节省来自传递中间结果、减少 CPU 工作，并让 CPU 与 GPU 尽量重叠。[Figure 9、§4.4–4.5](https://arxiv.org/html/2610.01265v1)

### 为什么不能每层都固定补两个专家？

固定数量容易忽略三个差别：当前输入对各专家的依赖不同，不同层对量化误差的敏感度不同，读入提示与逐字生成对误差的影响也不同。论文把一次处理提示称为 prefill，把随后逐 token 生成称为 decode；prefill 产生的注意力缓存还会被后续生成反复使用。

系统先离线测哪些层更敏感，然后为每层、每个阶段计算一个阈值：全局基准乘上层系数，再乘上阶段系数。所选专家的路由分数达到阈值，才进入补精度集合。作者称其为 UMIA，即综合多个层面信息进行选择。较敏感层的阈值较低，更容易保留高精度专家；decode 的阶段系数大于一，提高阈值，使其通常比 prefill 保留更少。

这不是给每个请求做昂贵的搜索。部署后只用已标定的参数和当前分数判断。批量推理或 prefill 有多个 token 时，论文先平均路由分数再选择重要集合，这也意味着批次组成可能改变精度集合。因此不能把它想成每个 token 都有完全独立、精确最优的精度预算。[§4.3 与 §5](https://arxiv.org/html/2610.01265v1)

### 少补一个专家，是否一定会更快？

不一定。若 CPU 仍是最慢的一边，减少其工作会缩短等待；若 GPU 已经更慢，再削减 CPU 工作可能几乎不改变总时间。可用“总时间≈同步时间+max(CPU时间,GPU时间)”理解这一点。它是有助于判断瓶颈的近似模型，不是任意请求的延迟上界。

论文据此先做硬件测量，再搜索满足估计延迟目标的精度配置，并用输出分布的差异衡量量化影响。该差异采用 KL 散度：它比较两个概率分布偏离多少，不直接等于任务正确率。默认用 WikiText-2 的 16 个提示标定；作者报告 671B 模型的层敏感度测量约 30 分钟，配置搜索约五小时。无需再训练并不意味着没有部署准备成本。[§4.2–4.3](https://arxiv.org/html/2610.01265v1)

校准还决定了这套方法的适用边界。延迟模型来自具体硬件测量，量化影响来自少量文本提示；换 CPU、GPU 或工作负载后，两者都可能变化。因此部署时需要重新检查质量与时间，而不能把一次搜索得到的配置当成对所有请求都成立的最优方案。

### 显存省在哪里，还需要多大的 CPU 内存？

性能最好的工作区间，是全部低精度主体都能留在 GPU。重要专家的 gate/up 残差及较高精度 down 留在 CPU 内存，按需计算。对 DeepSeek-V3，Table 10 报告 RapidMoE 的 GPU 峰值为 149 GB、CPU 内存峰值为 240 GB；同配置 KTransformers 分别为 150 GB 和 385 GB。它主要减少 CPU 侧重复权重，并非把整机需求缩到 149 GB。

如果显存装不下全部主体，系统可以缓存一部分。命中时走刚才的分工，未命中则回到 CPU 执行相应专家。论文通过限制缓存覆盖 25%–100% 的主体测试这个退化路径，也明确最佳区间是全部主体常驻。因此，这篇不支持“任意小显卡都能获得同样加速”。[§5、Table 10 与 §6.4.3](https://arxiv.org/html/2610.01265v1)

残差也没有凭空消失：CPU 必须从内存读取它，再完成计算。低并发生成时，每次只有少量 token，读取权重的时间很重要；把一部分读取与运算交给 GPU，才可能缩短 CPU 的关键路径。当 CPU 已跟不上更多同时请求时，继续提高 GPU 吞吐也不能自动解决等待。

### 吞吐结果：先把模型、硬件和批量说清

主配置用两张 A800 80GB 运行 DeepSeek-R1/V3，用一张 A800 80GB 运行 Qwen3-235B，CPU 为论文列出的 Xeon Gold 6326（64 核），配有 512 GB DDR4 内存和 PCIe 4.0。另一个 R1 配置用七张 RTX 4090，不是单张消费卡。多 GPU 按模型层分配工作；这里不是跨节点把同一层专家分散后做 all-to-all 通信的实验。

Table 8 在 1K 序列长度设置下给出 R1 的结果：单请求 decode 为 21.8 token/s，KTransformers 为 8.0；batch=4 时为 43.6 对 10.5 token/s。后者是这批请求的总吞吐，不能说每个用户都得到 43.6。相同表里的 prefill 为 150.2 对 62.8 token/s。摘要的倍数不能代替这些负载条件。

基线包括 KTransformers、HybriMoE、MoE-APEX 和 llama.cpp。作者对齐可比内存预算，并在相同量化格式下使用相同矩阵运算内核；但完整模型的计算精度策略仍不同。这里证明的是这些混合部署配置下的收益，不是战胜显存充足的纯 GPU 服务系统。[Tables 3–4/8 与 §6.1](https://arxiv.org/html/2610.01265v1)

### 速度之外：正确率接近，并不等于结果完全相同

Table 5 的正确率对照是 Q4_K_M 量化模型，而非原始 BF16 模型。其中 MMLU-Pro 只随机抽取 1000 题。batch=1 的 R1 在 MMLU-Pro 上为 83.8 对 83.9，在 MATH-500 上为 96.2 对 95.6，AIME-24 均为 73.3。这支持已测任务中质量接近；小幅上下波动没有给出足以确认优势的跨种子证据，更不能推出逐 token 输出一致。

服务实验还测用户真正等多久。首 token 等待时间称 TTFT，相邻输出 token 的平均用时称 TPOT。对 R1，1000 个 ShareGPT 请求、平均输入 715 token、输出最多 512 token、并发上限四、每秒 0.2 个请求时，同时满足 TTFT≤5 秒与 TPOT≤100 毫秒的请求占 87.4%。

该配置的第 99 百分位 TTFT 为 6.21 秒，TPOT 为 101 毫秒，均超过目标。这说明系统能改善低并发服务，但没有让所有请求达标。批量增大可能提高总吞吐，却让每个请求等待更久；不能仅凭吞吐提升推断尾部延迟必然更好。[Tables 5/9 与 §7](https://arxiv.org/html/2610.01265v1)

### 最值得带走的是分工方法，而不是一个固定精度配方

精读时先沿 Figure 9 追踪一个重要专家：哪些矩阵在哪边，何时传中间结果，CPU 最后还做什么。再读 Figure 8 与 §4.3，理解为何精度选择要考虑两边谁更慢。最后将 Table 8 的吞吐、Table 9 的请求延迟和 Table 10 的整机内存放在一起判断部署价值。

对实际系统的启发是：先问能否把大块数据分成常用主体与按需补充，再确认计算是否允许分开、非线性在哪里迫使汇合。这是从本文机制得到的思考方法，不意味着所有模型层都适用。更快的 GPU、更慢的 CPU 或不同带宽都可能移动瓶颈，原有精度配置与加速比需要重新验证。

## 选读 · Stepped MoE: Segment-Level Routing with Configurable Inference Complexity

**年份 / 发表信息：** 2026 · arXiv 2026 · Apple · v1 2026-10-05 · [原文](<https://arxiv.org/abs/2610.07348v1>)

**阅读建议：** 值得选择性精读。先读 Figure 2、§2.3–2.5 理解选专家和多预算训练，再看 Table 1、Appendix A.6/A.7；§3.4 的延迟来自模拟器，不能当作手机实测。

### 如果连续写一句话时，暂时不换专家会怎样？

假设一台设备的内存只装得下部分专家。普通 token 级路由可能刚生成一个词就换一批专家，新的权重又得从存储设备读取。Stepped MoE 提出一个折中：一段生成过程共用一套专家，到下一段才重新选择。它牺牲部分逐 token 调整的自由度，换取更长的权重复用时间；整套模型本来就能常驻内存时，这项搬运收益未必成立。

这篇是 Apple 的 Arnav Kundu 等人于 2026 年 10 月 5 日发布的技术论文。以下依据 CC BY 4.0 的 v1 作解释与评议；它提出的是需要训练的新架构，不能直接给任意已有 MoE 加一个开关就获得同样结果。[原文与许可](https://arxiv.org/abs/2610.07348v1)

### 先看上下文，一次选好后面各层的专家

论文模型有 56 层，前 12 层是始终执行的稠密层，后 44 层使用专家。前面的层先理解输入，再由一个选择器为后面所有专家层生成选择掩码。掩码就是“这层启用哪些专家”的清单；一旦清单确定，系统可以提前加载后面层的权重，而不必逐层等路由结果。

生成回答时，第一份清单依据提示词最后一个 token 的表示产生，保留 S 个生成步骤，再按段更新。段内专家输出不像普通路由那样再按逐 token 路由权重组合。这里 S 是复用多长时间，不是选几个专家；两种设置控制不同成本。预训练则使用每段第一个位置的表示选专家，不能借后续内容提前作决定。[§2.3–2.5](https://arxiv.org/html/2610.07348v1#S2.SS3)

### 同一份模型怎样切换 1B 到 4B 的工作量？

总参数表示模型一共保存多少权重；激活参数表示一次计算实际用到多少。本文主要实验保存一份约 12B 总参数的模型，支持约 1B、2B、3B、4B 的激活档位。较大的档位允许选更多专家。系统还把代表目标档位的可学习向量加入输入，让模型知道今天可以使用多少容量。

例如同一应用在内存紧张时选择较小档位、资源充足时选择较大档位，这是架构支持的部署用法，不是论文已经测得的手机体验。12B 的总存储需求仍然存在；运行内存也不只包含激活权重，还要容纳上下文缓存和中间结果。不能把“1B 激活”直接换算成整机只需存放 1B 参数。

### 能切换档位，是训练出来的能力

训练时，同一批样本复制到四个档位，让共享权重同时适应不同容量。论文主要预训练实验使用 1T 文本 token、8192 上下文长度，并作四倍批次复制；这不是只付出一份普通小模型的训练计算。较大档位才常用到的参数更新机会较少，作者通过调整各档位损失权重来补偿，再配合容量向量训练。

这种补偿是实用近似，作者并未声称它等价于逐专家设置学习率。Appendix A.6 另做两档位实验：共享模型的估算训练 FLOPs 对齐的是两份独立基线的总预算，而非每一份基线；该设置下独立训练的 Static S-MoE 在报告的四项指标上都更好。因此，单一模型便于部署多档位，不等于训练一定更省、每档精度都更高。[§2.4、Appendix A.6](https://arxiv.org/html/2610.07348v1#A1.SS6)

### 效果处于稠密模型与逐 token 路由之间

Table 1 的预训练评测中，按 S=32 训练和评测、3B 激活的 Flexible S-MoE 在 MMLU 五样例测试得 62.27%，Dense 3B 为 57.8%，逐 token 路由的 Vanilla MoE 为 66.2%；后者也是 3B 激活、12B 总参数。GSM8K 八样例准确率依次为 48.0%、34.5%、52.8%。这些结果呈现了论文的取舍：共享大量候选专家有收益，限制换专家的频率又会损失一部分灵活性。

不能据此说全部任务都赢。1B 档的 Core-En 零样例综合分为 64.0%，低于 Dense 1B 的 66.2%；它同时包含语言理解、常识和科学知识任务。上面的比较也没有消除多档位训练投入差异，应与前一节的预算对照一起看。[Table 1、§3.1](https://arxiv.org/html/2610.07348v1#S3.SS1)

### 少换专家能更快，但目前的延迟证据是模拟结果

§3.4 使用 NPU 模拟器，结合矩阵乘法延迟与 NAND 存储到 DRAM 内存的传输时间，并考察不同专家缓存命中率。论文报告分段路由接近稠密基线的延迟；这支持减少换入换出的设计动机，却不是某款 iPhone 的端到端实测，也没有证明数据中心 GPU 高并发服务会获得相同收益。

Appendix A.7 则使用另一份 12B 总参数、3B 激活、按 S=16 训练的模型，实际比较推理时 S=16、32、64。MMLU 为 65.3%、65.4%、65.0%，GSM8K 为 51.3%、50.8%、48.9%。因此延长复用时间并非每项任务都立即变差，但确实有质量风险。这张表只给质量；不能自行给它配上不存在的同配置延迟数据。[§3.4 与 Table 9](https://arxiv.org/html/2610.07348v1#A1.SS7)

### 与 RapidMoE 对照，先问允许改变哪一层设计

RapidMoE 面向已有模型，主要改变所选专家的表示精度与 CPU/GPU 执行；Stepped MoE 则把专家多久更换、允许多少激活容量纳入架构和训练。前者需要检查近似计算的质量，后者需要评估新训练成本与路由限制。这是两篇论文之间的分析性比较，不是作者做过的直接速度对决。

建议先画一个两段生成的例子：每段开始选专家，段内反复复用，下一段再刷新。然后看 Figure 2 和 §2.3–2.5，最后读 Table 1、Appendix A.6/A.7。最值得带走的是四个不同的量：总存储、当前激活容量、专家更换频率、实际数据搬运成本。只报其中一个，无法判断部署是否划算。

## 选读 · Semantic Parallelism: Redefining Efficient MoE Inference via Model-Data Co-Scheduling

**年份 / 发表信息：** 2026 · ICLR 2026 · arXiv v5, February 2026; first posted March 2025 · [原文](<https://proceedings.iclr.cc/paper_files/paper/2026/hash/f0552f14388d95b19740dee809f5cad1-Abstract-Conference.html>)

**阅读建议：** 值得精读图 2、3 与 §3.3，再用表 2 区分首 token 延迟和完整回答延迟；附录 C.1 检查旧数据得到的调度规律能否迁移。

### 1. 专家没选错，为什么还是要跨卡跑一趟

先用教学例子看问题：两张卡分别放专家 A、C 和 B、D，一个 token 需要 A、B，就必须跨卡传送中间数据。如果把经常一起使用的 A、B 放到同一卡，并让经常需要它们的请求优先到这张卡，传输就可能减少。这里的专家是模型中的计算子网络；路由器负责选择本次使用哪些专家。[§2、图 3](https://arxiv.org/html/2503.04398v5)

Sem-MoE 把专家摆放和输入调度一起优化，而不只盯着某一边。论文由华为和中山大学团队完成，2025 年首次发布，2026 年 2 月更新至 v5，并正式收录于 ICLR 2026。现在读它的价值是理解怎样减少 MoE 通信，而不是把它当成刚发布的新方案。[原文记录](https://arxiv.org/abs/2503.04398)、[官方会议页](https://proceedings.iclr.cc/paper_files/paper/2026/hash/f0552f14388d95b19740dee809f5cad1-Abstract-Conference.html)

### 2. 从历史输入里，找经常一起工作的专家

作者先运行一批输入，记录每个 token 在各层经常激活哪些专家，再统计成查找表。实际路由仍会受上下文影响，但某些 token 的选择存在稳定倾向，可以用来猜它更适合在哪张卡开始计算。这是统计性的调度提示，不是用 token 编号精确替代路由器。[§3.2](https://arxiv.org/html/2503.04398v5)

离线算法交替调整输入分组和专家分组：既希望相关输入与专家靠近，又要避免工作量挤到少数卡上，并限制每组专家数量相等。求解使用近似的交替优化，不保证找到全局最优方案。部署时按结果重新排列专家及对应路由索引；这里没有重新训练语言模型。[§3.3、附录 B](https://arxiv.org/html/2503.04398v5)

### 3. Attention-DP：把整个请求送到更合适的卡

如果每张卡都有完整的 attention 模块，可以分别处理不同请求，这叫 attention 数据并行（DP）。后面的专家仍然分散在多张卡上，称为专家并行（EP）。Sem-MoE 汇总请求中各 token 的统计倾向，优先把请求安排到更可能拥有所需专家的设备，而不是简单轮流分配。[§3.1、§3.3](https://arxiv.org/html/2503.04398v5)

但不能把所有相似请求都挤到同一卡。算法每分配一张卡就暂时屏蔽它，等这一轮各卡都拿到请求才重置。因此它同时顾及相关性和请求数分配。请求数均匀不代表不同长度请求的计算时间一定相等；这是应用到真实服务时仍需注意的条件。[附录 B、算法 2](https://arxiv.org/html/2503.04398v5)

### 4. Attention-TP：在本来就要通信时重排 token

如果一个 attention 计算本身拆到多张卡共同完成，就是张量并行（TP）。这时不能靠选择一张卡接整个请求解决问题。各卡产生的部分结果原本就需要合并；Sem-MoE 把合并与分发安排在一起，让 token 合并后的结果尽量落到拥有相关专家的卡上。[§3.1、§3.4](https://arxiv.org/html/2503.04398v5)

具体做法是带重排的 reduce-scatter：先合并部分结果，再分给各卡；MoE 完成后再 allgather 收集结果，并恢复 token 顺序。预测既参考 token 的历史统计，也参考此前层的专家设备选择。实际路由器仍决定该调用哪些专家；猜错主要会失去减少传输的机会，而不是因此强行改用别的专家。[§3.3–3.4、附录 B.2 算法 3](https://arxiv.org/html/2503.04398v5)

### 5. 首 token 更快，不等于完整回答同幅度变快

实验使用单机 8 张加速卡，每卡 96GB HBM，互联带宽超过 400GB/s，未注明具体卡型号。主要模型是 DeepSeek-V2-Lite 和 Qwen3-30B-A3B，比较 SGLang 及接入同一框架的 MoETuner。使用 MMLU、LMSYS 和 ShareGPT 的输入文本；每个数据集 20% 用于建立预测与放置表，80% 用于采样实验请求。[§4.1–4.3](https://arxiv.org/html/2503.04398v5)

看表 2 的一个具体配置：Qwen3-30B-A3B、Attention-TP、每秒 1 个请求、输入 512 token；输出长度固定，但表中未列出具体长度。SGLang 的 p99 首 token 延迟为 104.76ms，Sem-MoE 为 83.87ms；完整回答延迟的中位数则从 766.80ms 变为 759.16ms。p99 表示约 99% 请求不超过这个延迟。两种指标的变化幅度很不同，不能把首 token 的改善当成整段生成同样加速。[§4.4、表 2](https://arxiv.org/html/2503.04398v5)

### 6. 旧的统计规律，还能用于新的请求吗

作者另外检查跨数据集迁移：DeepSeek-V2-Lite 用 ShareGPT 建表，再处理 LMSYS 输入，本卡专家激活比例达到 41.25%，SGLang 为 25.01%。这个比例表示有多少专家计算可以留在输入所在卡上，不是答题准确率，也不直接等于吞吐提升。它支持统计规律有一定迁移性，不能证明任意新业务都适用。[附录 C.1、表 3](https://arxiv.org/html/2503.04398v5)

主要性能测试固定输入和输出长度，且在单机高速互联上完成。把方法用于请求长度差异大、流量持续变化或多机服务，还要重新判断预测、排队和通信的成本。与主读通过 CPU/GPU 协同减少权重搬运相配合，本篇让我们多问一步：能否先减少数据必须去远端找专家的次数？这是一种可比较的设计选择，并不保证任何部署都更优。[§4.1、§4.3](https://arxiv.org/html/2503.04398v5)
