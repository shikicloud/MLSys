# Attention 怎样变快：减少等待、降低精度、重新分工

主读2026年的 FlashAttention-4，解释 Blackwell 上矩阵乘变快后，softmax、数据搬运和线程协作为什么会成为瓶颈。选读 SageAttention3，理解 FP4 推理和 INT8 训练分别怎样取舍速度与误差；再读 FlashInfer，把高效算子接到变长请求、共享前缀和 CUDA Graph 的服务现场。三篇从计算流程、数值精度和负载分配三个角度展开。先读主文的具体例子，不必一天读完；所有性能数字保留原实验条件，不把单算子加速当成整个服务的加速。

每天推荐 1 篇主读与 2–4 篇选读，覆盖 LLM Inference、RL Infra、Post-Training、RSI（递归自我改进），以及推理计算、Agent 学习与记忆、数据评估和模型架构。经典与前沿并行，按主题逐步展开；不要求与当前工作直接相关。候选不等于已读，无需一天读完。

## 主读 · FlashAttention-4: Algorithm and Kernel Pipelining Co-Design for Asymmetric Hardware Scaling

**年份 / 发表信息：** 2026 · MLSys 2026 · arXiv v1, 2026-03-05 · [原文](<https://arxiv.org/abs/2603.05451v1>)

**阅读建议：** 值得精读。优先跟着一个128×128分块读图1、表1、表2，再看图3的反向协作，最后检查基线版本与消融条件。

### 先看一次注意力计算：乘法算完，还不能直接输出

假设正在处理一段输入，其中每个注意力头的向量长度为128。取128个查询向量Q，与128个键向量K计算相似度，就得到一块128×128的分数S；随后逐行做softmax，把分数变成权重，再用权重对值向量V加权求和。softmax要先减去一个共同参照值，再算指数、求和和归一化。于是一次注意力计算至少串着两次矩阵乘法，以及它们中间一整段非矩阵乘法工作。这是后文一直使用的分块例子。[§2.1](https://arxiv.org/html/2603.05451v1#S2.SS1)

FlashAttention系列不把整张序列长度×序列长度的分数表写回显存，而是逐块读取K、V，保留必要的统计量和累计输出。FA4继续计算这种稠密注意力：它没有靠删掉“不重要”的token来减少任务量。新问题是，在Blackwell上，矩阵乘法变得更快以后，其余步骤能不能跟上？[§1、§3.1](https://arxiv.org/html/2603.05451v1#S3.SS1)

### 硬件并非一起加速：指数计算和片上搬运开始卡住流水线

GPU中的Tensor Core专做矩阵乘加；MUFU是能执行指数等特殊函数的单元；shared memory是线程块共享的一小块片上存储。论文按每个SM、每个时钟周期比较：Hopper到B200，BF16矩阵乘加能力从4096增至8192次运算，指数吞吐仍是16次，共享内存读取仍是128字节。SM可以理解为GPU上执行线程块的一组计算资源。乘法能力翻倍，不会让每个中间步骤也自动快一倍。[§2.2](https://arxiv.org/html/2603.05451v1#S2.SS2)

对刚才128×128、头维128的分块，表1的简化估算是：两次矩阵乘法需要1024周期，指数也需要1024周期，共享内存读取需要768周期。它不是实测总延迟，更不能把三项直接相加；不同单元可以重叠工作。它说明的是：即使让矩阵乘法接近峰值，指数仍足以让整条流水线等待。因此优化目标变成减少等待、给瓶颈分担工作。[§3.1.1、表1](https://arxiv.org/html/2603.05451v1#S3.SS1.SSS1)

### 前向流水线：准备两块查询，让乘法与softmax交替前进

FA4让一个线程块同时负责两块Q，每块都是128个查询。计算第一块的softmax时，可以推进另一块的矩阵乘法；论文称它为ping-pong安排。Blackwell会把矩阵乘法结果异步写进TMEM——Tensor Core专用的片上存储，而不必一直占着线程寄存器。两个128线程的工作组分别负责两块softmax，每个线程处理一整行；它们还会错开指数计算的关键阶段，避免同时争抢同一组指数单元。[§3.1.2、图1](https://arxiv.org/html/2603.05451v1#S3.SS1.SSS2)

另一个工作组专门修正累计输出的缩放，减少softmax主路径必须等待的工作。权重P也分批写入TMEM：先写前四分之三并启动相应乘法，再写最后四分之一，避免线程同时握住太多临时数值。正式会议版还有直接消融：B200、非因果注意力、16个头、头维128、长度16384、batch 2时，默认前向耗时2.817毫秒，只保留一块Q的版本为4.234毫秒；这是单核配置对比，不是整模型加速比。[会议版附录B，表5、7](https://proceedings.mlsys.org/paper_files/paper/2026/file/ae8b0b5838ba510daff1198474e7b984-Paper-Conference.pdf)

### 给指数单元分担工作：只让一部分元素走多项式近似

指数可以换成以2为底来算。FA4把2的x次方拆成“整数部分对应的2次幂”乘“0到1之间小数部分对应的2次幂”：前者借助浮点数的位表示，后者用多项式近似。这样一部分指数就能交给普通乘加单元，与硬件指数指令并行。论文只把每行约10%–25%的元素这样处理，其余仍用MUFU；全部改成多项式反而会增加寄存器占用和计算延迟。[§3.1.3](https://arxiv.org/html/2603.05451v1#S3.SS1.SSS3)

这确实引入了数值近似。表2对[0,1)内400万个随机输入、以FP64为参考测试：三次多项式的FP32最大相对误差约8.77×10⁻⁵，高于硬件指数的1.41×10⁻⁷；但转成BF16后，两者最大相对误差约为3.90×10⁻³和3.89×10⁻³。BF16舍入误差在这个测试中占主导，不等于输出逐位相同，也不是长时间训练、任意输入分布或最终模型质量的完整验证。[表2](https://arxiv.org/html/2603.05451v1#S3.SS1.SSS3)

### 少做重复缩放：保留同一个参照值也能正确合并

为了看懂“有条件地缩放”，从一行里只挑四个分数，分成两块。下面是教学算例，分数已换成以2为底的单位：第一块是[10,9]，减去参照值10，得到指数权重[1,0.5]；第二块是[11,8]。通常的在线softmax会把参照值升到11，先将旧累计量乘0.5，再加入新权重[1,0.125]。FA4可以暂时保留10，直接加入[2,0.25]。只要加权输出与分母使用同一个参照值，最终相除的答案相同：两套权重只是整体差一倍。[§3.1.4](https://arxiv.org/html/2603.05451v1#S3.SS1.SSS4)

论文只在新最大分数与旧参照值的差超过阈值时，才更新参照值；以2为底的实现中，典型阈值8对应256倍的缩放范围。没有触发时，并非忘记补乘一个系数，而是连参照值也暂不更新，继续一致地累计分子与分母。这个代数改写在实数运算中保持等价；浮点实现仍受可表示范围和舍入影响，不能说最后一次归一化会消除所有数值误差。实际还按warp（32个线程组成的一组）统一决定是否缩放，避免相邻线程走不同分支。

### 反向传播的瓶颈不同：先减少中间结果的片上搬运

训练时，前向给出输出O之后，还要计算损失对Q、K、V的梯度，分别记作dQ、dK、dV。它们表示Q、K、V的各分量发生微小改变时，损失会怎样变化。FlashAttention没有保存整张权重表，所以反向会重算分数S，再完成dP、dV、dQ、dK等矩阵乘法，共五次。论文对128×128、头维128的1-CTA方案估算：矩阵乘法2560周期，共享内存访问3328周期。这里更急迫的问题是中间数据来回搬，而不只是指数计算。[§2.1、§3.2.1、表3](https://arxiv.org/html/2603.05451v1#S3.SS2)

FA4把更多结果留在TMEM，并把上一轮的dQ、dK乘法与当前轮的逐元素计算穿插执行。空间并不无限：TMEM放不下五块128×128的FP32累计结果，因此必须安排谁先用、谁后用；例如某块分数S用完后，原位置可存权重P。流水线的改进来自数据的存放位置、使用顺序和计算依赖一起设计，而不是简单多启动几个并发任务。[§3.2.2、图2](https://arxiv.org/html/2603.05451v1#S3.SS2.SSS2)

### 两个线程块协作：少重复读数据，也少做全局累加

CTA就是一个协同执行的线程块。Blackwell的2-CTA模式让同一cluster（可协作的线程块组）里的两个线程块协作完成较大的矩阵乘法，每块只准备其中一半B操作数，并保存自己的输出部分。反向计算dQ时还需要特殊处理：两个块原本各掌握一段K对应的贡献，而每个查询行需要把两段都加起来。FA4通过cluster内的分布式共享内存交换一半dS，使每块拿到自己查询行所需的两段贡献，再做乘法与合并。代价是多了一次片上交换；收益是减少重复读取，并把全局dQ原子累加次数减半。[§3.2.3、图3](https://arxiv.org/html/2603.05451v1#S3.SS2.SSS3)

原子累加保证多个线程块共同更新数据时不丢写入，但到达顺序可能变化，浮点加法的结果也可能随之变化。FA4另提供确定性反向模式：线程块按预定顺序取得信号量，完成累加后再交给下一块。它会引入等待与同步成本；解决的是这里的跨线程块归约顺序，不自动保证换batch形状仍逐位相同，更不是整个训练与推理系统的零差异证明。[§3.2.4](https://arxiv.org/html/2603.05451v1#S3.SS2.SSS4)

### 调度也要看工作量：先做长任务，同时保住缓存复用

因果注意力中，靠前的查询只能看较少历史，靠后的查询需要读取更多K、V块。如果按从短到长分发，很多计算单元可能先忙完，最后只剩少数单元处理最长的任务。FA4优先安排较长的工作块，同时按头分组，让可能复用的K、V尽量还留在L2缓存中。它不是不管缓存地把所有任务按长度排序；变长输入也可以先生成一个重排索引，改变工作次序而不改变答案。[§3.3](https://arxiv.org/html/2603.05451v1#S3.SS3)

这与上一节确定性反向里的特殊顺序要区分：后者还受“谁必须先取得累加锁”约束，论文为因果反向设计了避免第一次写入就等待的短任务优先安排。对系统研究的启发是，最佳顺序同时取决于算多久、复用什么数据、要等谁；不能把“最长任务优先”或“最短任务优先”当成通用策略。这里讨论的是单个attention kernel内的工作块调度，不是完整服务系统的请求调度。[§3.2.4、§3.3](https://arxiv.org/html/2603.05451v1#S3.SS2.SSS4)

### 实验到底快了多少：先固定卡、形状、精度和基线版本

主实验按正文使用B200、BF16输入，序列长度从1K到32K，调整batch使总token数保持32K，覆盖因果与非因果注意力，预热5次后测量10次取平均。图4的头维128配置有16个头；论文报告前向相对cuDNN 9.13约1.1–1.3倍、相对Triton约2.1–2.7倍，最高1613 TFLOPs/s，约为所用理论峰值的71%。这是按矩阵乘法工作量折算的attention kernel吞吐，不是整模型每秒token数。附录所列Triton为3.6，FA3本身不能作为直接运行在B200上的基线。[§5、图4、附录A.1](https://arxiv.org/html/2603.05451v1#S5)

必须一起读的限制是：同一篇论文已经加入cuDNN 9.19.1.2，并说明更新版本吸收了相关技术，性能接近FA4。因此旧版本上的最大倍率不代表今天换库必然有同样收益。图里的长序列、前后向kernel结果，也不能直接推成单token decode延迟或Agent端到端收益。硬件名称另有版本差异：arXiv附录写B100，正文写B200；正式会议版附录A.1明确为B200 180GB SXM6、1000W，本笔记以该正式说明校对。[会议版附录A.1](https://proceedings.mlsys.org/paper_files/paper/2026/file/ae8b0b5838ba510daff1198474e7b984-Paper-Conference.pdf)

先读§2.1与表1，用128×128这块数据跟一遍“算分数→指数→加权求和”；再对照图1读§3.1.2–3.1.4，逐个追踪等待、寄存器压力、近似和缩放。随后读图2、图3与表3，看反向为什么换成共享内存瓶颈；最后对照§5和会议版附录B判断每项优化的证据。实现语言部分§4也值得看：论文用Python中的CuTe-DSL编译GPU代码，语言换了，显式管理流水线与内存的责任仍在。这是论文实现描述，不是对今天仓库默认行为的检查。

## 选读 · SageAttention3: Microscaling FP4 Attention for Inference and An Exploration of 8-Bit Training

**年份 / 发表信息：** 2025 · NeurIPS 2025 · Tsinghua University / Shengshu Technology · first preprint 2025-05-16; arXiv v3 2026-01-14 · [原文](<https://arxiv.org/abs/2505.11594v3>)

**阅读建议：** 值得选读。先读 Figure 2 与 Algorithm 1，再看 §3.2 的两级缩放；关注训练时，接着读 Algorithm 3、Figure 8 和 Appendix A.6。

### 加速的是两次乘法，不是把整套模型都变成 FP4

可以先想一个视频生成步骤：当前画面中的一小块，需要从其他位置取得有用信息。attention 先让它的 query 向量 Q 与其他位置的 key 向量 K 做点积，得到相关程度；softmax 再把这些分数转成非负、总和为一的权重 P；最后用 P 对 value 向量 V 加权求和。主要计算可简写为 `S=QKᵀ`、`P=softmax(S)`、`O=PV`。SageAttention3 要加速的是其中两次矩阵乘法，利用 Blackwell GPU 能快速处理的 FP4，也就是每个数只用 4 bit 表示的浮点格式。[§2–3 与 Figure 2](https://arxiv.org/html/2505.11594v3#S3)

低位数的代价是可表示的数很少，原来的数必须舍入到邻近值。论文仍沿用 FlashAttention 分块计算和在线 softmax，避免把完整的分数矩阵写回显存；但矩阵乘法的输入会经过量化，因此结果允许近似。softmax、缩放和累加也并非一律使用 FP4。它没有把全模型权重都变为 FP4，更不是一项把长期 KV cache 压成 4 bit 的存储策略；这里讨论的是 attention 计算路径。[§2、§3.1 与 Algorithm 1](https://arxiv.org/html/2505.11594v3#S3.SS1)

### 为什么每 16 个数需要一个自己的缩放因子？

先看一个自拟的数值情形：大部分数接近 0.1，但远处出现一个很大的值。若整条向量共用一个缩放因子，为容纳大值，小值之间的差别可能被舍入抹掉。论文选择 NVFP4：每 16 个数共享一个 FP8 缩放因子，各个数存成 FP4，计算时两者共同表示原数。这种 microscaling 把大值的影响限制在较小组内。NVFP4 的数值格式是 E2M1、缩放因子是 E4M3，意思分别是指数和尾数使用的位数；它与每 32 个数一组、采用另一种缩放格式的 MXFP4 不相同。小组缩放能改善误差，但同组内仍有大值时，并不会自动解决所有问题。[§3.1 与 Table 1(a)](https://arxiv.org/html/2505.11594v3#S3.SS1)

作者还沿用前作的 Q/K 平滑：先减去共同的偏移，让送入量化的数据更集中。对所有 key 减去同一个均值，会让一个 query 对应的整行分数都减去同一常数；在精确运算下，softmax 对这种变化不敏感。对一块 query 减均值则不同，因为被减掉的部分对不同 key 的影响不同，所以必须另算均值与 key 的乘积并加回。Algorithm 1 里的补偿项正是为此而来。这个区别解释了为什么平滑不是随意删去大数，也不意味着后面的舍入误差消失。[Algorithm 1 与 Appendix A.7](https://arxiv.org/html/2505.11594v3)

### 更隐蔽的误差：缩放因子自己也存不准

第二次乘法还会遇到小数问题。实现中量化的是在线 softmax 暂时生成的指数值 P̃，它还要经过后续归一化，不能直接当成最终概率 P。设某个数据块最大的值只有 0.0006，这是帮助理解的自拟例子。若直接按 FP4 最大值 6 来计算缩放因子，会得到 0.0001；这个缩放因子还必须存进 E4M3 FP8，本身就可能舍入到零。即使 FP4 数值选得再仔细，乘回一个错误的缩放因子，也无法恢复原来的小数。[§3.2 与 Figure 3](https://arxiv.org/html/2505.11594v3#S3.SS2)

两级缩放把这个问题拆开：先为每一行算一个 FP32 因子 `a=rowmax(P̃)/(448×6)`，用 P̃ 除以 a 放大数值，再做每 16 个数一组的 FP4 量化。448 是这里 FP8 缩放格式的最大有限值，6 是 FP4 的最大数值。乘法结束后再乘回 a，并继续在线 softmax 的归一化。这样，小数的总体量级由较高精度的 a 保存，FP8 因子主要描述放大后的局部大小。它改善了表示范围的使用，并没有把 FP4 变成精确计算；正文的两级缩放实验测量的也正是减少了多少误差。[公式 5 与 Algorithm 1](https://arxiv.org/html/2505.11594v3#S3.SS2)

### 更快的 Tensor Core，还需要处理数据搬运和质量取舍

硬件速度不会自动变成完整 kernel 的速度。量化要找局部最大值，不同线程还要交换数据；第二次乘法要求的 V 布局也会增加转置成本。论文把部分最大值归约与在线 softmax 合并，并把 V 的转置并入量化过程，减少额外工作。在 RTX 5090 上，Figure 4–5 对 head dimension 为 128 和 64、不同序列长度的 attention kernel 做比较，正文报告相对 FlashAttention2 约 4–5 倍加速。这个数字属于这些核测试，不能直接写成整套模型或单 token 解码快 5 倍；对照是论文当时在这张 GPU 上使用的 FlashAttention2，不是把不同 GPU 上的 FlashAttention3 拿来混比。[§3.3、§5.2、Figure 4–5 与 Appendix A.5](https://arxiv.org/html/2505.11594v3)

质量也要逐项看。论文用 Open-Sora 的提示集测试视频生成；Table 2 中，HunyuanVideo 的文本匹配指标略升，但用于评价时序一致性的 Flow-score 从 16-bit 对照的 1.4793 降至 1.232，按表中箭头是越高越好。因此不能把平均观感接近写成所有指标不变。Appendix A.6 还在 CogVideoX-2B 上观察到跨层误差累积，并另外试验将误差增长最大的三个层保留 FP16。这个补救实验说明精度选择可能需要按层处理，不能据此假定所有主表结果都用了相同的回退策略。[Table 2、Appendix A.3 与 A.6](https://arxiv.org/html/2505.11594v3)

### 训练部分为什么另用 INT8，还留下一次 FP16 乘法？

SageBwd 是论文的另一套方案，采用 INT8 整数量化，而不是把 FP4 推理核直接拿来训练。训练除了计算输出，还要反向计算梯度：哪些输入的变化会让损失增大或减小。论文统计 attention 前向两次、反向五次矩阵乘法，其中六次使用 INT8，唯独 `dP=dO·Vᵀ` 保留 FP16。这里 dO 是损失对输出的梯度，dP 是损失对 attention 权重的梯度。换言之，这一步决定模型应怎样调整各位置的关注程度。[§4 与 Algorithm 3](https://arxiv.org/html/2505.11594v3#S4)

保留它的原因是误差会继续传下去：dP 影响分数梯度 dS，dS 又参与 Q、K 的梯度计算，沿序列分块累加时可能不断积累偏差。作者选择保护这个敏感环节，而非统一降低所有运算的精度。在 RTX 4090、head dimension 64/128 的前向加反向核测试中，SageBwd 相对 FlashAttention2 最高约 1.67 倍；这仍然不是完整训练步的同幅加速，也不代表权重、优化器状态和所有梯度都采用 8 bit。[§4.2、§5.2 与 Figure 6–7](https://arxiv.org/html/2505.11594v3#S4.SS2)

### 微调接近不等于预训练可靠：建议这样精读

语言模型部分以 Qwen2.5 和 Llama3.2 为对象，对数学问答 GSM8K、阅读理解 DROP、知识问答 MMLU、常识补全 HellaSwag 分别做微调与评估。Appendix A.3 的微调设置为 700 步，Table 3 和多随机种子补充实验表明 INT8 attention 与 BF16 的任务分数大体接近，但有升有降；这不是零梯度误差的证据。另一个实验从头训练 400M 参数的 Llama 型模型，使用 FineWeb-Edu、每步 200 万 tokens，Figure 8 显示 8-bit 方案收敛较慢。§5.3 还有单独的 1,000 步微调后使用 FP4 推理的搭配实验，不能与前述 700 步设置混为一谈，更不能由此推出它适合长周期 RL。[§5.2–5.3、Figure 8 与 Appendix A.3–A.4](https://arxiv.org/html/2505.11594v3)

阅读顺序建议是 Figure 2 → Algorithm 1 → §3.2，先弄清量化数值和缩放因子分别承担什么；再读 Algorithm 3 与 Figure 8，理解推理误差为何不等同于训练误差；最后检查 Table 2 和 Appendix A.6 的反例。本文依据 Jintao Zhang、Jia Wei 及合作者的 [arXiv v3（2026-01-14）](https://arxiv.org/abs/2505.11594v3)，会议身份由 [NeurIPS 2025 官方论文集](https://proceedings.neurips.cc/paper_files/paper/2025/hash/4db397e0f760cc573c681e81a01a3dba-Abstract-Conference.html)核实。原文采用 [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)，本笔记是解释性改写与评议；标出的数值小例子为自拟，不是论文实验。

## 选读 · FlashInfer: Efficient and Customizable Attention Engine for LLM Inference Serving

**年份 / 发表信息：** 2025 · MLSys 2025 · arXiv v1 2025-01-02, v2 2025-04-21 · University of Washington / NVIDIA / CMU / Perplexity AI and collaborators · [原文](<https://arxiv.org/abs/2501.01005v2>)

**阅读建议：** 值得选读图2、图3、算法1和图6；若正在做 serving，再精读评估与附录 G.3。

### 先看服务现场：一批请求并没有相同的工作量

假设一轮生成里，三个请求分别有 1,000、1,000 和 12,000 个历史 token，每个请求都只要生成下一个 token。这是教学例子：如果按“一请求一个工作单元”分工，前两个很快结束，第三个还要继续读很长的 KV cache。即使每个工作单元内部的矩阵乘已经很快，整轮仍可能被最后一个拖住。KV cache 是前面 token 的键和值，后续生成要读取它们来计算注意力。

FlashInfer 讨论的正是这种服务环境：请求长度不断变化，KV 可能按页分散存放，多个候选回答又可能共享同一段开头。论文将缓存访问方式、单块计算和任务分配分开设计，让它们能组合使用。本文固定阅读 2025 年 4 月的 v2；它是华盛顿大学、NVIDIA、CMU、Perplexity AI 等作者合作的 MLSys 2025 论文。今天读它，是为了把前两篇的算子优化接到实际服务负载上。[原论文](https://arxiv.org/html/2501.01005v2)、[会议记录](https://proceedings.mlsys.org/paper_files/paper/2025/hash/dbf02b21d77409a2db30e56866a8ab3a-Abstract-Conference.html)

### 先解决去哪里读：把页表看成一张访问清单

想象给每组 query 列出它要读的 KV 页编号。query 是当前 token 发出的查询向量；页编号告诉算子，相关的历史数据实际放在哪。FlashInfer 把这种访问清单表达成块稀疏矩阵：行对应 query 块，列对应缓存块，有条目的位置表示需要访问。这里的“稀疏”可以只是在描述不同请求与物理缓存页的对应关系，不意味着模型自动丢掉了自己应该看的历史 token。[§3.1.1、图2](https://arxiv.org/html/2501.01005v2#S3.SS1)

物理页可以分散，矩阵乘的输入却需要规则排列。因此，使用 Tensor Core 的算子根据索引，从显存中收集相应 KV，放进 GPU 芯片内的共享内存，再交给 Tensor Core 做矩阵乘。共享内存是一个线程块内协作使用的暂存区。论文还把 query/output 紧凑地拼在一起，避免把短请求补到最长请求的长度。收益来自减少无用存储和兼容多种布局，代价则包括索引计算与不规则数据搬运；页表统一并没有让这些开销消失。[§3.1–3.2](https://arxiv.org/html/2501.01005v2#S3)

### 共享前缀为什么还要拆开计算？

再设想同一个长提示词生成四个候选回答：开头的 KV 相同，后面各自生成的 KV 不同。把前缀在显存里只存一份，已经节省容量，但四个独立的计算单元仍可能分别把它读一遍。论文把“大家共享的部分”和“各自独有的部分”分别组织：共享部分将多条 query 放进同一计算块，以便复用加载到共享内存的 KV；独有部分按各自的索引计算。分解主要改变索引，无需把整份 KV 重新搬到另一种物理布局。[§3.1.2、图3](https://arxiv.org/html/2501.01005v2#S3.SS1)

两部分结果不能直接求平均，因为它们得到的注意力权重总量可能不同。每部分都保留输出，以及未归一化权重之和的对数，称为 LSE（log-sum-exp）。合并时按两部分的权重总量重新加权。例如某一 query 对前缀和后缀的权重总量是 9 与 1，最终输出就是两部分输出的 0.9 与 0.1 加权和，而不是各一半；这些数仅用于说明公式。该合并在数学上保留完整 softmax 注意力的结果，有限精度下仍可能有舍入差异。[§2.2，式1–3](https://arxiv.org/html/2501.01005v2#S2.SS2)

### 长请求切小块，短请求不用等一整条长队

回到 1,000、1,000、12,000 token 的例子，FlashInfer 会先根据 query/KV 长度估计工作量，将较长的 KV 区间进一步切分，再把这些小任务分给 GPU 工作单元。论文算法按任务长度排序，逐个把任务交给当前估计负载最轻的线程块；实际切分大小由整批工作量与线程块数量共同决定，并不是固定把每个请求切成同样多份。长请求可以由多个线程块共同完成，之后用上一节的注意力状态合并结果。[§3.3.1、算法1](https://arxiv.org/html/2501.01005v2#S3.SS3)

这种分工更均匀，但也需要存中间输出、运行合并步骤。论文因此把 plan 与 run 分开：CPU 先算分工清单，复制到固定的 GPU 缓冲区；GPU 再读取清单执行。每一步生成重新规划，同一步多个模型层若长度配置相同，就可以复用计划。GPU kernel 的启动规模和缓冲区地址保持稳定，允许重放 CUDA Graph——预先记录好的 GPU 操作流程——同时让清单内容随请求变化。计划本身在 CPU 上，不在所捕获的图内。[§3.3–3.4、图6](https://arxiv.org/html/2501.01005v2#S3.SS3)

### 可定制的算子，实验到底测了什么？

论文也允许使用者指定 query/key 的变换、注意力分数的变换与 mask，再把这些逻辑填进 CUDA 模板，在初始化时编译并缓存。这样，旋转位置编码 RoPE 等变换有机会和注意力融合，减少单独运行、写回显存再读出的过程。这里的“可定制”有明确的接口和模板边界，不能理解为任意 Python 程序都能自动变成最快 kernel。[§3.2.3、§4.3](https://arxiv.org/html/2501.01005v2#S3.SS2)

论文评估的是 FlashInfer v0.2。在线服务实验将它接入 SGLang v0.3.4，与同框架的 Triton v3.0 后端比较；模型是单张 H100 上的 Llama 3.1 8B 和四张 H100 上的 70B，负载包括 ShareGPT 以及长度均匀分布在 512–2,048 token 的合成请求，调整请求率使首 token 延迟的 P99 小于 200 ms。在这些条件下，作者报告 token 间延迟下降 29%–69%；这组在线服务实验使用 FP16、CUDA 12.4 和 PyTorch 2.4.0。这个数字不是今天各框架最新版的排名，也不能与前两篇的单算子峰值吞吐直接比较。[§4.1、图7](https://arxiv.org/html/2501.01005v2#S4.SS1)

### 值得带走的设计，以及还没有保证的事

最值得带走的是“先检查负载，再执行计算”的分离方式：模型算法可以不变，运行时仍有机会通过任务切分和共享数据减少等待。也要算清新增的 CPU 规划、元数据复制和结果合并成本；前缀共享很少或任务很小时，额外机制未必划算。论文避免无序的原子累加，在相同长度信息下产生固定的聚合顺序，但这不等于跨不同 batch、不同硬件或训练/推理两端逐位一致。后一句是对其保证范围的分析，不能把它宣传成 zero mismatch。[§3.3.1、§4.4](https://arxiv.org/html/2501.01005v2#S3.SS3)
